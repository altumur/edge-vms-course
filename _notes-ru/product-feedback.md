## A. Go-порт потерял ветку возрождения строки

**Было самым серьёзным из найденного.**

Питоновский [урок 10 М10A](../М10A_Platform/10-SpecController-rows.md) разбирает случай «оператор выключил запись, через час включил снова» на целую страницу, перечисляет три неверных варианта и выбирает четвёртый:

> Отказать («уже существует») — неверно: удалённая единица не существует. Записать заново с `cas=0` — невозможно: ключ-то есть, помеченный. Стереть и создать — потеря истории: ревизия начнётся с единицы, и любой, кто помнил ревизию 5, увидит 1 и решит, что строка **откатилась**.
>
> Выбрано четвёртое: новая запись, ревизия на одну больше старой, по CAS на прочитанный индекс.

В Go-порте этой ветки не было: надгробие читалось как «единица существует». Следствие для продукта — **«Стоп записи» нажимался один раз на камеру и не отменялся никогда**, и это ровно та кнопка, которую страница [урока 16 М10A](../М10A_Platform/16-HTML.md) предлагает нажимать. То есть Go-реализация ломала сценарий, который сама же и рисовала.

**Куда легло.** Ветка перенесена. Теперь проверка различает живую строку и надгробие:

```186:190:vmsserver-go/w2cplatform/placement.go

		if old != nil && old["deleted"] != "true" {
			return nil, &Refused{fmt.Sprintf("%s unit %s exists", c.Spec.Name, name)}
		}
		if old != nil {
```

Вместе с веткой переехала и мелочь, на которой мы споткнулись: в возрождении `uid` ещё не присвоен, и `NewRow(uid, …)` тихо кладёт `id: nil` — строка создаётся, но размещения не получает, потому что идентификатор пустой. В курсе стоит правильная форма:


## B. Конвейер не мог запускаться против браузера

**Была самой дорогой для диагностики ошибкой из всех.**

Урок платил полезную нагрузку один раз, в общем источнике: `rtph264pay config-interval=1 pt=96` стоял до `tee`.

Номер 96 у Chrome — это **VP8**. H.264 он раздаёт по 102, 108, 116, 118 и далее, по паре на профиль и режим пакетизации, и номера у разных браузеров разные. А ответ SDP вправе использовать только номера из оффера.

Что при этом видно: сессия устанавливается, ICE соединяется, DTLS проходит, `bytesReceived` растёт до мегабайтов, `packetsLost` равен нулю, `framesDecoded` равен нулю, `codecId` у `inbound-rtp` отсутствует — и **ни одной строки ни в одном логе**, ни у GStreamer, ни у браузера. Вкладка молча выбрасывает каждый пакет, потому что 96 для неё значит VP8.

До этого есть ещё одна ступень: если номер в capsfilter не совпадает с оффером, `webrtcbin` не находит соответствия и возвращает ответ с `a=inactive` — сессия «работает», медиа нет.

**Причина структурная**, а не опечатка: номер назначает браузер, значит упаковщик принадлежит ветви зрителя, а не общему источнику. Два браузера с разными номерами один общий `rtph264pay` обслужить не может в принципе.

**Куда легло.** Урок 13 перестроен целиком. `tee` несёт элементарный поток, а не RTP:

> `rtspsrc location={url} latency=200 protocols=tcp ! rtph264depay ! h264parse config-interval=-1 ! tee name=t allow-not-linked=true`

Упаковщик уехал в ветвь зрителя — `tee ! queue ! rtph264pay pt=<номер этого зрителя> ! capsfilter ! webrtcbin`, — а номер вычитывается из оффера чистой функцией `h264_payload_type` в `gstvms/payload.py`, у которой пять тестов. Диапазон 96..127 и предпочтение `packetization-mode=1` названы с причинами: браузер вправе назвать H.264 и ниже динамического диапазона, а `rtph264pay` объявляет исходный pad только над ним; при режиме 0 в один пакет кладётся один NAL, и ключевой кадр камеры туда не влезает. Оба отказа попали в раздел «что может пойти не так».

**Две вещи, специфичные для Go**, если порт живого видео когда-нибудь будет. `webrtcbin`, в отличие от `tee`, отдаёт sink-pad только по запросу (`RequestPad`/`RequestPadSimple`), обычный `Link` на нём не работает. А untyped `nil` в `Emit("set-remote-description", desc, nil)` даёт неинициализированный GValue, GLib молча отбрасывает вызов, и симптом — ответ, который никогда не приходит. Нужны типизированные nil.

## C. Первое нажатие Live проваливалось всегда

**Двухстрочная правка, а ломала обещание урока.**

Страница повторяет запрос **только на 503**:

```322:325:М10A_Platform/16-HTML.md
  let r, tries = 0;
  for (;;) {
    r = await fetch(`/whep/${current}`, { method: 'POST', headers: { 'Content-Type': 'application/sdp' }, body: pc.localDescription.sdp });
    if (r.status !== 503 || ++tries > 8) break;
```

Шлюз на вещание, которого у него ещё нет, отдавал `KeyError` → **404**. А не быть его может по совершенно штатной причине: консоль создала строку мгновение назад, контроллер её разместил, но проход самого шлюза ещё не случился — он ходит раз в две секунды.

То есть на первом нажатии Live браузер получал 404 и сдавался, показав «live refused: no such stream here». Обещание урока 12 — «оператор нажал один раз» — не выполнялось ни разу. Мы наблюдали это ровно так.

**Куда легло.** Консоль больше не отдаёт чужой 404 наружу — она переводит его в 503 с объяснением:

> `KeyError` → **404**: «этого вещания нет на этом шлюзе»… Консоль этот 404 наружу не отдаёт: для неё он значит «размещение есть, подписка будет следующим проходом», и она превращает его в 503, который страница повторяет (урок 12).
>
> — [`13-live-video.md`](../М10B_ServerVMS/13-live-video.md)

Соседний код ответа разведён там же: `OverflowError` → 503 «шлюз полон». Это состояние машины, а не ошибка запроса, поэтому контроллер разместит следующие вещания на другом шлюзе.

## D. `codec` был назван, но не объяснён

Урок честно говорил, что камера с потоком, который браузер не декодирует, «отвалится у браузера, и шлюз скажет `codec` в статусе». Не хватало двух вещей: откуда шлюз это узнаёт и как отличить от пункта B.

Симптом у них идентичен — пакеты идут, кадров ноль. У нас совпали обе причины сразу, и это стоило половины отладки.

**Куда легло.** Обе вещи в уроке 13. Источник знания назван: шлюз читает согласованные caps у `h264parse` и сверяет профиль со списком, который берут браузеры, — это единственное место, где известно, чем поток оказался на самом деле, а не что написано в паспорте камеры. Различение тоже записано:

> **Как отличить от неверного номера нагрузки (шаг 6) — по `framesReceived`.** …при неверном номере браузер даже не собирает кадры из пакетов (`framesReceived` ноль, `codecId` у `inbound-rtp` отсутствует), а при неподъёмном профиле — собирает, но не декодирует (`framesReceived` растёт, `framesDecoded` ноль).

Полезная деталь тоже дошла: `x264enc` и `ffmpeg` без явного `-pix_fmt` дают **High 4:4:4 Predictive, 10 бит**. Это не играет ни один браузер, и именно такими оказались наши собственные тестовые клипы.

## E. Архивного видео в браузере не было ни в одном уроке

Регистратор писал в ObjectStorage, страница умела таймлайн и `<video>`, а между ними было пусто: **никто не превращал выборки из тома во что-то, что браузер проиграет**. Для продукта это половина ценности архива, и работы там было на отдельный урок.

**Куда легло.** Написан отдельный урок, и не один. [Урок 20 «Интервал архива»](../М10B_ServerVMS/20-an-interval-of-the-archive.md) читает `[from, to)` из манифеста, а [урок 24 «Интервал архива в браузере»](../М10B_ServerVMS/24-an-interval-in-the-browser.md) закрывает ровно тот список, который мы принесли:

> Annex-B против AVCC; параметры кодека один раз в `avcC`, а не в каждом ключевом кадре; почему обычный MP4 не годится для интервала, который читается по мере ответа; `tfdt`, смещение от `moof` и флаги синхронизации — и проверка муксера разбором собственного вывода.
>
> — [указатель М10B](../М10B_ServerVMS/README.md), строка урока 24

Причина, по которой обычный MP4 не годится, названа так же, как мы её нашли: он держит индекс в конце, значит интервал нельзя отдавать по мере чтения.

## F. Тест переносимости предполагал чистый Go

`TestThePlatformCompilesForEveryOperatingSystemItClaims` собирал `./...`. У любого реального продукта медиапуть — cgo поверх GStreamer и драйверпака, он не кросс-компилируется ни под какой GOOS, и падение теста не говорит о платформе ничего.

**Куда легло.** Тест собирает явный список пакетов, и причина записана прямо над ним:

```22:26:vmsserver-go/w2cplatform/portability_test.go
// The packages that CLAIM portability — and not `./...`, which is every package there happens to be.
// A media path is cgo over GStreamer and a vendor's driver pack: it cross-compiles for nothing, and a
// red line here would say that and nothing about the platform. So portability is a property a package
// DECLARES by being on this list, and adding one is a decision somebody makes on purpose.
var portable = []string{"./w2cplatform/...", "./vms/...", "./cmd/..."}
```

Формулировка от этого только выиграла: переносимость — это свойство, которое пакет **заявляет**, а не то, что случайно получилось.

## G. Три мелочи, стоившие строки

**Правило свежести дошло до всех читателей heartbeat'а.** Платформа ввела правило и объяснила его отлично: читать все heartbeat'ы правильно для консоли и неверно для того, кто потом пойдёт с найденным разговаривать. Но подсистемы, написанные раньше, правила не получали — у нас два места обходили heartbeat'ы руками и подписывались на раздачу мёртвого воркера. Теперь единственная дверь — `HolderOf`, и сужают её тремя полями:

```53:58:vmsserver-go/w2cplatform/heartbeats.go
// HolderQuery narrows HolderOf past "is it held at all".
type HolderQuery struct {
	LostAfter float64 // 0 = 45s
	Phase     string  // "" = any phase
	Field     string  // "" = any: else the status entry must carry a non-empty value there
}
```

Через неё ходят все: регистратор, детекторы, обзор чужого архива, дозапись, консоль и проход освобождения диска. Руками heartbeat'ы не обходит никто.

**`libnice` — отдельный пакет.** Урок говорил «`GstPeer` нужен коробке с `gst-plugins-bad`», и этого было мало: `webrtcbin` действительно оттуда, но ICE берётся из libnice, который ставится отдельно. Без него `webrtcbin` регистрируется, создаётся — и **молча не отдаёт sink-pad**. Теперь это первое, что урок 13 говорит про установку, вместе с командами для macOS и Debian и с диагностикой: причина видна только при `GST_DEBUG=webrtcbin:4`, одной строкой `libnice elements are not available`.

**Цена непрозрачного индекса.** Переход `int64` → `Index` — правильное изменение, и оно стоило ровно того, чего должно: литералы `-1` и `0` перестали компилироваться. Соответствие теперь названо явно, и это то самое, что нужно знать при переносе:

> Соответствие такое: `-1` → **`NoCAS`** (писать безусловно, что бы там ни лежало), `0` → **`Absent`** (создать, только если ключа нет). Два имени вместо двух чисел — и `put(..., 0)`, набранное по привычке, больше не значит «перезаписать».
>
> — [`03-RegisterScheme.md`](../М10A_Platform/03-RegisterScheme.md)

## Что осталось открытым

Один пункт из записки не закрыт, и закрывать его, возможно, не надо. **Живого видео в Go-порте нет вовсе:** в `vmsserver-go/` лежат пять спек подсистем — `vms`, `rec`, `det`, `detjob`, `survey`, — и `live` среди них не значится.

В питоновском курсе живое видео есть целиком, это [урок 13 М10B](../М10B_ServerVMS/13-live-video.md), доведённый до картинки. То есть пробел не в знании, а в порте. Решать надо одно: догоняет ли Go-порт питоновский курс по составу подсистем или сознательно везёт только те, на которых показывает свои собственные уроки.
