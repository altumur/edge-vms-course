# Аудит настроек и отчёты по домену

> [!note] Записки поверх репозитория, а не его документация
> Это документ для обсуждения. Аудита правок в коде нет вовсе: здесь разобрано, что для него уже есть, чего не хватает, и что предлагается решить.
> **Источник истины — код.** Всё, что описано как будущий аудит, в репозитории не реализовано.
> Проект описывает себя сам: [`README.md`](../README.md) и указатели модулей.
> Состояние: коммит `4099cd5`, 23 сентября 2026.

[← все записки](README.md)


Документ для обсуждения. Продолжение [`where-camera-settings-go.md`](./where-camera-settings-go.md), который разбирал путь одной правки. Здесь другой вопрос: **оператор поменял настройку — как узнать об этом через полгода, и как построить по этому отчёт за квартал по всему домену.**

Требование, от которого документ считает: нужны **произвольные** отчёты в границах **одного домена** (по всем его кластерам), и графа **«кто» обязательна** — отчёт без имени оператора смысла не имеет.

Части 1–3 — то, что есть в коде. Части 4–6 — то, чего нет, и что придётся решить.

## Пять фактов, если читать некогда

1. **Аудита настроек сейчас нет вообще.** Variables хранят только текущее значение, в строке камеры нет ни времени правки, ни автора.
2. **Nomad его не даст.** Встроенный `audit`-блок — фича Enterprise, и даже она логирует запросы к Nomad, а не действия человека.
3. **Механизм записи уже есть и используется.** У консоли свой append-only журнал на resource, а `/events` умеет фильтровать по времени, объекту и типу — это готовый движок отчётов по кластеру.
4. **Личность оператора тоже уже доставлена в кластер.** Агент домена копирует ключи подписанта в Variables каждого кластера, проверка токена офлайновая. Консоль просто не читает `Authorization`.
5. **Аудит — первое невосстановимое хранилище в дизайне.** Всё остальное пересчитывается: видео на дисках, индекс сканированием, события из бакетов, конфигурация в raft. История правок не выводится ни из чего.

## Часть 1 — Почему сейчас нет ничего

### Variables хранят только текущее значение

`PUT` перезаписывает Variable целиком. `ModifyIndex` растёт, но это счётчик для CAS, а не версия, которую можно прочитать: **после записи предыдущего значения не существует нигде.**

### В строке камеры нет ни времени, ни автора

Сериализация пишет ровно `id`, `revision` и поля спеки — больше ничего:

```392:396:vmsserver/w2cplatform/spec.py
    def items(self, row: dict) -> dict:
        out = {"id": str(row["id"]), "revision": str(row.get("revision", 1))}
        for n, f in self.fields.items():
            out[n] = f.to_item(row.get(n, f.default_value()))
        return out
```

`revision` говорит, что правка была. Что поменялось, когда и кем — не говорит.

**Асимметрия, которую стоит назвать вслух:** решение контроллера объясняется и датируется, а правка человека — нет. В `placement/<id>` лежит `reason` («most free capacity (18) among 3 worker(s) reaching vlan:cctv-a; on srv-1, whose resource is live») и `at`. Машина о своих решениях отчитывается. Оператор — нет.

### «Кто» пока не существует как понятие в кластере

В `console.py` нет разбора `Authorization` — аутентификации нет вообще. Единственное место, где появляется имя человека, это маркер оператора, и там оно берётся из непроверенного заголовка с дефолтом:

```603:604:vmsserver/w2cplatform/console.py
            if path == "/marks":
                resp = con.mark(h._body(), h.headers.get("X-User", "operator"))
```

То есть имя заявляет сам клиент, а если не заявил — запись подписана словом `operator`. Для маркера наблюдения это приемлемо, для аудита — нет.

### Nomad это не решает

[`audit`-блок требует Enterprise](https://developer.hashicorp.com/nomad/docs/configuration/audit). На прямой вопрос в [issue #7759](https://github.com/hashicorp/nomad/issues/7759) HashiCorp ответили: не поддерживается в OSS, ставьте reverse proxy.

Но дело даже не в лицензии. Это **не тот уровень**: Nomad залогирует «токен консоли записал `vms/cameras/7`», а не «Иванов поменял маску на камере 7». Какой оператор сидел за консолью, Nomad не знает и знать не может — консоль ходит в Nomad своим workload-токеном, одним для всех операторов.

## Часть 2 — Что уже есть и подходит

### Журнал консоли

`EventLog` — append-only JSON-lines в бакетах на диске resource, один писатель на файл по построению. Консоль **уже держит свой экземпляр**:

```267:267:vmsserver/w2cplatform/console.py
        self.marks = EventLog(marks_root, "console", self.instance, 1) if marks_root else None   # the console's own log: one writer, so epoch 1
```

Epoch 1 навсегда — писатель один, ограждать не от кого. Сейчас туда пишутся только маркеры оператора, в `console/<instance>/e1/…`.

Запись — одна строка:

```128:133:vmsserver/w2cplatform/events.py
    def append(self, t: float, kind: str, **fields) -> str:
        p = self.path_for(t)
        os.makedirs(os.path.dirname(p), exist_ok=True)
        with open(p, "a") as f:
            f.write(json.dumps({"t": t, "kind": kind, **fields}) + "\n"); f.flush()
        return p
```

### Отчёты по кластеру — тоже есть

`GET /events?from&to&unit&kind&subsystem`, за ним `MergedIndex`, который опрашивает каждый живой resource кластера и сливает результаты. То есть покластерная отчётность с фильтрами по времени, камере и типу записи уже работает.

### Диф получается бесплатно

Чтобы записать «было → стало», не нужно ничего читать дополнительно: мутатор в `update()` и так держит старое значение в руках прежде, чем его перезаписать.

```582:592:vmsserver/w2cplatform/spec.py
    def update(self, uid, fields: dict) -> dict:
        self.spec.refuse(fields)
        def mutate(it):
            if not it or it.get("deleted") == "true":
                raise KeyError(uid)
            r = self.spec.row(it)
            for k, v in fields.items():
                r[k] = self.spec.fields[k].parse(v)
            r["revision"] += 1                       # the trigger from М9 Lesson 5, in the controller
            return self.spec.items(r)
        r = self.spec.row(self.write(self._row_key(uid), mutate))
```

`it` — это старое значение, `fields` — новое. Обе половины дифа в одной точке.

**Итого: запись аудита в кластере — это новый `kind` в существующем журнале, а не новая подсистема.**

## Часть 3 — Графа «кто»: дорога уже построена

Это выглядело самой дорогой частью, и оказалось, что механизм есть целиком.

```
подписант домена → токен {sub: "alice", exp, jti}
DomainPublisher  → domain/keys в Variables ДОМЕННОГО кластера
DomainAgent      → копирует domain/keys в Variables КАЖДОГО кластера
ClusterTrust     → консоль читает ключи из СВОЕГО кластера, никогда с домена
verify()         → offline, возвращает payload["sub"]
```

Два свойства, которые здесь важны, записаны в коде буквально:

```74:77:М12_DomainVMS/domainvms/domain/agent.py
class ClusterTrust:
    """What a cluster's console and gateway read from THEIR OWN cluster's
    Variables — never from the domain — to verify tokens and decide grants
    offline."""
```

```128:130:М12_DomainVMS/domainvms/domain/tokens.py
def verify(token: str, keys: KeySet, revoked: set[str] = frozenset(), now: float | None = None,
           skew: float = 60.0) -> dict:
    """Offline. Returns the payload (the subject is payload["sub"])."""
```

**Консоль получает достоверное имя оператора, не спрашивая домен.** Это не деталь удобства: правка настроек обязана работать при лежащем uplink, и офлайновая проверка — единственный способ совместить «знаем, кто правит» с «домен имеет право быть недоступным».

Чего не хватает: `console.py` не читает `Authorization`. Это **проводка существующих `ClusterTrust` и `verify` в путь запроса**, а не новая инфраструктура.

### Граница, за которой имени нет

При недоступном домене работает ограниченный отказ: выданные токены доживают до истечения, грант — до своего, новый никто не логинится. За этой границей остаётся break-glass — одна аварийная учётная запись.

Она уже пишет собственный аудит, и токен несёт клеймы `via="break-glass"` и `who=<человек>` именно для того, чтобы **след называл человека, хотя субъект — учётная запись**. Значит, запись аудита должна тащить не только `sub`, но и `via`/`who`, иначе аварийные правки схлопнутся в безымянный `break-glass`.

## Часть 4 — Отчёты по домену: четвёртый тип данных

### Почему федеративный запрос не подойдёт

Самый дешёвый вариант — не хранить на домене ничего, а в момент отчёта опросить кластеры. Для аудита он не работает, и причина в слове «произвольные»:

```146:149:vmsserver/w2cplatform/eventdatabase.py
    def query(self, t0: float, t1: float, cam: int | None = None, kind: str | None = None,
              subsystem: str | None = None, unit: str | None = None,
              current_epochs: dict[tuple[str, str], int] | None = None, limit: int = 1000,
              epoch_policy: dict[str, str] | None = None) -> dict:
```

Фиксированный набор фильтров и `limit: 1000`. А «сколько раз за квартал меняли retention и кто», «какие камеры правились чаще пяти раз», «все правки оператора по всем кластерам» — это `GROUP BY` и агрегация. Фан-аутом это делается единственным способом: вытащить все строки из всех кластеров в память и посчитать там. Хранилище на домене всё равно появляется, просто временное и на каждый запрос.

**Произвольная отчётность требует одного места, где лежат все строки.** Это свойство агрегирующих запросов, а не вопрос вкуса.

### Почему домен — правильный уровень, а не компромисс

Есть второй, независимый аргумент. Операторы, чьи действия аудируются, **сами живут на домене**: `identity/users/<id>` в Variables доменного кластера, подписант — единственный писатель. И определение домена в архитектуре — *«кластеры под одним каталогом, одним подписантом и одним набором операторов»*.

Область видимости хранилища аудита совпадает с областью видимости реестра личностей. Аудит действий оператора не может жить ниже уровня, на котором оператор существует как понятие: в кластере его нет.

Два несвязанных аргумента указали на одну границу. Проект относится к такому совпадению как к признаку, что граница настоящая — в `where-the-database-lives.md` это сказано про границу кластера: *«when two unrelated reasons pick the same line, the line is usually real»*.

### Правило «detail is local» здесь не выполняется

Правило выведено **из объёма**. Видео, индекс и события остаются внизу, потому что их порождает машина непрерывно. Аудит настроек порождает **человек**, и это меняет порядок величины полностью:

| Тип данных | Кто порождает | Объём для домена в 10 000 камер | Где живёт |
|---|---|---|---|
| Видео | машина, непрерывно | ~2.2 ТБ в день на сервер | диски, не уезжает никогда |
| Индекс архива | машина, постоянно | перестраивается сканированием | кэш на resource |
| События камер | машина, ~100 строк/с на 1000 камер | миллионы строк в день | бакеты на resource |
| **Аудит настроек** | **человек** | **~550 записей в день, ~50 МБ в год** | **нигде** |

Расчёт: 10 кластеров × 1000 камер, по 20 правок на камеру в год (щедро — это пусконаладка плюс несколько правок), запись ~250 байт JSON. Выходит 200 тысяч записей и 50 МБ в год, около 1.6 байта в секунду через uplink. Ошибиться в сто раз — скриптованная переконфигурация всего парка — это 5 ГБ в год и один файл SQLite.

**Аргумент, по которому три типа данных оставили внизу, для аудита не выполняется.** Значит, и вывод не переносится. Правило стоит сформулировать точнее: детали внизу, **пока детали — это поток**. Документ М12 сам предупреждал, что четвёртый тип данных придёт:

> **Detail is local; summary is domain.** Three data types, one rule — worth naming once rather than rediscovering per data type, **because the fourth one will arrive eventually.**
>
> — [`where-the-database-lives.md`](../М12_DomainVMS/where-the-database-lives.md)

### Почему эта база не возвращает проблему доступности

Это главный аргумент, и его стоит принести коллегам первым. Посмотрите, **почему** домен остался без базы: каждая база-кандидат была **несущей**. Она была авторитетом конфигурации, или держала эпоху-ограждение, или стояла на пути восстановления — от её доступности зависела работа. Оттуда вся страница про repmgr против Patroni и «ловушку Patroni».

Хранилище аудита — **не несущее**:

| Если хранилище аудита недоступно | |
|---|---|
| запись видео | идёт |
| правки настроек | идут |
| failover воркера | идёт |
| создание камер | идёт |
| **отчёты** | **не работают — и это всё** |

Если оно потеряно — восстанавливается из бэкапа, а кластеры досылают неподтверждённое. **База, отказ которой ничего не останавливает, не возвращает проблему, с которой боролись семь ревизий.**

### Движок

При 50 МБ в год и нескольких пользователях **SQLite достаточно**, и это сохраняет важное свойство дизайна: домен получает *хранилище, которое бэкапится как файл*, а не *СУБД, которую надо эксплуатировать*. Выбор между repmgr, pg_auto_failover и Patroni не возвращается, потому что делать этот файл высокодоступным не нужно.

## Часть 5 — Единственное по-настоящему новое свойство

**Аудит — первый тип данных в проекте, который невосстановим.**

| Данные | Как восстанавливаются |
|---|---|
| Видео | лежит на дисках, которые его записали |
| Индекс архива | перестраивается сканированием сегментов |
| База событий | прямо названа кэшем: удалить и перестроить из бакетов |
| Конфигурация | лежит в raft, реплицирована |
| **История правок** | **не выводится ни из чего** |

Текущее состояние камеры не содержит информации о том, кто и когда менял маску. Потерянная запись аудита потеряна навсегда. Отсюда четыре требования, которых у событий нет.

**Локальная запись должна быть долговечной.** Сейчас `append` делает `flush` без `fsync`, а порванная последняя строка при потере питания пропускается (счётчик `torn`). Для события камеры это принятая потеря, для записи аудита — дыра в журнале.

**Доставка на домен — store-and-forward с подтверждением.** Uplink имеет право лежать, поэтому запись сначала фиксируется в кластере, потом уезжает. At-least-once, дедупликация на приёме по хешу содержимого или по паре «кластер + номер записи».

**Локальная уборка только после подтверждения.** Прямое применение правила *«destructive operations stop at the grace period»*: локальную запись нельзя удалять, пока домен не подтвердил приём. Иначе долгий обрыв плюс обычная retention тихо съедят журнал. Диск заполнится — видимая и решаемая проблема; потерянный аудит — нет.

**Отчёт обязан заявлять свою полноту.** Отчёт, молча не включивший записи недоступного кластера, **хуже отсутствия отчёта** — он выглядит завершённым. М13 формулирует это как тезис модуля: `unreachable` не равно ни `up`, ни `down`. Значит, у каждого отчёта нужна строка вида «кластер room-b последний раз отчитывался 4 минуты назад, его записи после этого момента отсутствуют».

## Часть 6 — Ловушки

### Журнал правок — это путь утечки пароля камеры

В `ARCHITECTURE.md` это уже найдено «на аудите, гораздо позже»: RTSP-URL несёт `user:pass@` внутри себя, и **любой** путь кода, форматирующий этот URL, утекает учётные данные. М13 формулирует правило: *«Never log a secret — это ошибка форматирования, а не хранения»*.

Наивный аудит запишет `old`/`new` для поля `source` и положит пароль камеры в текстовый файл на диске, который зеркалируется на соседний сервер, а потом уезжает в централизованную базу с историей. **Признак «поле не логируется в открытом виде» должен быть свойством спеки** — по имени поля, а не по памяти автора.

### Retention журнала аудита

`retention_days` берёт дни из строки подсистемы, а дефолт — год:

```134:140:vmsserver/w2cplatform/resource.py
def retention_days(vars_, subsystem: str, unit: str, default: float = 365.0) -> float:
    """The unit's days if its subsystem set them, else the subsystem's, else a year."""
    for path in (f"{subsystem}/retention/{unit}", f"{subsystem}/retention"):
        items, _ = vars_.get(path)
        if items and "days" in items:
            return float(items["days"])
    return default
```

Значит, журнал консоли сейчас живёт по случайному правилу. Нужна явная строка `console/retention`.

### Давление на диск опаснее retention

`platform/space` при заполнении диска освобождает место, срезая бакеты: есть верхняя и нижняя метки и `min_days` как пол. Механизм не знает, что бакеты консоли — это аудит. **Журнал аудита не должен быть побочной жертвой видеозаписи**, и его надо из этого прохода исключить явно.

### Локальность и зеркалирование

Консоль — `system`-job, каждый экземпляр пишет на resource своего сервера. След размазан по серверам кластера; `MergedIndex` его сливает, но аудит с упавшего сервера недоступен, пока сервер не вернётся. Значит, зеркалирование (`platform/mirror`) для аудита важнее, чем для событий.

### Тяжёлые значения

Мегабайтную маску в строку журнала класть нельзя — только хеш «до» и «после». Стыкуется с частью 4 документа про настройку камеры.

### Персональные данные

Домен-wide база с полями `old`/`new` и именами операторов — это персональные данные со своими сроками хранения, правами доступа и экспортом. И это первое хранилище в проекте, для которого бэкап обязателен по существу, а не для удобства.

## Что предлагается решить

1. **Пишем ли `kind: "config_change"` в существующий журнал консоли** — предложение документа: да. Это одна запись в `update()` и ноль новых компонентов в кластере.
2. **Проводка личности в консоль.** `ClusterTrust` + `verify` существуют и работают офлайн; консоль не читает `Authorization`. Решить: делаем это в консоли или ставим перед ней прокси. Плюс не забыть `via`/`who` для break-glass.
3. **Редактирование секретных полей — признак в спеке, а не дисциплина.** Без этого пароли камер из `source` попадут в централизованную базу с историей. Предложение: блокирующее для всего остального.
4. **`fsync` для записей аудита** — принимаем ли потерю последней строки. Для событий принимали; здесь, вероятно, нет.
5. **Retention и исключение из освобождения диска.** Явная строка `console/retention` плюс исключение бакетов аудита из прохода `platform/space`, и правило «не удалять до подтверждения доменом».
6. **Транспорт на домен.** Кто инициирует — кластер пушит или доменный сервис забирает; как дедуплицируется; как выглядит подтверждение, на которое опирается локальная уборка.
7. **Движок на домене.** Предложение: SQLite, один файл, бэкап как файла. Проверить на реальном профиле правок — оценка 50 МБ в год построена на 20 правках на камеру в год.
8. **Строка полноты в каждом отчёте.** Формат: какие кластеры отвечали, до какого момента их записи присутствуют. Без этого отчёт врёт молча.
9. **Сроки хранения персональных данных и права доступа к отчётам** — отдельно от технической части, но решать надо до первой строки кода.
10. **Восьмая ревизия `where-the-database-lives.md`.** Документ ведётся в традиции «каждая ревизия остаётся видимой, потому что последовательность и есть урок», и семь ревизий выносили состояние из баз. Это первая, которая движется обратно, — её надо написать именно так, с аргументом про объём и про «не несущее». Иначе через полгода её откатят как противоречащую остальным семи.
