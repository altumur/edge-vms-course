## Справка: HTTP API Nomad Variables

Всё хранилище системы — это четыре метода. Больше их нет, и всё, что в документе дальше, собрано из них.

| Что нужно | Запрос |
|---|---|
| прочитать один ключ | `GET /v1/var/<путь>?namespace=default` |
| записать один ключ | `PUT /v1/var/<путь>?namespace=default&cas=<индекс>` |
| перечислить ключи по префиксу | `GET /v1/vars?prefix=<префикс>&namespace=default` |
| удалить один ключ | `DELETE /v1/var/<путь>?namespace=default&cas=<индекс>` |

Все четыре несут два заголовка, и дальше я их не повторяю:

```
X-Nomad-Token: <токен процесса>
Content-Type: application/json
```

Параметр `?namespace=default` тоже дальше опускаю: он есть в каждом запросе.

### Чтение одного ключа

```
GET /v1/var/vms/cameras/1
```

```json
HTTP/1.1 200 OK

{
  "Namespace": "default",
  "Path": "vms/cameras/1",
  "CreateIndex": 4409,
  "ModifyIndex": 4409,
  "CreateTime": 1757500000123456789,
  "ModifyTime": 1757500000123456789,
  "Items": {
    "id": "1",
    "revision": "1",
    "name": "Ворота",
    "enabled": "true"
  }
}
```

Что в этом ответе есть и что из него берут:

| Поле ответа | Что это | Зачем |
|---|---|---|
| `Items` | сами данные, плоский набор «ключ → строка» | это и есть значение |
| `ModifyIndex` | версия ключа | чтобы записать обратно с условием «версия та же» |
| `CreateIndex`, `CreateTime`, `ModifyTime` | когда создан и когда изменён | в этой системе не используются |

**Значения в `Items` всегда строки.** Число `365` лежит как `"365"`, признак «включена» — как `"true"`, список меток — как `"vlan:cctv,floor:2"`. Разбор обратно в числа и списки делает читатель.

**Ключа нет — это `404`**, а не пустой ответ:

```
GET /v1/var/vms/cameras/99
```

```
HTTP/1.1 404 Not Found
```

Читатель понимает это как «значения нет, версия 0». Отсюда правило, которое встретится в документе десяток раз: **`cas=0` означает «записать, только если ключа ещё нет»**.

### Запись одного ключа

Значение кладётся **целиком**. Обновить одно поле нельзя: прочитал всё, подменил поле, записал всё обратно.

```
PUT /v1/var/vms/cameras/1?cas=4409

{
  "Items": {
    "id": "1",
    "revision": "2",
    "name": "Ворота",
    "enabled": "false"
  }
}
```

```json
HTTP/1.1 200 OK

{
  "Namespace": "default",
  "Path": "vms/cameras/1",
  "CreateIndex": 4409,
  "ModifyIndex": 4471,
  "Items": {
    "id": "1",
    "revision": "2",
    "name": "Ворота",
    "enabled": "false"
  }
}
```

`ModifyIndex` в ответе — **новая** версия ключа. Её и надо предъявлять в следующей записи.

`cas` означает «запиши, только если версия сейчас ровно такая». Три случая:

| `cas` в запросе | Смысл | Когда так пишут |
|---|---|---|
| `cas=0` | записать, только если ключа не существует | создание камеры, взятие слота, захват ключа идемпотентности |
| `cas=4409` | записать, только если версия сейчас 4409 | любая правка существующей строки |
| параметра нет | записать безусловно, затерев чужое | heartbeat и снапшот — у них один писатель, спорить не с кем |

### Что приходит, когда записать не вышло

Три отказа, и они означают разное.

**Версия не совпала — кто-то записал раньше:**

```
PUT /v1/var/vms/cameras/1?cas=4409
```

```
HTTP/1.1 409 Conflict
```

В теле Nomad возвращает текущее состояние ключа, но читателю хватает самого кода: `409` значит «твоя версия устарела». Это не авария. Читатель перечитывает ключ, накладывает свою правку на свежее значение и пробует снова — до десяти раз подряд.

**Токену не разрешён этот путь:**

```
PUT /v1/var/vms/placement/1?cas=0
```

```
HTTP/1.1 403 Forbidden

Permission denied
```

Так консоль узнаёт, что размещение не её дело. Подробнее — в следующем разделе.

**Запись больше 64 КБ — до Nomad не доходит вовсе.**

`65536` байт на всю запись, считая имена ключей и значения вместе. Это константа планировщика, и изменить её нельзя. Процессы этой системы проверяют размер **до** отправки, поэтому оператор получает от консоли внятный отказ с числами, а не ошибку от сервера после круга по сети:

```json
HTTP/1.1 413 Payload Too Large

{
  "detail": "vms/cameras/7: 71204 bytes over this store's limit of 65536",
  "error": "vms/cameras/7: 71204 bytes over this store's limit of 65536"
}
```

### Перечисление по префиксу

```
GET /v1/vars?prefix=vms/cameras/
```

```json
HTTP/1.1 200 OK

[
  {
    "Namespace": "default",
    "Path": "vms/cameras/1",
    "CreateIndex": 4409,
    "ModifyIndex": 4409,
    "CreateTime": 1757500000123456789,
    "ModifyTime": 1757500000123456789
  },
  {
    "Namespace": "default",
    "Path": "vms/cameras/2",
    "CreateIndex": 4421,
    "ModifyIndex": 4421,
    "CreateTime": 1757500001200000000,
    "ModifyTime": 1757500001200000000
  },
  {
    "Namespace": "default",
    "Path": "vms/cameras/3",
    "CreateIndex": 4433,
    "ModifyIndex": 4433,
    "CreateTime": 1757500002000000000,
    "ModifyTime": 1757500002000000000
  }
]
```

**Обратите внимание, чего здесь нет: поля `Items`.** Листинг отдаёт только пути и версии, без значений. Чтобы получить данные трёх камер, нужны ещё три `GET`.

Отсюда растёт `N+1` — обход, где на один листинг приходится по чтению на каждый найденный ключ. На трёх камерах это четыре запроса, на шестистах — шестьсот один.

Зато `ModifyIndex` в листинге есть у каждого ключа, и это ровно тот ответ на вопрос «что изменилось с прошлого раза», который позволил бы дочитывать только изменившиеся строки. Сейчас читатели его выбрасывают — про это подробно в записках [«Куда попадает настройка камеры»](../where-camera-settings-go.md), часть 2.

#### Что вообще считается префиксом

Здесь кроется главное недоразумение, поэтому скажу прямо: **префикс — это просто начало строки пути, а не каталог.**

Никаких каталогов в хранилище нет. Есть плоский список ключей, где ключ — строка вида `vms/cameras/1`. Слэши в ней ничего не значат для Nomad: он берёт ваш префикс и оставляет те ключи, чей путь с него начинается. Ровно как сравнение строк.

Из этого следуют вещи, которые иначе выглядят загадочно:

| Запрос | Что вернёт | Почему |
|---|---|---|
| `prefix=vms/cameras/` | `vms/cameras/1`, `vms/cameras/2`, `vms/cameras/3` | все ключи, начинающиеся с этих 12 символов |
| `prefix=vms/cameras/1` | `vms/cameras/1`, а также `vms/cameras/17` | это по-прежнему сравнение строк, а не «камера номер один» |
| `prefix=vms/camera` | **всё то же самое** | слэш не обязателен, префикс может обрываться посреди слова |
| `prefix=vms/` | все камеры, размещения, назначения, слоты, эпохи, счётчик, ключи повторов | всё, что начинается с `vms/` |
| `prefix=vms` | то же самое | и заодно `vmsfoo/…`, если бы такой ключ завели |
| `prefix=` (пусто) | **весь кластер целиком** | пустая строка — начало любой строки |

Поэтому во всех запросах документа префикс кончается слэшем: `vms/cameras/`, `vms/slots/`, `objects/vms/heartbeats/`. Слэш здесь — не украшение, а **граница**. Без него `vms/camera` однажды поймает соседний ключ, которого в момент написания кода ещё не существовало.

Один процесс в системе пользуется пустым префиксом — консоль, когда собирает временную шкалу событий: ей нужны эпохи всех подсистем сразу, и она перечисляет весь кластер, а потом отбирает пути, содержащие `/epoch/`. Это единственное такое место, и оно осознанное исключение.

#### Раскладка ключей: что под каким префиксом лежит

Раз префикс — это начало строки, то **раскладка ключей и есть структура хранилища**. Вот вся раскладка нашего сценария:

| Префикс | Что под ним лежит | Кто его перечисляет |
|---|---|---|
| `vms/cameras/` | по строке на камеру | консоль (список для UI), контроллер (проход) |
| `vms/placement/` | по решению на камеру: где ей работать и почему | контроллер |
| `vms/workers/` | по назначению на воркера: что ему запускать | контроллер, консоль (`/where`) |
| `vms/slots/` | по строке на имя воркера: кто его держит и до когда | воркер при старте, контроллер |
| `vms/epoch/` | по токену ограждения на камеру | консоль (временная шкала) |
| `vms/idem/` | по ключу на каждый POST оператора | консоль (подчистка) |
| `vms/retention/` | по сроку хранения событий на камеру | ресурс сервера |
| `vms/holds/` | по занятому месту: какой из объявленных администратором томов взял процесс | воркер (в нашем сценарии пусто) |
| `vms/requests/` | по заявке оператора на разовую работу вне обычного прохода | воркер, консоль (уборка) |
| `objects/vms/heartbeats/` | по отчёту на воркера | контроллер, консоль |
| `objects/vms/snapshot/` | по шарду на воркера | домен |
| `objects/vms/blobs/` | по объекту на большое поле строки, по его хешу | консоль (уборка) |
| `objects/platform/resources/` | по отчёту на сервер | контроллер, консоль |

И три ключа, которые **не** префиксы, а одиночные строки: `vms/next_id` (счётчик), `vms/policy` (настройка администратора) и `vms/sweep` (что уборка больших полей пометила к удалению и когда). Перечислять там нечего, их читают по имени.

Видно правило, по которому всё это разложено: **`<подсистема>/<вид записи>/<кого она касается>`**. Подсистема первая, потому что подсистем несколько (`vms`, `rec`, `live`, `det`) и каждая живёт в своём куске хранилища. Вид записи второй, потому что именно он определяет писателя. Имя камеры или воркера — последним.

Имя воркера стоит последним не для красоты. Благодаря этому право выражается одной строкой `objects/vms/heartbeats/*`, а читатель перечисляет один префикс и ничего не отсеивает — под ним не лежит ничего постороннего. **Префикс, который нельзя назвать в политике, — это ошибка раскладки, а не нехватка возможностей у ACL.**

#### Один и тот же префикс — это сразу три вещи

Последнее, что делает раскладку важнее, чем кажется. Одна и та же строка живёт в трёх разных местах:

| Где | Как выглядит | Что означает |
|---|---|---|
| ключ в хранилище | `vms/cameras/1` | где лежат данные |
| право в политике | `path "vms/cameras/*"` | кому разрешено туда писать |
| каталог на диске сервера | `<архив>/vms/1/e1/…` | куда воркер кладёт события этой камеры |

Поэтому имя единицы проверяется на входе. У камер это неважно — им номер выдаёт счётчик, — но в подсистемах, где имя единицы придумывает оператор, слэш или `..` сломали бы все три вещи по-разному: ключ раздвоился бы, право совпало бы не с тем префиксом, а каталог уехал бы вверх по дереву. Такое имя консоль отклоняет с `400`, а не пытается починить.

#### Порядок в ответе — лексикографический

Ещё одна мелочь, о которую легко споткнуться. Nomad возвращает пути как строки, отсортированные посимвольно:

```
vms/cameras/1
vms/cameras/10
vms/cameras/100
vms/cameras/2
```

Числового порядка тут нет и быть не может: в ключе лежит текст. Читатели сортируют по номеру уже после того, как прочитали строки. Для нашего сценария из трёх камер это незаметно, а вот постраничный список в UI на такой сортировке ломается — страницы надо резать по путям **до** чтения значений.

### Объекты — это те же Variables

Heartbeat'ы воркеров и снапшот для домена в коде называются «объектами», но физически это те же самые Variables под префиксом `objects/`. Весь JSON объекта кладётся в **одно** поле `data`:

```
PUT /v1/var/objects/vms/heartbeats/w-1

Items.data:
{"worker": "w-1", "ts": 1757500010.3, "status": []}
```

Отсюда две вещи. Лимит 64 КБ действует и на них, потому что это обычная запись. И JSON здесь лежит строкой внутри JSON, то есть по проводу все кавычки внутри `data` экранированы обратными слешами.

**Как я показываю это дальше.** Экранирование ничего не объясняет и мешает читать, поэтому содержимое `data` я привожу отдельным блоком после строки `Items.data:` — как обычный JSON. Помните, что в настоящем запросе это одна строка с экранированными кавычками.

Там, где объект читают и от него нужны два-три поля, я пишу в ответе сразу содержимое `data`, без обёртки `{"Items": {"data": …}}` — например `GET /v1/var/objects/vms/heartbeats/w-1 → {"worker": "w-1", "server": "srv-1", …}`. Обёртка та же самая, просто она в таких строках только мешает.

## Откуда берётся `X-Nomad-Token`

Короткий ответ: **процесс его не хранит, а получает от планировщика при запуске**. Файла с токеном на диске нет, в образе его нет, в переменных окружения задания его тоже никто не прописывает.

### Как это устроено

В описании задания стоит одна строка:

```hcl
task "vmsworker" {
  driver = "podman"
  identity { env = true }    # NOMAD_TOKEN: собственная workload identity задачи
  ...
}
```

`identity { env = true }` означает: при запуске задачи Nomad сам кладёт ей в окружение переменную `NOMAD_TOKEN` со свежим токеном, выпущенным **на эту конкретную задачу**. Процесс читает переменную и подставляет её значение в заголовок каждого запроса.

Токен живёт ровно столько, сколько живёт задача. Перезапустили — токен новый. Украсть файл нельзя, потому что файла не существует.

### Что этот токен разрешает

Права описаны отдельным документом — ACL-политикой, привязанной к заданию по имени. Политика воркера целиком:

```hcl
namespace "default" {
  variables {
    path "vms/epoch/*"              { capabilities = ["write", "read", "list"] }
    path "vms/slots/*"              { capabilities = ["write", "read", "list"] }
    path "vms/holds/*"              { capabilities = ["write", "read", "list"] }
    path "objects/vms/heartbeats/*" { capabilities = ["write", "read", "list"] }
    path "objects/vms/*"            { capabilities = ["read", "list"] }
    path "vms/*"                    { capabilities = ["read", "list"] }
  }
}
```

Читается так: воркер **пишет** только свои эпохи, свой слот, занятое место и свой heartbeat. Всё остальное в подсистеме — **только чтение**. Занятое место (`vms/holds/*`) — это том архива, который процесс взял из объявленных администратором; устроено как слот, только имена кандидатов придумывает не воркер. В нашем сценарии томов не объявляли, и эти ключи пусты.

Привязывается политика к заданию одной командой при развёртывании:

```
nomad acl policy apply -namespace default -job vmsworker vmsworker vmsworker-policy.hcl
```

### Три токена этого сценария

У каждого процесса свой токен и своя политика. Именно они, а не договорённость в коде, делят ключи между процессами:

| Процесс | Пишет своим токеном | Только читает |
|---|---|---|
| **консоль** | `vms/cameras/*`, `vms/next_id`, `vms/retention/*`, `vms/idem/*`, `vms/requests/*`, `vms/policy`, `vms/sweep`, `objects/vms/blobs/*`, `platform/drain` | всё остальное |
| **контроллер** | `vms/workers/*`, `vms/placement/*`, `vms/slots/*`, `objects/vms/snapshot/*` | всё остальное |
| **воркер** | `vms/epoch/*`, `vms/slots/*`, `vms/holds/*`, `objects/vms/heartbeats/*` | `vms/*` и `objects/vms/*` |

Ключ `vms/slots/*` — единственный общий: воркер слот **захватывает**, контроллер может только пометить его отпущенным. Оба пишут в него с условием по версии, поэтому одновременная запись не портит строку.

#### Сначала — чем оператор пользуется обычно: `platform/drain`

Прежде чем разбирать слоты, стоит назвать ту строку, которой оператор действительно распоряжается, иначе следующий раздел повисает в воздухе. Когда машину собираются остановить — обновить, перезагрузить, увезти, — оператор говорит это **консолью**, и его слова ложатся в одну строку на весь кластер:

```
PUT /v1/var/platform/drain
{"Items": {"server": "srv-2", "at": "1757500050.0"}}
```

Строка одна и не начинается с `vms/`, потому что выводят **машину**, а на ней живут воркеры всех подсистем сразу. Выводить можно только один сервер за раз: попытка объявить второй, пока не закончился первый, отклоняется — обновление идёт по очереди, иначе кластер из трёх серверов разом теряет две трети.

Дальше никого не уведомляют. Контроллер и так читает эту строку на каждом проходе (вы видели её в разделе [4.1](04-placement.md)) и делает из неё два вывода: на воркеров выводимого сервера новые камеры не ставить, а те, что на них есть, увезти к живым — с причиной `server srv-2 draining`. Смысл в слове «заранее»: выключи сервер молча, и кластер узнает об этом только через 45 секунд, когда протухнет heartbeat, и все эти 45 секунд камеры лежат.

Строку слота вывод сервера при этом **не трогает вовсе**. Машина вернётся, процесс поднимется под тем же именем и заберёт своё назначение обратно.

#### А теперь — как контроллер помечает слот отпущенным

Это уже другой и куда более редкий случай: процесс не вернётся никогда. Сервер списали, аллокацию удалили навсегда — и имя `w-2` вместе с ними.

Вся власть контроллера над слотами сводится к одному: он может **пометить слот отпущенным**. Занять слот, переименовать или удалить его контроллер не может — только поднять в чужой строке один флаг. И делает он это **по слову оператора**, а не сам: оператор знает то, чего хранилище знать не может, — «этот процесс не вернётся, сервер списан».

Контроллер читает строку, поднимает в ней единственный флаг и записывает обратно с условием по версии:

```
GET /v1/var/vms/slots/w-2

→ 200
{
  "Items": {
    "holder": "srv-2:2044:1c7e9b",
    "until": "1757500050.0",
    "released": "false",
    "gen": "1"
  },
  "ModifyIndex": 5120
}

PUT /v1/var/vms/slots/w-2?cas=5120

{
  "Items": {
    "holder": "srv-2:2044:1c7e9b",   ← не трогает
    "until": "1757500050.0",         ← не трогает
    "released": "true",              ← единственное изменение
    "gen": "1"                       ← не трогает
  }
}
```

Три правила этой операции:

- **Меняется ровно один флаг.** Ни имя держателя, ни срок, ни поколение контроллер не переписывает: он не претендует на слот, а только сообщает о нём факт.
- **Повторный вызов ничего не делает.** Если `released` уже `true`, контроллер не пишет вовсе — записи без изменений в этой системе не делаются.
- **Сам по себе он так не решает.** Молчание воркера контроллер трактует как падение и слот не трогает, потому что упавший процесс вернётся под тем же именем и заберёт своё назначение. Разбор — в разделе [8.6](08-failures.md).

Дальше ничего особенного не происходит. На ближайшем проходе контроллер, как и каждые пять секунд, просматривает слоты, видит среди них отпущенный с непустым списком камер и раздаёт эти камеры живым воркерам — с причиной `slot w-2 released; …`. Отдельной процедуры «разобрать списанного воркера» в системе нет: пометка просто делает слот заметным для шага, который и так выполняется на каждом проходе.

Есть и второй случай, когда контроллер трогает камеры по молчанию, но слот при этом **не** переписывает: сервер признан потерянным по двум независимым молчаниям сразу. Камеры уезжают, строка слота остаётся как была. Подробности — в конце раздела [8.6](08-failures.md).

> И вот здесь разница с выводом сервера становится неудобной. Вывод оператор делает сам, маршрутом консоли. А списать слот консоль не может: `vms/slots/*` в её токене нет, и это не упущение — консоль, умеющая писать размещение, была бы вторым контроллером с браузером впереди. Писать слоты может только контроллер, но у процесса контроллера **нет HTTP-порта вообще**: он публикует результат каждого прохода в хранилище и никого не слушает. Так что попросить его не у кого — [TODO: уточнить, каким способом оператор списывает слот в эксплуатации].

### Почему это важно для сценария

Когда в [части 3](03-creating-a-camera.md) консоль отвечает `worker: null`, это не вежливость и не недоработка. Консоль **физически не может** записать размещение: её токен такого пути не знает, и Nomad ответит ей `403`.

Проверить это можно прямо изнутри работающей задачи — стендовый прогон кластера так и делает: пишет в свой префикс и в чужой, и ожидает `200` на первом и `403` на втором.

**Чтение при этом никому не ограничено**, и это сознательно. В хранилище лежит конфигурация и решения о размещении, а не секреты; пароли камер живут отдельно. Ограничивать чтение значило бы заплатить сложностью и ничего не получить.
