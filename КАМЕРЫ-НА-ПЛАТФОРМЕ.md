# Камеры на нашей платформе: где живут Variables — с серверами и без

Записка о развёртывании, которого курс не рассматривает. Мы — вендор: делаем камеры и софт для онпрем-инсталляций, и код в камере — та же платформа, что на серверах. Два сценария: **с серверами** — камеры и кластер серверов в одном домене — и крайний случай, **только камеры**: ни одного сервера, ни NAS, записи на SD-картах. В обоих каждая камера — отдельный кластер из одного и свою строку пишет всегда сама; сценарии отличаются тем, где размещён домен и кто пишет запись. Отдельно — камера сама по себе, вне домена, и переход из одного сценария в другой.

Ссылки вида `vmsworker/w2cplatform/contract.go` — на продукт (`vmssubsystem/vmsworker`), проверены против рабочей копии на 25 сентября 2026; если код с тех пор уехал, верьте коду. Записка начиналась как проектирование; что из неё сделано и где — в разделе «Что решено» и в ссылках на уроки по ходу текста: камеры как члены домена — М12, уроки 9–15; резервный архив и дозапись из него — в продукте и в курсе (М10B, уроки 16 и 26).

## Что решено (26 сентября 2026)

Записку сверили с курсом, и бо́льшая часть её механизмов оказалась **доменом М12 под другими именами**. Решили строить на М12: камеры — отдельные кластеры, серверы — ещё один кластер, домен объединяет их в одну систему. Это вторая часть М12, уроки 10–15 (все написаны, с кодом и тестами; решения — в [`М12_DomainVMS/module-design.md`](М12_DomainVMS/module-design.md), раздел «Вторая часть»). Урок 9 про правку выключенной камеры закрывает первую часть: он нужен любому домену, где кластеры часто недоступны, — например, филиалам на слабой связи.

| Решение | Что выбрано | Почему |
|---|---|---|
| Что такое камера | **Отдельный кластер — кластер из одного** | У набора камер нет того, что делает кластер кластером в М11: ни raft, ни оркестратора, ни юнита, который может переехать на другую камеру. Если все камеры считать одним кластером, им понадобится одно согласованное хранилище, то есть Raft между камерами, от которого записка отказывается. Если каждую камеру считать своим кластером, её хранилище согласовано бесплатно (флеш, один писатель), а правило М12 «ни один raft не охватывает кластеры» — это и есть «без консенсуса» из записки. |
| Что их объединяет | **Домен М12** | Вступление — М12 урок 6. Одна консоль, правящая любую камеру, — пересылка правки кластеру-владельцу из урока 3. Недоступная камера — неполный ответ урока 1. Доверие без связи — урок 7. «Домен может пропасть, и камеры не заметят» — тезис М12, и это ровно «главная выключена, запись идёт» из этой записки. |
| Кто пишет строку камеры | **Сама камера, всегда** | Первый вариант записки переносил строку на серверный кластер при привязке (режим adopted), и для этого требовались маршрутизирующее хранилище, поток изменений и запись камеры в хранилище серверов. От него отказались: если владелец не меняется, ничего из этого не нужно. |
| Номер камеры | **Локальный id остаётся целым, серийник — в `ref`** | Домен М12 уже отвечает по `ref`. Сделать серийник id значит пройтись по всем целым номерам камер ниже — в индексе событий `cam INTEGER` — без выгоды. |
| Строка устройства | **`vms/devices/<устройство>` — по устройству, не по id камеры** | В курсе «устройство» уже значит прибор за каналами (`device_of`, `group_by: device`): регистратор на 16 каналов — одно устройство и 16 строк камер. Если ключевать по камере, сведения о регистраторе повторятся 16 раз. |
| Главная камера | **Доменный кластер, размещённый на камере** | В М12 уже есть один назначенный кластер со всеми доменными службами, и при его падении переносить их некуда. На камере это доменный кластер из одного узла: перенос домена становится обычной операцией, а старый хост, который вернулся, — обычным событием. Для этого нужен **срок** (урок 15). |
| Правка выключенной камеры | **Сохраняется по полям и применяется, когда камера вернётся** (урок 9, написан) | `503` честен, но для члена домена, который часто недоступен — филиал на слабой связи или камера, — бесполезен. Правка лежит рядом с правами (`domain/pending/<кластер>`), агент камеры забирает её домой, консоль камеры применяет её от имени оператора и проверяет права в момент применения. По каждому полю: применено / уже на месте / конфликт. Результат сверяется по номеру версии, а не по часам. Владелец не меняется. |

**Что отпадает.** ACL на юнит: токен камеры действует только в её собственном кластере, и в чужие хранилища она ничего не пишет. Перенос строки на серверы, маршрутизирующее `Variables`, поток изменений для строк. Федеративное хранилище объектов как отдельная сущность: его роль играет чтение каталога и вида для чтения М12.

**Что осталось новым** — уроки 10–15: кластер из одного; домен на сотнях мелких членов (край заявленного предела М12, проверен замером); общие настройки без базы у домена; регистратор сервера, пишущий камеру из чужого кластера; тревоги со всех камер одним списком и их зеркала у соседей; доменный кластер из одного узла со сроком.

Разделы ниже переписаны под эти решения; где механизм уже есть в курсе или в продукте, стоит ссылка.

## Что это такое в трёх абзацах

В камере vmsworker работает **на месте**: видео берёт не через DriverPack, а прямо с сенсора, и переехать никуда не может. Оркестратор решает вопрос «на каком сервере работает юнит» — в камере на него ответило железо, поэтому оркестратор ей не нужен. Variables нужны для другого: хранить своё, получать общее сверху и отдавать своё состояние тем, кто спросит.

У платформы уже есть свойство, которое делает это дешёвым: **у каждого семейства ключей ровно один писатель** по ACL. Значит, копии можно сводить односторонним копированием — без консенсуса и без конфликтов. Консенсус понадобился бы только ключу с двумя писателями, а платформа их не допускает.

Ключи раскладываются на три кучки. **Своё** камеры — её строка, устройство, эпоха, события — живёт в ней самой и только в ней; строку пишет её собственная консоль, а правка из консоли домена пересылается камере. **Общее** — настройки по умолчанию, дерево папок, сценарии между камерами — публикует домен одним подписанным объектом, и агент приносит копию в каждую камеру; два хоста домена сразу разводит номер срока — так же, как эпоха разводит два экземпляра воркера. **Публикуемое** — heartbeat, срез snapshot, записи, события — читается у источника: домен читает каждую камеру, как любой свой кластер. Сценарии отличаются только тем, где размещён домен: на серверах или на одной из камер.

## Три кучки ключей

| | Примеры | Писатель | Где живёт |
|---|---|---|---|
| **своё** камеры | её строка `vms/cameras/<id>` (`ref` — серийник), `vms/devices/<устройство>`, `vms/epoch/<id>`, `vms/requests/*` к ней, события | строку — консоль камеры, в том числе по пересланной правке из консоли домена; остальное — сама камера | в камере, и только в ней |
| **общее** на систему | настройки по умолчанию (retention и пр.), дерево папок, сценарии между камерами | домен: подписывающий публикует документ, доменный кластер держит указатель | объект за указателем в доменном кластере; подписанная копия в каждой камере, на карте (М12 урок 12) |
| **доверие** | ключи подписывающего, список отзыва, права на эту камеру (`domain/keys`, `domain/grants`) | домен; в камеру пишет только её агент | в камере, под `domain/*` (М12 урок 4) |
| **публикуемое** | heartbeat, срез snapshot, `rec/<cam>/…`, корзины событий | своя камера | в своей камере (heartbeat и срез — в RAM); читается у источника |

Пользователи в камеру не попадают вовсе: они у подписывающего домена, а камера держит только его публичный ключ, отзыв и права, — так же, как любой кластер М12.

У камеры два имени. **`ref` — её серийный номер**: по нему её знает домен, он выдан на заводе и остаётся, если камеру вывели из домена и ввели снова. **Локальный id** в её кластере из одного — целый, как в любом кластере; `next_id` для него не нужен, строка одна.

**Строка камеры делится на две**, потому что у неё два писателя и внутри одной камеры. `vms/cameras/<id>` — то, что решает оператор: имя, папки, метки, включена ли, retention, live; пишет консоль. `vms/devices/<устройство>` — то, что знает только устройство: модель, прошивка, возможности сенсора, адрес; пишет воркер. Пока это одна строка, у неё два писателя; разделённые — каждая с одним писателем, как везде в платформе.

## Своё: камера — кластер из одного

Каждая камера работает так, как сегодня работает `vmsdev` на одной коробке, минус контроллер (М12 урок 10):

- **Строка.** Её создаёт собственная консоль камеры при первой загрузке, с `ref: <серийник>`.
- **Закреплённый юнит.** В спеке — `place: device`: юнит и есть устройство. Размещать его некому и незачем: слотов и аренд нет, назначение неизменно, ключей, которые писал бы размещающий, просто нет. Контроллер в камере не работает.
- **Эпоху** воркер берёт сам — он её единственный писатель — и пишет на флеш раз за загрузку. Она нужна не для переезда, а для путей архива `rec/<cam>/e<epoch>/` и для отсечения событий по эпохам: после перезагрузки, в том числе аварийной, номер должен вырасти.
- **Хранилище** — обычный `FileVariables`: интерфейс `Get/Put/List/Delete` с CAS (`w2cplatform/variables.go:80`), код воркера не меняется.
- **Флеш.** Heartbeat и срез snapshot живут в RAM и отдаются по запросу, а не пишутся на флеш; аренд у камеры нет. На флеш уходят только конфигурация, эпоха и то, что приносит агент, — единицы записей в сутки.
- **Дверь открывается после первой публикации.** Камера, ответившая раньше, ответила бы «камер нет» — а это *полный* ответ, которому домен обязан поверить.
- **Связь вверх** — агент домена, как в любом кластере: пишет `domain/*` и ничего больше.

### Хранилище камеры — без маршрутизации

Раз строку всегда пишет камера, её хранилище — обычное хранилище кластера из одного. Куда идёт каждый ключ:

| Ключ | Get | Put |
|---|---|---|
| своё, пишет воркер камеры | локальный файл | локальный файл |
| своя строка | локальный файл | локальный файл — консоль камеры, в том числе по пересланной правке |
| общее и доверие | локальная копия, принесённая агентом | только агент; правка общего — в консоль домена |
| heartbeat, срез snapshot | RAM | RAM |

## Камера одна и камера в домене

**Одна** — камера из коробки: её веб-страница и есть консоль, строку пишет она. Общего нет, точнее, оно тоже своё: политика и пользователи одной камеры.

**В домене** — камера вступила в домен (М12 урок 6). Строку по-прежнему пишет она сама; меняется только то, откуда приходят общее и доверие: их приносит агент домена. Домен читает её heartbeat и срез snapshot, как любого своего члена, и отвечает по её `ref`.

### Вступление в домен

1. **Заявка.** Оператор в консоли домена выбирает найденную камеру (WS-Discovery / mDNS) или вводит серийник. Камера должна доказать, что она физически у этого заказчика: одноразовый код с наклейки или QR, либо пароль администратора камеры; с ваучером производителя — без участия человека. Без доказательства в домен можно было бы ввести чужую камеру из той же сети.
2. **Выдача.** Подписывающий домена выдаёт камере LDevID на её серийник. Токенов на чужие ключи камера не получает: писать ей есть куда только в собственном кластере.
3. **Строка никуда не едет.** Домен добавляет камеру как ещё один кластер и начинает читать её публикации; её строка остаётся её строкой.
4. **Агент.** Агент камеры начинает приносить `domain/*`: ключи подписывающего, отзыв, права, общие настройки, сохранённые правки.

### Правка

На странице камеры оператор правит её строку сам, в любой момент, — это консоль её кластера. Из консоли домена правка пересылается в дверь камеры (М12 урок 3); если камера выключена, домен сохраняет правку по полям, и камера применяет её, когда вернётся (урок 9). Настройки самого устройства — адрес, NTP, параметры сенсора — лежат в `vms/devices/<устройство>` или в собственных ключах камеры и правятся на ней.

### Выход из домена

- **Плановый.** Домен забывает кластер и отзывает LDevID. Переносить нечего: строка у камеры и так своя, общие настройки остаются на карте последней копией.
- **Домена больше нет.** Камера продолжает работать по своей строке и последним общим настройкам; сброс к заводским — по желанию оператора, с паролем администратора.
- **Чужой домен.** Пока камера в домене A, заявка домена B отклоняется. Сначала выход или сброс.

## Сценарий с серверами

Серверы — ещё один кластер того же домена, обычная платформа с оркестратором; доменный кластер, как правило, на них. Камеры в кластер серверов не входят: каждая — свой кластер, и контроллер серверов о них не знает — их строк в его хранилище нет.

### Что остаётся оркестратору

Всё, что может переезжать:

- **Регистраторы.** Регистратор сервера пишет камеру из чужого кластера: находит её не в heartbeat'ах своего кластера, а в **книге источников** — `domain/sources/<кластер>`, которую домен публикует для кластера записи, а агент кластера приносит домой (М12 урок 13). Одну камеру пишет один кластер — это решение домена, хранится как размещение. Запись продолжается и при выключенном домене: регистратор разрешает `ref:` по копии книги в своём кластере.
- **Live-шлюзы и автоматизация** — без изменений.
- **Контроллер** серверов размещает регистраторы и остальное своё, как всегда; камер он не размещает и срезов snapshot за них не пишет — каждая камера публикует свой.

### Что ходит между камерой и доменом

| Направление | Что | Кто пишет | Как доходит |
|---|---|---|---|
| вниз | `domain/keys`, отзыв, `domain/grants`, общие настройки, `domain/pending` | домен | агент камеры забирает сам |
| вверх | ничего не пишется | — | домен читает heartbeat и срез snapshot камеры через её дверь |
| на месте | события, записи на SD | камера | читаются у источника, не копируются |

У каждого ключа один писатель, поэтому никакого слияния нет: агент применяет документ с большим `(term, rev)`, подпись которого сходится с ключами, которые у камеры уже есть.

### События не копируются, записи дозаписываются

> **В силе**, и уже есть в курсе: архив устройства и дозапись из края — М10B урок 16; запись на карте нашей камеры как резервный архив и копирование из неё сэмплами, а не перезаписью, — М10B урок 26. Новое одно: регистратор сервера находит камеру через каталог домена, а не в heartbeat'ах своего кластера — М12 урок 13.

Камера публикует heartbeat ресурса, и `MergedIndex` на серверах (`w2cplatform/eventdatabase.go:519`) находит её среди источников и забирает `GET <url>/events` прямо у неё. Недоступная камера честно видна как `unreachable`, а не как пустое окно.

Живую запись ведёт регистратор на сервере, как сейчас: тянет RTSP с камеры и пишет в свой том ObjectStorage. Карта камеры — **резервный архив** этой записи: том вида `backup`, который пишет регистратор в самой камере. Закрытие дыр основной записи из него — **дозапись**, урок 16 М10B. Это сделано в продукте (26 сентября) и проверено на коробке; ниже — как. В курсе то же самое — урок 26 М10B: резервный том с сервером и без, `register_admit` и `register_near_rank` вместо `Admit` и `NearRank`, `when: offline` с 20 секундами на старт, кольцом предзаписи на 30 секунд и минутой перекрытия; и пункт 4 списка «Дозапись» ниже — шаг 9 урока 16. Отличия курса: происхождение — в строке манифеста, а не в имени потока (у файлового архива манифест есть), и имена по времени съёмки — только у конвейера с кольцом.

**Резервный архив — не про камеры.** Вид тома назван `backup`, а не по карте, потому что механизм одинаков для карты в камере и для диска другого сервера: критичная камера пишется в два архива, и основная запись закрывает из резервной любую дыру — обрыв связи с площадкой или те секунды, что её регистратор переезжает на другой сервер. С `server` резервный том — диск или карта одной машины, без `server` — адрес, который может обслужить любой ящик.

- **Место.** Резервный том принимает только записи, сделанные для него, и запись резервного тома никуда с него не уходит (`vms.GuardBackups` поверх общего шва `SpecController.Admit`). Для обычного тома `home` — предпочтение; для резервного — фильтр в обе стороны: основная запись, переложенная на резервный том, оставила бы одну копию там, где их должно быть две.
- **Воркер камеры — рядом с резервной записью.** `near: {sub: rec, of: cam}` при двух записях камеры выбирает резервную (`vms.PreferBackups` поверх `SpecController.NearRank`). Тогда сервер основной записи может упасть, не унося с собой поток: воркер и резервная запись на другом сервере его не замечают, а основная потом дозаписывает свой переезд из резервной.
- **Покрытие.** Регистратор резервной записи публикует в heartbeat сводку `coverage` (начало, конец, число фрагментов) и дверь `url` — то, что урок 15 кладёт в heartbeat держателя.

**Когда пишет резервная — `when` в строке записи.** `always`: каждую секунду, и основная закрывает из неё любую дыру. `offline`: только пока основная запись **включена, но никто её не пишет** — её регистратор молчит (связь потеряна, сервер лёг), не сообщает запись идущей или она никуда не размещена.

- **Сбой, а не решение.** Основная выключена, событие детектора закончилось (`until` прошёл), основной нет вовсе — резервная ждёт. Иначе запись по событиям превратилась бы в постоянную. Только что созданной или ещё не размещённой основной — так начинается каждая запись по событию — даётся 20 секунд на запуск.
- **Предзапись.** Пропажу основной замечают с опозданием — сторожевой таймер регистратора и heartbeat, 15–25 секунд. Поэтому конвейер резервной записи работает всегда, **на удержании**: `recworkersink` держит в памяти последние 30 секунд (`prebuffer-ms`, от ключевого кадра) и ничего не пишет. Пропажу заметили — удержание снимается, кольцо ложится в архив первым, дальше без шва идёт живой поток. На коробке запись резервного архива началась за 28,5 секунды до снятия удержания.
- **Метки по времени съёмки.** Чтобы кольцо легло своим временем, `recworkersink` ставит кадру метку по часам конвейера — когда кадр снят, а не когда дошёл (`timestamps=capture`, по умолчанию; привязка по приходу осталась запасной).
- **Перекрытие.** Основная вернулась — резервная пишет ещё минуту: архивы перекрываются, и дозапись находит шов с обеих сторон.

**Дозапись.** Регистратор основной записи сверяет своё покрытие с покрытием резервной; дыры — со склейкой швов, бюджет диапазонов, окно по местному времени, пауза при нехватке места, перекрытие с живой записью проверяется дважды (урок 16). Четыре отличия от урока, все из-за того, что том ObjectStorage — не каталог с манифестом:

1. **Своё покрытие** — таймлайн тома по всем потокам записи, а не манифест.
2. **Диапазон копируется сэмплами** из тома в том с исходными метками (`/samples` у двери регистратора → запись в уже открытый писатель тома), а не записывается заново через конвейер — быстрее реального времени и без разбора потока.
3. **Отдельный поток** `<rec>/e<n>/backfill`: дозапись в поток живой записи перемешала бы старые сэмплы с новыми, и движок резал бы последовательность на каждом переключении. Происхождение живёт в имени потока — в томе нет ни манифеста, ни починки по пути.
4. **Только дыры внутри записанного.** Плановая дозапись берёт дыры между первой и последней видимой секундой основной записи — до своей первой секунды запись не шла (создана позже или детектором для одного события), и заливать это из резервной значило бы превратить запись по событиям в постоянную. Верхняя граница — конец видимого покрытия: хвост идущей записи ещё не виден, и это не дыра. Закрепить любой интервал оператор может кнопкой «Закрепить» — заявкой через `rec/requests`, вне бюджета и окна.

Камера при этом ничего не знает о серверах: она пишет и показывает свой архив, а инициатива у того, кому не хватает — то же правило, что записано в `vms/space.go:119`: эвакуация толкает, дозапись тянет.

**Чужие камеры.** Для камеры с картой, но без нашей платформы, архив устройства читается через DriverPack — а у привязки к DriverPack в продукте нет вызовов хранилища и воспроизведения (`ipint_storage_*`, `ipint_playback_*` в `ipint.h` только зарезервированы). Когда они появятся, карта чужой камеры станет ещё одним источником дозаписи; остальное не изменится.

### Когда серверов не видно

Камеру это почти не касается: её строка — её, общие настройки лежат у неё на карте, реконсайлер работает от сохранённого желаемого состояния. Она пишет на SD, события лежат у неё, правка на её странице работает как всегда. Не работает то, что живёт на серверах: консоль домена, если домен на них, и основная запись. Когда связь вернулась, регистраторы дозаписывают пропуск из её резервного архива (урок 16), а правки, которые домен сохранил для неё, агент приносит домой.

### Отказы

| Отказ | Что происходит |
|---|---|
| упал один сервер | оркестратор переносит регистраторы, которые там были; камеру это не касается — она не в кластере серверов |
| недоступны все серверы | камера живёт как жила и пишет на SD; её строку можно править на её странице; консоль домена, если домен на серверах, недоступна |
| недоступна камера | домен показывает её `unreachable`, а не «камеры нет»; правка из консоли домена сохраняется и применяется при её возвращении (урок 9) |

## Сценарий «только камеры»: домен на одной из камер

Серверов нет, и домен размещён на камере, назначенной оператором, — это доменный кластер из одного узла (М12 урок 15). Его по привычке можно звать главной камерой, но это не особый режим: это те же доменные службы — подписывающий, каталог, вид для чтения, консоль домена, — только хост у них камера.

### Кто пишет общее

Общее пишет домен и только он. Правка общего со страницы любой камеры уходит в консоль домена на хосте; два оператора одновременно разводятся CAS по ревизии документа.

### Что он публикует

Всё общее целиком, одним документом, подписанным ключом подписывающего (М12 урок 12):

```
{ term, rev, …настройки…, kid, sig }
```

Документ — объект; в доменном кластере на него смотрит указатель-Variable, записанный по CAS после объекта. Объём — даже для 500 камер десятки килобайт, больше потолка Variable в 64 КиБ, поэтому объект. Копия у соседа — это данные, которым камера верит по подписи и своему набору ключей, а не по тому, от кого их получила.

### Как документ доходит до всех

1. **Агент забирает.** Агент каждой камеры сравнивает `(term, rev)` указателя со своей копией и, если отстал, забирает документ; назад — никогда: копию новее он не отдаёт за старую.
2. **Проверка.** Подпись проверяется по ключам, которые у камеры уже есть под `domain/keys`; не сходится — документ отвергнут, остаётся прежний.
3. **Хранение.** Документ ложится на карту, а не в RAM: настройки должны пережить перезагрузку при выключенном домене. Значения по умолчанию применяются при чтении и в строки не пишутся.
4. **Доставка видна.** Консоль показывает «rev 7 на 47 из 50; не отвечают: …», пока не станет 50 из 50.

Каждая камера держит последний документ у себя — поэтому смерть хоста не теряет общего: оно уже лежит на всех.

## Только камеры: смена хоста домена, срок как эпоха

Срок полномочий — у доменного кластера (М12 урок 15). Он растёт при каждом переносе домена и старше ревизии: документ нового срока побеждает, даже если восстановлен из копии на несколько ревизий позади.

- **Плановая.** Оператор выбирает «перенести домен на камеру X». Хост замораживает запись состояния домена на секунды переноса, делает последнюю копию прямо на X, X восстанавливается из неё со сроком `term+1`, старый хост видит больший срок и уступает. Если X копию не взяла — перенос отменяется, хост остаётся хостом, ничего не потеряно.
- **Аварийная.** Хост молчит. Оператор нажимает ту же кнопку на X; X восстанавливает домен из ключа подписывающего и самой свежей проверенной копии состояния домена, которую держат другие камеры, и публикует его со сроком `term+1`.
- **Старый хост вернулся.** Он видит больший срок и понижает себя до обычного члена. То, что успел сделать только он и что не попало в копию, **не пропадает молча и не применяется само**: консоль показывает это списком «не вошло в срок N+1 — применить заново?».

Это единственное место, где возможны два хоста сразу, и оно разрешается как везде в платформе: побеждает больший номер, а проигравший узнаёт об этом при первом чтении.

**Автоматический выбор** («живая камера с наименьшим серийником») возможен, но без кворума разрыв сети даёт два хоста **с одним и тем же сроком**: их придётся разводить по серийнику и показывать проигравшие правки как конфликт. Для конфигурации, которая меняется раз в неделю, это терпимо; по умолчанию — вручную. Это открытый вопрос и в М12: выбирать доменный кластер автоматически или это решение человека сознательно.

**Если автоматика обязательна** — кворум: Raft на трёх–пяти назначенных камерах, остальные — читатели копии. По размеру влезает (`hashicorp/raft` — единицы мегабайт), но камеры теряют питание чаще серверов, а голосующая камера пишет журнал на флеш при каждой правке. Это для заказчиков, которым недопустимо «общее заморожено, пока оператор не перенесёт домен», — не первый шаг.

## Только камеры: картина системы без общего хранилища

Общего хранилища объектов нет, и отдельный федеративный `ObjectStore` не нужен: картину системы собирают каталог и вид для чтения домена, которые и так читают каждый кластер — здесь каждую камеру, через её дверь. Окупается старое решение платформы: **имя писателя — последний сегмент ключа** (`HeartbeatsDir`, `w2cplatform/contract.go:322`: `<sub>/heartbeats/<worker>`, а не `<sub>/<worker>/heartbeat`), поэтому по ключу видно, у какой камеры спросить.

**Предел.** Проход вида для чтения по сотням камер проверен замером (М12 урок 11): 300 камер, 30 выключены — по очереди 82 с, в 16 полос 5 с, с отсрочкой для молчащих 1,4 с. «Где камера» отвечается из памяти вида для чтения, а не обходом всех камер. Около тысячи — нужна иерархия или сервер.

**Тревоги со всех камер** — один список, по странице на камеру, с честно названными недоступными (М12 урок 14). **Зеркала:** соседи держат копии **закрытых корзин тревог**; тянет хранитель, план зеркал выбирает домен и хранит в `domain/mirrors`. Закрытые корзины не меняются, поэтому копирование не требует координации. Всё видео на соседях не уместится; тревоги — да.

**Записи** — только SD-карты, каждая камера — свой том. **Retention** не нужен как служба: каждая камера чистит только своё дерево — у каталога один писатель.

**Автоматизация между камерами.** Сценарий лежит в общем документе, и его выполняет камера, чьё событие его запускает. Действие на другой камере — это запрос в кластер той камеры, пересланный через домен, как правка (М12 урок 12). В отличие от правки, запрос **не сохраняется**, если цель выключена: у него есть срок, и он умирает на нём — «пресет 3 сейчас» через час никому не нужен. Узкое право `RequestsACL` (`w2cplatform/contract.go:119`: ровно `<sub>/requests/*`) для этого и задумано.

## Что появляется только без серверов и NAS

1. **Состав системы.** Кто в неё входит, решает **вступление в домен** (М12 урок 6). Находить кандидатов — WS-Discovery / mDNS в своём сегменте; между подсетями — список начальных адресов.
2. **Ключ подписывающего.** LDevID камер, взаимный TLS между ними и подпись общего документа — всё от ключа подписывающего домена. Его **нельзя держать только на хосте**: с его смертью домен нельзя будет ни восстановить, ни расширять. Резервная копия ключа лежит за пределами хоста — файлом восстановления у оператора или зашифрованной на нескольких камерах (М12, «Два куска состояния»). Проблемы прав на NAS нет вовсе: каждая камера пишет только себя.
3. **Время.** Слияние событий и таймлайнов требует синхронных часов. Источник NTP — хост домена или внешний, если есть.
4. **Предел масштаба.** Проверенный замером — сотни камер (М12 урок 11). Дальше — иерархия или сервер, и это уже другой вариант развёртывания.

| Отказ | Что работает | Что нет |
|---|---|---|
| хост домена выключен | запись, своя конфигурация каждой камеры и её правка на её странице, общие настройки (они на карте), события, сценарии | правка общего, консоль домена, новые входы: консоль камеры пишет «домен недоступен: хост, камера 3, молчит 12 мин» и предлагает «перенести домен сюда» |
| разрыв сети на две части | каждая часть живёт по последнему общему; своё правится в обеих | правка общего — только там, где хост |
| сгорел флеш хоста | всё | ничего не теряется, кроме того, что было только на хосте после его последней копии: последний общий документ есть у всех, копия состояния домена — у других камер |

## Переход между сценариями

Система растёт: сначала десять камер без серверов, потом заказчик ставит сервер. Или наоборот, сервер выводят. Переход — это перенос домена, и делается он той же механикой, что смена хоста; строки камер не трогает вовсе.

**Только камеры → с серверами.**
1. Серверы разворачиваются как новый кластер и вступают в домен (М12 урок 6).
2. Домен плановой передачей переносится с камеры на серверный кластер (М12 урок 15): срок `term+1`, последняя копия — прямо на новый хост. Ключ подписывающего переезжает вместе с доменом, поэтому перевыпускать сертификаты камер не нужно.
3. Агенты камер видят больший срок и дальше следуют за новым хостом. Ни одна камера ничего не переписывает.
4. Если оператор хочет, чтобы серверы писали камеры, домен назначает камерам кластер записи, и регистраторы находят их через книгу источников (урок 13).

**С серверами → только камеры.** Обратно: домен плановой передачей переносится на назначенную камеру, серверный кластер выходит из домена. Записи, которые жили только на серверах, остаются на серверах; это решение оператора, а не платформы.

## Чего не хватает в платформе

Исходный список из девяти пунктов строился на переносе строки камеры на серверы. На домене М12 он сжался; ниже — что осталось и где это сделано.

Что **отпало**:

- ~~ACL на юнит~~ — токен камеры действует только в её кластере из одного, в чужие хранилища она не пишет;
- ~~маршрутизирующее `Variables`~~ — строку всегда пишет камера;
- ~~поток изменений для строк~~ — строка не течёт вниз;
- ~~федеративный `ObjectStore`~~ — картину собирают каталог и вид для чтения М12;
- ~~Raft~~ — как и было: только если заказчику нужна автоматическая смена хоста домена.

Что **осталось** — вторая часть М12, всё написано:

1. **Правка выключенной камеры** — М12 урок 9, конец первой части: `domain/pending.py`, 9 тестов.
2. **Кластер из одного**: закреплённый юнит `place: device`, без оркестратора, эпоху камера берёт сама, доменный агент — её единственная связь вверх — урок 10: `domain/device.py`, 7 тестов. Новое по сути: флеш (heartbeat — в RAM) и порядок загрузки (дверь открывается после первой публикации, иначе домен получит ложный полный ответ «камеры нет»).
3. **Сотни мелких членов домена**: М12 заявлен до «низких сотен кластеров», это край; проверено замером — урок 11: `domain/scale.py`, 7 тестов. 300 камер, 30 выключены: проход по очереди — 82 с, в 16 дорожек — 5 с, с отсрочкой для молчащих — 1,4 с; «где камера» — из памяти вида для чтения, а не обходом всех членов.
4. **Общие настройки без базы**: политика по умолчанию, дерево папок, сценарии между камерами — опубликованы один раз, подписаны, донесены агентами — урок 12: `domain/shared.py`, 7 тестов. Значения по умолчанию разрешаются при чтении и в строки не пишутся.
5. **Поток из чужого кластера**: регистратор сервера пишет и дозаписывает камеру из её кластера, находя её через книгу источников, которую агент приносит в его кластер, — урок 13: `domain/crossing.py`, 6 тестов. Одну камеру пишет один кластер — решение домена.
6. **Тревоги со всех камер**: один список, по странице на камеру; зеркала закрытых корзин тревог у соседей, тянет хранитель; план зеркал выбирает домен — урок 14: `domain/alarms.py`, 6 тестов.
7. **Доменный кластер из одного узла**: только камеры; срок; подписанная копия состояния домена у других членов; перенос домена как обычная операция; старый хост уступает и показывает, что было только у него; плановая передача с живого хоста (заморозка, последняя копия на новую камеру, перенос) ничего не теряет, а если новая камера копию не взяла — отменяется, — урок 15: `domain/term.py`, 9 тестов.

Вступление с доказательством владения, сертификат на устройство и сроки жизни — уже есть: М12 уроки 6–7.

## Как это ложится на то, что уже есть

Почти ничего здесь не новое — старое под другими именами:

| Здесь | В платформе |
|---|---|
| камера | кластер из одного: воркер с закреплённым юнитом и без контроллера |
| вступление в домен | регистрация М12: доказательство владения, LDevID от подписывающего |
| строка камеры | строка кластера, у неё один писатель — консоль этого кластера |
| правка из консоли домена | пересылка владельцу (М12 урок 3); выключенному — сохранённая правка (урок 9) |
| запись на SD и закрытие дыр | резервный архив (`backup`, обобщение архива устройства М10B урока 15) и дозапись из него (урок 16) |
| главная камера | доменный кластер, размещённый на камере |
| номер срока | его эпоха |
| общий документ | публикация-и-указатель, как набор идентичностей у подписывающего; объект за указателем по CAS |
| «наибольший целый документ» | `(term, rev)` и подпись, никогда назад |
| события со всех камер | `MergedIndex` как есть |
| зеркала тревог | `platform/mirror` как есть |
| «одно семейство — один писатель» | ACL, как с урока 1 |

Новое по существу — немного, и всё про размер и характер членов домена, а не про механизмы. Камера — член домена, который часто выключен, мал, пишет на флеш и может сам оказаться хостом домена; отсюда порядок загрузки, RAM для heartbeat'а, правка, которая ждёт, замер на сотнях членов и перенос домена как обычная операция.
