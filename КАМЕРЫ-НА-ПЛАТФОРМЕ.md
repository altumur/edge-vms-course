# Камеры на нашей платформе: где живут Variables — с серверами и без

Записка о развёртывании, которого курс не рассматривает. Мы — вендор: делаем камеры и софт для онпрем-инсталляций, и код в камере — та же платформа, что на серверах. Два сценария: **с серверами** (камеры привязаны к кластеру, режим adopted) и крайний случай — **только камеры**, ни одного сервера, ни NAS, записи на SD-картах. Между ними — режимы камеры standalone и adopted и переход из одного сценария в другой.

Ссылки вида `vmsworker/w2cplatform/contract.go` — на продукт (`vmssubsystem/vmsworker`), проверены против рабочей копии на 25 сентября 2026; если код с тех пор уехал, верьте коду. Это проектирование, а не перенос: ни в курсе, ни в продукте этого ещё нет.

## Что решено (26 сентября 2026)

Записку сверили с курсом, и бо́льшая часть её механизмов оказалась **доменом М12 под другими именами**. Решили строить на М12: камеры — отдельные кластеры, серверы — ещё один кластер, домен объединяет их в одну систему. Это вторая часть М12, уроки 10–15 (все написаны, с кодом и тестами; решения — в [`М12_DomainVMS/module-design.md`](М12_DomainVMS/module-design.md), раздел *Part two*). Урок 9 про правку выключенной камеры закрывает первую часть: он нужен любому домену, где кластеры часто недоступны, — например, филиалам на слабой связи.

| Решение | Что выбрано | Почему |
|---|---|---|
| Что такое камера | **Отдельный кластер — кластер из одного** | У набора камер нет того, что делает кластер кластером в М11: ни raft, ни оркестратора, ни юнита, который может переехать на другую камеру. Если все камеры считать одним кластером, им понадобится одно согласованное хранилище, то есть Raft между камерами, от которого записка отказывается. Если каждую камеру считать своим кластером, её хранилище согласовано бесплатно (флеш, один писатель), а правило М12 «ни один raft не охватывает кластеры» — это и есть «без консенсуса» из записки. |
| Что их объединяет | **Домен М12** | Привязка — М12 урок 6. Одна консоль, правящая любую камеру, — пересылка правки кластеру-владельцу из урока 3. Недоступная камера — неполный ответ урока 1. Доверие без связи — урок 7. «Домен может пропасть, и камеры не заметят» — тезис М12, и это ровно «главная выключена, запись идёт» из этой записки. |
| Кто пишет строку камеры | **Сама камера, всегда** | Режим adopted переносил строку на серверный кластер, а для этого требовались маршрутизирующее хранилище, поток изменений и запись камеры в хранилище серверов. Если владелец не меняется, ничего из этого не нужно. |
| Номер камеры | **Локальный id остаётся целым, серийник — в `ref`** | Домен М12 уже отвечает по `ref`. Сделать серийник id значит пройтись по всем целым номерам камер ниже — в индексе событий `cam INTEGER` — без выгоды. |
| Строка устройства | **`vms/devices/<устройство>` — по устройству, не по id камеры** | В курсе «устройство» уже значит прибор за каналами (`device_of`, `group_by: device`): регистратор на 16 каналов — одно устройство и 16 строк камер. Если ключевать по камере, сведения о регистраторе повторятся 16 раз. |
| Главная камера | **Доменный кластер, размещённый на камере** | В М12 уже есть один назначенный кластер со всеми доменными службами, и при его падении переносить их некуда. На камере это доменный кластер из одного узла: перенос домена становится обычной операцией, а старый хост, который вернулся, — обычным событием. Для этого нужен **срок** (урок 15). |
| Правка выключенной камеры | **Сохраняется по полям и применяется, когда камера вернётся** (урок 9, написан) | `503` честен, но для члена домена, который часто недоступен — филиал на слабой связи или камера, — бесполезен. Правка лежит рядом с правами (`domain/pending/<кластер>`), агент камеры забирает её домой, консоль камеры применяет её от имени оператора и проверяет права в момент применения. По каждому полю: применено / уже на месте / конфликт. Результат сверяется по номеру версии, а не по часам. Владелец не меняется. |

**Что отпадает.** ACL на юнит: токен камеры действует только в её собственном кластере, и в чужие хранилища она ничего не пишет. Режим adopted, маршрутизирующее `Variables`, поток изменений для строк. Федеративное хранилище объектов как отдельная сущность: его роль играет чтение каталога и вида для чтения М12.

**Что осталось новым** — уроки 10–15: кластер из одного; домен на сотнях мелких членов (край заявленного предела М12, проверен замером); общие настройки без базы у домена; регистратор сервера, пишущий камеру из чужого кластера; тревоги со всех камер одним списком и их зеркала у соседей; доменный кластер из одного узла со сроком.

Разделы ниже — исходное проектирование. Там, где решение его отменило, в начале раздела стоит пометка.

## Что это такое в трёх абзацах

В камере vmsworker работает **на месте**: видео берёт не через DriverPack, а прямо с сенсора, и переехать никуда не может. Оркестратор решает вопрос «на каком сервере работает юнит» — в камере на него ответило железо, поэтому оркестратор ей не нужен. Variables нужны для другого: **конфигурация течёт сверху вниз, состояние — снизу вверх**.

У платформы уже есть свойство, которое делает это дешёвым: **у каждого семейства ключей ровно один писатель** по ACL. Значит, копии хранилища можно сводить односторонним копированием каждого ключа — без консенсуса и без конфликтов. Консенсус понадобился бы только ключу с двумя писателями, а платформа их не допускает.

Ключи раскладываются на три кучки, и сценарии отличаются только тем, где лежит каждая. **Своё** камеры всегда живёт в ней самой. **Общее** с серверами лежит в хранилище кластера, а без них — у одной назначенной «главной» камеры и в копиях на всех остальных; две главные сразу разводит номер срока — так же, как эпоха разводит два экземпляра воркера. **Публикуемое** (heartbeat'ы, записи, события) читается у источника: с серверами — через их общее хранилище и `MergedIndex`, без них — консолью прямо из камер. Кто пишет собственную строку камеры — она сама или кластер, — решает режим: standalone или adopted.

## Три кучки ключей

| | Примеры | Писатель | Где живёт |
|---|---|---|---|
| **своё** камеры | её строка `vms/cameras/<id>`, `vms/devices/<id>`, `vms/epoch/<id>`, `vms/requests/*` к ней, события | строку — консоль (standalone: консоль камеры; adopted: консоль кластера); остальное — сама камера | в камере; с серверами — ещё и в кластере |
| **общее** на систему | `vms/policy`, пользователи и роли, дерево папок, сценарии между камерами, retention по умолчанию, список привязанных камер | консоль кластера / главная камера | в кластере / у главной с CAS; копия на каждой камере |
| **публикуемое** | `vms/heartbeats/<серийник>`, `rec/<серийник>/…`, корзины событий | своя камера | в своей камере; читается у источника |

Id камеры — **её серийный номер**. `next_id` для камер не нужен: номер уже выдан на заводе, и он же остаётся после перепривязки к другому кластеру.

**Строка камеры делится на две**, потому что у неё два писателя. `vms/cameras/<id>` — то, что решает оператор: имя, папки, метки, включена ли, retention, live. `vms/devices/<id>` — то, что знает только устройство: модель, прошивка, возможности сенсора, адрес. Пока это одна строка, у неё два писателя, и любая схема копирования ломается; разделённые — каждая с одним писателем, как везде в платформе.

## Своё: камера — кластер из одного

Каждая камера работает так, как сегодня работает `vmsdev` на одной коробке, минус контроллер:

- **Закреплённый юнит.** В спеке — `place: device`: юнит и есть устройство, строка несёт `ref: <серийник>`. Размещать его некому и незачем: слотов и аренд нет, назначение неизменно. Контроллер в камере не работает; на серверах, если они есть, он такие юниты не размещает.
- **Эпоху** воркер берёт сам — он её единственный писатель — и пишет на флеш раз за запуск. Она нужна не для переезда, а для путей архива `rec/<cam>/e<epoch>/` и для отсечения событий по эпохам: после перезагрузки номер должен вырасти.
- **Хранилище** — обычный `FileVariables`: интерфейс `Get/Put/List/Delete` с CAS (`w2cplatform/variables.go:80`), код воркера не меняется.
- **Флеш.** Heartbeat живёт в RAM и отдаётся по запросу, а не пишется на флеш; аренд у камеры нет. На флеш уходят только конфигурация и эпоха — это единицы записей в сутки.

## Режимы камеры: standalone и adopted

> **Решено иначе.** Строку камеры всегда пишет сама камера; владелец при привязке не меняется. Режима adopted нет. Привязка ниже остаётся в силе — это М12 урок 6; правка из единой консоли — пересылка владельцу (М12 урок 3); правка выключенной камеры — М12 урок 9.

Режим отвечает на один вопрос: **кто пишет строку `vms/cameras/<id>`** — консоль самой камеры или консоль кластера. Всё остальное своё (`vms/devices/<id>`, эпоха, heartbeat, события) камера пишет всегда сама.

**Standalone** — камера из коробки: её веб-страница и есть консоль, и строку пишет она. Общего нет, точнее, оно тоже своё: политика и пользователи одной камеры.

**Adopted** — камера привязана к кластеру; кластер — это серверы или, в сценарии «только камеры», система с главной камерой. Строку пишет консоль кластера, камера держит её копию только для чтения.

Факт владения записан в самой камере ключом `platform/owner`: `{cluster, doors: [...], cert_fp, since}`. Он же переключает маршрутизацию хранилища камеры (см. «Маршрутизирующее хранилище»).

### Привязка

1. **Заявка.** Оператор в консоли кластера выбирает найденную камеру (WS-Discovery / mDNS) или вводит серийник. Камера должна доказать, что она физически у этого заказчика: одноразовый код с наклейки или QR, либо пароль администратора камеры. Без этого привязать можно было бы чужую камеру в той же сети.
2. **Выдача.** Кластер выдаёт камере сертификат и **токен на юнит**: `vms/epoch/<id>`, `vms/devices/<id>`, `vms/heartbeats/<id>`, и ничего о других камерах (см. «ACL на юнит»).
3. **Передача строки.** Камера отдаёт свою строку наверх: `Create` с `ref: <серийник>` и ключом идемпотентности = серийник, так что повтор после обрыва — та же одна запись. Если строка с таким `ref` в кластере уже есть (камеру привязывают повторно), консоль спрашивает: «взять с камеры» или «оставить системную».
4. **Переключение.** Камера пишет `platform/owner`; с этого момента её строка — копия, которую она получает из кластера.

### Правка на странице камеры в режиме adopted

> **Отпадает вместе с adopted.** Страница камеры правит её строку сама, как консоль своего кластера; правка из консоли домена пересылается камере или, если та выключена, сохраняется до её возвращения (М12 урок 9).

Строку пишет консоль кластера, поэтому правка на странице камеры **проксируется в дверь кластера с учётными данными оператора** — не токеном камеры: её токен строку писать не может, и не должен. Кластер недоступен — страница показывает строку только для чтения с объяснением. Писать локально нельзя: у строки появились бы два писателя.

Настройки самого устройства — адрес, NTP, параметры сенсора — лежат в `vms/devices/<id>` или в собственных ключах камеры и правятся на ней в любом режиме.

### Отвязка

- **Плановая.** Консоль кластера пишет последнюю версию строки в дверь камеры, отзывает сертификат и токен, строку в кластере удаляет (надгробие). Камера переключает `platform/owner` обратно на себя и продолжает работать с той же строкой.
- **Кластера больше нет.** Сброс на заводские настройки или локальная «принудительная отвязка» с паролем администратора: камера оставляет последнюю копию строки как свою.
- **Чужой кластер.** Пока `platform/owner` указывает на кластер A, заявка кластера B отклоняется. Сначала отвязка или сброс.

## Маршрутизирующее хранилище

> **Не нужно.** Маршрутизация требовалась, чтобы кластер серверов мог писать строку камеры. Раз строку всегда пишет камера, её хранилище — обычное хранилище кластера из одного.

Для кода камеры это одно `Variables`, которое по ACL и по `platform/owner` решает, куда идёт ключ. Таблица общая для всех сценариев:

| Ключ | Get | Put |
|---|---|---|
| своё, пишет камера | локальный файл | локальный файл (+ наверх, если есть кластер) |
| своя строка, standalone | локальный файл | локальный файл |
| своя строка, adopted | локальная копия | в дверь кластера с учётными данными оператора; недоступна — отказ с причиной |
| общее, с серверами | локальная копия | в дверь кластера |
| общее, только камеры, камера не главная | локальная копия | в дверь главной; недоступна — отказ с причиной |
| общее, только камеры, камера главная | локальный файл | локальный файл + публикация |

## Сценарий с серверами

Камеры привязаны к кластеру, на серверах работает обычная платформа с оркестратором. Для оркестратора камера — **воркер с закреплённым юнитом**: ёмкость 1, heartbeat называет сервером саму камеру, размещать её некуда и незачем.

### Что остаётся оркестратору

Всё, что может переезжать:

- **Регистраторы.** Правило `near: {sub: rec, of: cam}` ставит запись на сервер рядом с камерой: в её сегменте сети по меткам. Регистратор забирает поток с камеры по RTSP, как сегодня забирает его у vmsworker.
- **Live-шлюзы и автоматизация** — без изменений.
- **Контроллер** закреплённые юниты не размещает и слотов им не выдаёт, но по-прежнему проверяет строки, размещает зависящие от камеры юниты и пишет срез snapshot за камеру по её heartbeat'у.

### Копии Variables: вниз и вверх

> **Не нужно для строк.** Строка камеры не течёт вниз: её пишет камера. Вверх камера ничего не пишет — домен читает её кластер, как любой другой. Общие настройки, которые действительно нужны всем камерам, — М12 урок 12.

В камере — её локальное хранилище: полноправное для того, что пишет она, и копия только для чтения того, что пишет кластер.

| Направление | Ключи | Кто пишет | Как доходит |
|---|---|---|---|
| вниз | `vms/cameras/<id>`, `vms/retention/<id>`, `vms/policy`, общее | консоль кластера | камера забирает изменения с индекса |
| вверх | `vms/devices/<id>`, `vms/epoch/<id>` | камера | камера кладёт последнее значение своим токеном |
| вверх, объект | `vms/heartbeats/<id>`, `platform/resources/<id>/heartbeat` | камера | через ту же дверь в хранилище объектов кластера |
| на месте | события, записи на SD | камера | читаются у источника, не копируются |

У каждого ключа один писатель, поэтому достаточно правила «побеждает последнее значение по индексу источника».

- **Соединение открывает камера**, наружу, к двери любого сервера из списка, выданного при привязке. Так проще с VLAN, NAT и межсетевыми экранами, и один упавший сервер ничего не решает.
- **Вниз нужен поток изменений (changefeed):** `Changes(prefixes, since Index)` с долгим опросом (long-poll) по индексу — то, что у Nomad называется blocking queries. Сейчас в `Variables` только `Get/Put/List/Delete` (`w2cplatform/variables.go:80`), и следить за изменениями нечем.
- **Вверх** — обычные `Put` через дверь, и хранилище кластера само проверяет ACL токена камеры. Копится только последнее значение ключа: это состояние, а не журнал.

### События не копируются, записи дозаписываются

> **В силе**, и уже есть в курсе: архив устройства и дозапись из края — М10B урок 16. Новое одно: регистратор сервера находит камеру через каталог домена, а не в heartbeat'ах своего кластера — М12 урок 13.

Камера публикует heartbeat ресурса, и `MergedIndex` на серверах (`w2cplatform/eventdatabase.go:519`) находит её среди источников и забирает `GET <url>/events` прямо у неё. Недоступная камера честно видна как `unreachable`, а не как пустое окно.

Живую запись ведёт регистратор на сервере, как сейчас: тянет RTSP с камеры и пишет в свой том ObjectStorage. Камера сама пишет на SD — в свой том ObjectStorage, своим регистратором на закреплённом юните. Это **архив устройства** в смысле урока 15 М10B, а закрытие дыр после обрыва — **дозапись из края**, урок 16. Механизм один для наших и для чужих камер с картой; наша камера лишь лучше отдаёт свой архив.

- **Держатель публикует** в heartbeat `playback_url` (дверь архива камеры) и `coverage` — какие интервалы на карте есть (урок 15). Сессий у камеры мало, поэтому держатель считает их: одна живая, одна дозапись.
- **Регистратор на сервере сверяет покрытия**: дыры = покрытие устройства минус своё, со склейкой швов (`stitch`), не свежее `settle` и не старше того, что держит свой том. Бюджет диапазонов за проход, окно по местному времени площадки, пауза при нехватке места. Перекрытие с живой записью проверяется дважды: при планировании и перед записью (урок 16).
- **Дозаписанное — наше**: пишется текущей эпохой регистратора и живёт по сроку его тома. Оператор может «закрепить» интервал, который есть только на карте, заявкой через `rec/requests` — вне бюджета и окна.

Урок 16 написан для файлового архива с манифестом; в ObjectStorage четыре поправки:

1. **Своё покрытие** — таймлайн тома (`Reader.Timeline` по потокам записи), а не манифест.
2. **Как забрать диапазон.** `recworkersink` ставит метки по часам сервера в момент прихода кадра (`recworker-sink/recworkersink/render.go`, `mapTime`): позавчерашний час лёг бы как «сейчас». Нужен режим привязки к началу запрошенного диапазона — тогда годится любое воспроизведение, DriverPack для чужих камер и `/export` для наших. Для наших камер позже — копирование сэмплов из тома в том (`Reader.ReadSequence` → `Writer.PutMedia`) с исходными метками, быстрее реального времени.
3. **Отдельный поток.** Дозапись в поток живой записи `<rec>/e<n>` перемешала бы старые сэмплы с новыми, и движок резал бы последовательность на каждом переключении. Дозапись идёт в свой поток той же эпохи, и происхождение `source: edge` живёт в его имени — в ObjectStorage нет манифеста и нет починки по пути, которые в курсе запрещали нести происхождение в адресе.
4. **Нижняя граница.** Том освобождает место по объёму, а не по дням: «не старше срока» становится «не старше того, что свой том ещё держит», иначе дозапись и освобождение места гоняются по кругу.

Камера при этом ничего не знает о серверах: она пишет и показывает свой архив, а инициатива у того, кому не хватает — то же правило, что записано в `vms/space.go:119`: эвакуация толкает, дозапись тянет.

### Когда серверов не видно

Камера работает по последней полученной конфигурации: реконсайлер и так работает от сохранённого желаемого состояния. Пишет на SD, копит последнее значение своих ключей, события лежат у неё. Когда связь вернулась — отдаёт ключи наверх, а регистраторы дозаписывают пропуск с карты (урок 16).

### Отказы

| Отказ | Что происходит |
|---|---|
| упал один сервер | камера переходит к двери другого; оркестратор переносит регистраторы, которые там были |
| недоступны все серверы | камера живёт по последней конфигурации, пишет на SD; правка её строки невозможна (adopted) |
| недоступна камера | регистраторы и `MergedIndex` показывают её `unreachable`; строку можно править, камера получит её при подключении |

## Сценарий «только камеры»: общее у главной камеры и копии на всех

> **Решено: главная камера — это доменный кластер М12, размещённый на камере.** Файл общего — опубликованный подписанный объект, как в М12 (урок 12); смена главной — перенос домена (урок 15).

### Кто пишет

Одна камера, назначенная оператором, — **главная**. Она хранит общие ключи в своём локальном хранилище, где CAS настоящий (локальный диск), и она **единственная** их пишет. Правка общего из консоли на любой камере уходит в дверь главной; два оператора одновременно разводятся CAS по ревизии строки.

### Что она публикует

Всё общее целиком, одним файлом, неизменяемым:

```
{ term, primary, rev, keys: {…}, checksum, signature }
```

Объём — килобайты; даже для 500 камер — сотни КБ. Публиковать целиком проще и надёжнее, чем разницу. Файл подписан ключом системы (см. «Ключ системы»): копия у соседа — это данные, которым камера верит по подписи, а не по тому, от кого их получила.

### Как файл доходит до всех

1. **Толчок.** Главная фиксирует правку у себя и толкает новую ревизию в двери камер. Консоль показывает «доставлено на 47 из 50», пока не станет 50 из 50.
2. **Сверка (anti-entropy).** Раз в 30–60 секунд каждая камера спрашивает у двух-трёх случайных соседей их `(term, rev)` и забирает файл, если отстала. Так ревизия доходит и до камер, которых главная не видит напрямую.
3. **Выбор.** Камера применяет файл с наибольшей парой `(term, rev)`, у которого сходятся контрольная сумма и подпись. Недописанный или чужой — пропускает.

Каждая камера держит последний файл у себя — поэтому смерть главной не теряет общего: оно уже лежит на всех.

## Только камеры: смена главной, срок как эпоха

> **В силе, как М12 урок 15.** Срок — у доменного кластера: вернувшийся старый хост видит больший срок и понижает себя до обычного члена.

- **Плановая.** Оператор выбирает «сделать главной камеру X». Старая главная публикует последний файл с `term+1, primary: X` и перестаёт писать; X берёт общее из него и продолжает.
- **Аварийная.** Старая молчит. Оператор нажимает ту же кнопку на X; X берёт наибольший `(term, rev)` среди доступных камер и публикует его как `term+1, primary: X`.
- **Старая вернулась.** Она видит файл с большим сроком и понижает себя до читателя. Её правки, не успевшие разойтись, **не пропадают молча**: консоль показывает их как «не вошли в срок N+1 — применить заново?».

Это единственное место, где возможны две главные сразу, и оно разрешается как везде в платформе: побеждает больший номер, а проигравший узнаёт об этом при первом чтении.

**Автоматический выбор** («живая камера с наименьшим серийником») возможен, но без кворума разрыв сети даёт две главные **с одним и тем же сроком**: их придётся разводить по серийнику и показывать проигравшие правки как конфликт. Для конфигурации, которая меняется раз в неделю, это терпимо; по умолчанию — вручную.

**Если автоматика обязательна** — кворум: Raft на трёх–пяти назначенных камерах, остальные — читатели копии. По размеру влезает (`hashicorp/raft` — единицы мегабайт), но камеры теряют питание чаще серверов, а голосующая камера пишет журнал на флеш при каждой правке. Это для заказчиков, которым недопустимо «общее заморожено, пока оператор не назначит главную», — не первый шаг.

## Только камеры: хранилище объектов на каждой камере

> **Частично.** Отдельный федеративный `ObjectStore` не нужен: картину системы собирают каталог и вид для чтения М12, которые и так читают каждый кластер. Тревоги со всех камер одним списком и зеркала закрытых корзин тревог у соседей — М12 урок 14.

Общего хранилища объектов нет, и здесь окупается старое решение платформы: **имя писателя — последний сегмент ключа** (`HeartbeatsDir`, `w2cplatform/contract.go:322`: `<sub>/heartbeats/<worker>`, а не `<sub>/<worker>/heartbeat`). По ключу видно, у какой камеры спросить. Реализация `ObjectStore` (`w2cplatform/objects.go:17`) «по федерации»:

- `Get(key)` — в дверь камеры, чей серийник стоит в ключе;
- `List(prefix)` — опросить известные камеры и слить;
- `Put` — только своё, локально.

**Картина системы** собирается консолью этим опросом: 100 камер раз в 10 секунд — пустяк; около тысячи — нужна иерархия или сервер.

**События** уже устроены так, как нужно: `MergedIndex` (`w2cplatform/eventdatabase.go:519`) находит источники по heartbeat'ам ресурсов в `ObjectStore` и забирает `GET <url>/events` у каждого (`HTTPFetch`), сливая ответы и честно говоря `state`/`truncated`. В системе из одних камер каждая камера — ресурс; с федеративным `ObjectStore` под ним `MergedIndex` работает без изменений.

**Записи** — только SD-карты, каждая камера — свой том (`place_by: volume`, вид тома `edge`). Резерв — механизм зеркал, который в платформе уже есть (`platform/mirror {enabled, copies}`, `w2cplatform/resource.go:37`): соседи держат копии **закрытых корзин событий и тревожных фрагментов**. Всё видео на соседях не уместится; тревоги — да.

**Retention** не нужен как служба: каждая камера чистит только своё дерево — у каталога один писатель.

**Автоматизация между камерами.** Сценарий живёт в камере-источнике события и кладёт запрос в `requests/` целевой камеры, в её дверь. `RequestsACL` (`w2cplatform/contract.go:119`) уже задуман так узко: ровно `<sub>/requests/*` и ничего больше.

## Что появляется только без серверов и NAS

1. **Состав системы.** Кто в неё входит, решает **привязка**: общий ключ «привязанные камеры», ведёт главная. Находить кандидатов — WS-Discovery / mDNS в своём сегменте; между подсетями — список начальных адресов.
2. **Ключ системы.** Привязка — сертификат, подписанный ключом системы; между камерами — взаимный TLS; им же подписан файл общего. Этот ключ **нельзя держать только на главной**: с её смертью систему нельзя будет расширять. При установке оператор получает файл восстановления, либо ключ лежит зашифрованным на нескольких камерах. Проблемы прав на NAS нет вовсе: каждая камера пишет только себя.
3. **Время.** Слияние событий и таймлайнов требует синхронных часов. Источник NTP — главная или внешний, если есть.
4. **Предел масштаба.** Опрос всех камер консолью и сверка по соседям хороши до сотен камер. Дальше — иерархия (главная по сегменту) или сервер, и это уже другой вариант развёртывания.

## Только камеры: отказы

| Отказ | Что работает | Что нет |
|---|---|---|
| главная выключена | запись, своя конфигурация каждой камеры, события, сценарии | правка общего: консоль пишет «общее только для чтения: главная камера 3 молчит 12 мин» и предлагает «сделать главной эту» |
| разрыв сети на две части | каждая часть живёт по последнему общему; своё правится в обеих | правка общего — только там, где главная |
| сгорел флеш главной | всё | ничего не теряется, кроме правок, не успевших разойтись; последний файл есть у всех |
| сгорела SD-карта камеры | остальные камеры | её видео; тревоги — если зеркала включены |

## Переход между сценариями

Система растёт: сначала десять камер без серверов, потом заказчик ставит сервер. Или наоборот, сервер выводят. Переход — это смена писателя общего и строк, и он делается той же механикой, что смена главной.

**Только камеры → с серверами.**
1. Сервер разворачивается как новый кластер. Главная камера публикует последний файл общего со сроком `term+1` и `primary: cluster:<id>`.
2. Консоль кластера забирает этот файл и создаёт общие ключи у себя: `Create` с ключами идемпотентности, так что повтор безопасен.
3. Камеры, увидев `primary: cluster:<id>`, переключают маршрутизацию общего на дверь кластера.
4. Каждая камера привязывается к кластеру (оптом, одной кнопкой): строка уходит наверх, как в разделе «Привязка». Ключ системы, которым подписаны сертификаты камер, переносится в кластер — перевыпускать сертификаты не нужно.

**С серверами → только камеры.** Обратно: кластер публикует файл общего с `primary: <серийник>` назначенной камеры и отвязывает камеры плановой отвязкой — либо оставляет их adopted к системе с главной камерой. Записи, которые жили только на серверах, остаются на серверах; это решение оператора, а не платформы.

## Чего не хватает в платформе

> **Переписано по решениям 26 сентября.** Исходный список из девяти пунктов строился на режиме adopted. На домене М12 он сжался; ниже — что осталось и где это сделано.

Что **отпало**:

- ~~ACL на юнит~~ — токен камеры действует только в её кластере из одного, в чужие хранилища она не пишет;
- ~~маршрутизирующее `Variables`~~ — строку всегда пишет камера;
- ~~поток изменений для строк~~ — строка не течёт вниз;
- ~~федеративный `ObjectStore`~~ — картину собирают каталог и вид для чтения М12;
- ~~Raft~~ — как и было: только если заказчику нужна автоматическая смена главной.

Что **осталось** — вторая часть М12, всё написано:

1. **Правка выключенной камеры** — М12 урок 9, конец первой части: `domain/pending.py`, 9 тестов.
2. **Кластер из одного**: закреплённый юнит `place: device`, без оркестратора, эпоху камера берёт сама, доменный агент — её единственная связь вверх — урок 10: `domain/device.py`, 7 тестов. Новое по сути: флеш (heartbeat — в RAM) и порядок загрузки (дверь открывается после первой публикации, иначе домен получит ложный полный ответ «камеры нет»).
3. **Сотни мелких членов домена**: М12 заявлен до «низких сотен кластеров», это край; проверено замером — урок 11: `domain/scale.py`, 7 тестов. 300 камер, 30 выключены: проход по очереди — 82 с, в 16 дорожек — 5 с, с отсрочкой для молчащих — 1,4 с; «где камера» — из памяти вида для чтения, а не обходом всех членов.
4. **Общие настройки без базы**: политика по умолчанию, дерево папок, сценарии между камерами — опубликованы один раз, подписаны, донесены агентами — урок 12: `domain/shared.py`, 7 тестов. Значения по умолчанию разрешаются при чтении и в строки не пишутся.
5. **Поток из чужого кластера**: регистратор сервера пишет и дозаписывает камеру из её кластера, находя её через книгу источников, которую агент приносит в её кластер, — урок 13: `domain/crossing.py`, 6 тестов. Одну камеру пишет один кластер — решение домена.
6. **Тревоги со всех камер**: один список, по странице на камеру; зеркала закрытых корзин тревог у соседей, тянет хранитель; план зеркал выбирает домен — урок 14: `domain/alarms.py`, 6 тестов.
7. **Доменный кластер из одного узла**: только камеры; срок; подписанная копия состояния домена у других членов; перенос домена как обычная операция; старый хост уступает и показывает, что было только у него; плановая передача с живого хоста (заморозка, последняя копия на новую камеру, перенос) ничего не теряет, а если новая камера копию не взяла — отменяется, — урок 15: `domain/term.py`, 9 тестов.

Привязка с доказательством владения, сертификат и токен на устройство — уже есть: М12 уроки 6–7.

## Как это ложится на то, что уже есть

Почти ничего здесь не новое — старое под другими именами:

| Здесь | В платформе |
|---|---|
| камера | воркер с закреплённым юнитом |
| привязка | заявка + токен с ACL, как у любого писателя; передача строки — `Create` с ключом идемпотентности |
| копия строки в камере | желаемое состояние, от которого работает реконсайлер (М9, урок 6) |
| запись на SD и закрытие дыр | архив устройства (М10B урок 15) и дозапись из края (М10B урок 16) |
| главная камера | воркер с закреплённым юнитом `shared` |
| номер срока | его эпоха |
| файл общего | срез snapshot (`SnapshotShards`, `w2cplatform/placement.go:1292`: один объект на писателя) |
| «наибольший целый файл» | то же чтение, что слияние срезов у М12 |
| события со всех камер | `MergedIndex` как есть |
| зеркала тревог | `platform/mirror` как есть |
| «одно семейство — один писатель» | ACL, как с урока 1 |

Новое по существу — немного. С серверами: **писатель строки камеры меняется** при привязке и отвязке, и копирование идёт **через поток изменений**, а не через общее хранилище. Без серверов: писатель общего назначается **человеком**, а не арендой; копия общего живёт **на каждом** узле; хранилище объектов **адресуется по имени писателя**, а не лежит в одном месте.
