# Урок 5 — Раскладка ключей

**Модуль:** М10A — Платформа (ServerVMS, часть первая)
**Вы напишете:** `Subsystem` — двадцать строк, которые собирают все ключи системы, — и `Assignment`, строку назначения, в которой список единиц работы лежит одной строкой через запятую. И увидите раскладку целиком, до того как появится первая подсистема.
**Время:** ~60 минут.

## Зачем этот урок

В уроках 2–4 ключи набирались руками: `"vms/cameras/7"`, `"vms/epoch/7"`, `"vms/w-1/heartbeat"`. Это работало, потому что их было три и все они лежали в тестах. В системе их будет семь семейств на подсистему, четыре подсистемы, и ещё префикс платформы — и набранные руками они разойдутся: кто-то напишет `vms/worker/w-1` вместо `vms/workers/w-1`, тест пройдёт (он же пишет и читает одно и то же), а контроллер не найдёт назначения.

Поэтому ключ никогда не набирается. Есть один объект, который умеет их составлять, и все обращения к хранилищам идут через него. Двадцать строк, ни одного алгоритма — и всё же это, пожалуй, самый плотный файл курса по отношению «решений на строку», потому что каждый метод здесь — это утверждение о том, что в системе есть, кто это пишет и как оно называется.

Второе, что делает этот урок: выписывает раскладку **целиком**, на одну страницу. Когда все ключи видны разом, становится видно и то, чего в них нет, — а это в проектировании обычно важнее.

> **Что можно проверить без железа.** Всё. Тест урока 1 проверяет четыре ключа и оба ACL прямой подстановкой; тест `test_controller_and_worker_bases_speak_only_the_contract` гоняет через `Assignment` полный цикл — назначить, прочитать, переназначить, увидеть новую ревизию.

## Что нужно знать заранее

- **Урок 2 и 3** — хранилище конфигурации и то, что список разрешённых префиксов есть утверждение об архитектуре.
- **Урок 4** — хранилище объектов и ключ heartbeat'а.

## Чему вы научитесь

1. Собирать ключи в одном месте и объяснять, почему это не «красивая обёртка».
2. Читать раскладку целиком и говорить, кто пишет каждое семейство.
3. Хранить список в хранилище, у которого только строки, — и понимать, чем за это платят.
4. Объяснять, зачем у назначения есть своя ревизия, если у ключа уже есть `ModifyIndex`.
5. Отличать грубый ACL базы от точного ACL спецификации и говорить, почему они разные.

## Шаг 1 — Одно поле, шесть ключей

```python
class Subsystem:
    name: str

    def config(self, *parts: str) -> str:
        return "/".join((self.name,) + parts)

    def assignment(self, worker: str) -> str:
        return f"{self.name}/workers/{worker}"

    def heartbeat_key(self, worker: str) -> str:
        return f"{self.name}/{worker}/heartbeat"

    def epoch_key(self, unit: str) -> str:
        return f"{self.name}/epoch/{unit}"

    def slot_key(self, worker: str) -> str:
        return f"{self.name}/slots/{worker}"
```

Поле одно — имя. `Subsystem("vms")`, `Subsystem("rec")`, `Subsystem("thing")` в тестах. Всё остальное выводится из него.

`config(*parts)` — общий случай: `sub.config("cameras", "7")` даёт `vms/cameras/7`, `sub.config("next_id")` — `vms/next_id`, `sub.config("policy")` — `vms/policy`. Через него ходит всё, что не получило отдельного метода, и этим пользуется `SpecController`, который не знает заранее, как подсистема назвала свои строки (`cameras`, `recordings`, `streams`, `units` — четыре разных слова в четырёх YAML).

Четыре остальных метода — это четыре семейства, о которых платформа знает **по имени**, потому что сама их пишет и читает: назначение, heartbeat, эпоха, слот. Подсистема на них не влияет; она влияет только на первое слово.

Обратите внимание на `heartbeat_key`: `vms/w-1/heartbeat`, а не `vms/heartbeat/w-1`. Порядок выбран так, чтобы объекты одного воркера лежали в одном каталоге — у него их будет больше одного, когда шлюз начнёт публиковать свою статистику. `list("vms/")` при этом работает одинаково в обоих вариантах.

## Шаг 2 — Два ACL на базе

```python
    def acl_controller(self) -> list[str]:
        return [f"{self.name}/*"]

    def acl_worker(self) -> list[str]:
        return [f"{self.name}/epoch/*", f"{self.name}/slots/*"]
```

Те самые списки из урока 3, но выведенные из имени. И здесь есть неточность, которую надо назвать сразу, потому что иначе она обнаружится в уроке 10 как противоречие.

`acl_controller()` отдаёт **весь префикс подсистемы** — `vms/*`. Это грубо: контроллер получает право писать и строки камер тоже, хотя писать их будет консоль. Почему так: на этом уровне подсистемы-как-данных ещё нет, и платформа не знает, как называются строки оператора (`cameras`? `recordings`?) — а значит, не может вырезать их из прав. Точный список появится в уроке 10, когда появится YAML: `SubsystemSpec.acl_controller()` вернёт `["vms/workers/*", "vms/placement/*", "vms/slots/*"]`, и в нём строк оператора не будет.

Базовая версия остаётся для подсистем, у которых нет спецификации, — то есть для тестов платформы и для гипотетического случая, когда кто-то захочет использовать `Controller` напрямую. Полезное правило: **если у подсистемы есть YAML, права берутся из неё**, а `Subsystem.acl_controller()` — это то, что было до неё.

`acl_worker()` точен с самого начала: воркер пишет свои эпохи и свой слот, и это не зависит ни от какой спецификации. `test_the_platform_knows_nothing_about_video` проверяет обе строки подстановкой — `sub.acl_worker() == ["thing/epoch/*", "thing/slots/*"]`.

**Третьего списка здесь нет вовсе**, и это не потому, что консоль пишется только в уроке 17: `acl_console()` в `Subsystem` нечего было бы вернуть. Права воркера и контроллера собираются из слов платформы — `epoch`, `slots`, `workers`, `placement`, — одинаковых во всех подсистемах. Консоль пишет строки оператора, а как они называются, знает только подсистема: `cameras` у `vms`, `recordings` у `rec`, `units` у `det`. Вывести `vms/cameras/*` из имени `vms` нельзя, а зашить слово `cameras` в платформу не даст тест чистоты урока 1. Поэтому права консоли появляются вместе со спецификацией — `SubsystemSpec.acl_console()` в уроке 10, — и грубость `acl_controller()` выше есть та же дыра с другой стороны: `vms/*` временно покрывает и то, что принадлежит консоли.

## Шаг 3 — Раскладка целиком

Вот всё, что система когда-либо положит в два хранилища. Четыре подсистемы дают четыре копии первого блока; второй блок — общий.

**Конфигурация** (`variables.py`):

| Ключ | Кто пишет | Что это |
|---|---|---|
| `<sub>/<строки>/<id>` | консоль | строка оператора: камера, запись, поток, детектор |
| `<sub>/next_id` | консоль | счётчик идентификаторов, растёт по CAS |
| `<sub>/idem/<ключ>` | консоль | заявка на идемпотентный POST и сохранённый ответ |
| `<sub>/policy` | консоль | ручка администратора: `servers: shared \| distinct` |
| `<sub>/retention/<id>` | консоль | производная строка: сколько дней хранить бакеты этой единицы |
| `<sub>/workers/<воркер>` | контроллер | назначение: какие единицы несёт этот воркер |
| `<sub>/placement/<id>` | контроллер | решение о размещении, с причиной |
| `<sub>/slots/<воркер>` | воркер (захват), контроллер (освобождение) | имя, взятое по CAS |
| `<sub>/epoch/<id>` | воркер | токен отсечения: кто сейчас пишет эту единицу |
| `platform/mirror` | оператор | ручка зеркалирования бакетов между ресурсами |

Последняя строка стоит особняком: `platform/mirror` — единственный ключ, который не пишет ни один процесс курса. «Оператор» здесь — человек с управляющим токеном, а не роль рядом с консолью и контроллером: права на запись в `platform/*` нет ни у одного токена (в М11 и у консоли, и у ресурса на этот префикс только `read`/`list`). Так и задумано — ручка включает копирование бакетов между серверами, её ставят один раз при развёртывании, и процесса, которому это полагалось бы по работе, в системе нет. Та же форма у ручки из [урока 21](21-when-the-disk-fills.md).

**Объекты** (`objects.py`):

| Ключ | Кто пишет | Что это |
|---|---|---|
| `<sub>/<воркер>/heartbeat` | воркер | всё, что он про себя знает (урок 4) |
| `<sub>/snapshot` | контроллер | копия строк с возрастом — то, что уезжает из кластера в М12 |
| `platform/resources/<сервер>/heartbeat` | ресурс | что лежит на его дисках, сколько занято, где его HTTP |

Тринадцать строк, и это вся система. Теперь то, чего в ней нет.

**Нет ключа со списком воркеров.** Кто существует — выводится из `list` heartbeat'ов и из отметок времени в них. Реестр пришлось бы поддерживать в согласии с реальностью, а он бы расходился.

**Нет ключа со статусом.** Статус — в heartbeat'е, то есть у того, кто его наблюдает, а не у того, кто про него спрашивает.

**Нет ключа с блокировкой или лидерством.** Контроллеров может быть два, и они не выбирают лидера: каждая запись идёт по CAS, и второй проигрывает гонку. Ключ лидерства — это ключ, за который надо бороться, и время, в течение которого его никто не держит.

**Нет очереди и нет журнала команд.** Решение записывается в `placement/<id>` и остаётся там; воркер читает своё назначение. «Отправить» команду было бы значит завести получателя, подтверждение и повтор — а так повтором занимается сам цикл сверки.

## Шаг 4 — Назначение

```python
@dataclass
class Assignment:
    worker: str
    units: list[str]                 # what the subsystem calls its units of work; the platform does not know
    rev: int = 0
```

Три поля, и комментарий в середине — это граница модуля, записанная в объявлении структуры. `units` — список строк. Что эти строки значат, платформа не знает: для `vms` это номера камер, для `det` — имена вида `7-linecross`, для `thing` в тестах — `"1"`, `"2"`, `"3"`.

```python
    def to_items(self) -> dict:
        return {"units": ",".join(self.units), "rev": self.rev}

    @classmethod
    def from_items(cls, worker: str, items: dict | None) -> "Assignment":
        if not items:
            return cls(worker, [])
        return cls(worker, [u for u in items.get("units", "").split(",") if u], int(items.get("rev", 0)))
```

Список склеивается в строку через запятую, потому что в хранилище значения — строки (урок 2, шаг 8), и ничего вложенного туда положить нельзя. Разбор — `split(",")` с отбрасыванием пустых: без этого пустое назначение дало бы список из одной пустой строки, и воркер пошёл бы искать единицу с именем `""`.

Отсюда же — ограничение, о котором стоит знать: **идентификатор единицы не может содержать запятую.** В курсе они числовые или вида `7-linecross`, так что запрет незаметен, но он есть и нигде не проверяется. Альтернатива — JSON в значении — обменяла бы этот запрет на нечитаемость строки в `nomad var get` и на разбор, который может кинуть исключение. Выбрана запятая.

Отсутствующий ключ даёт пустое назначение, а не `None`. Это та же линия, что `get` → `(None, 0)` и `objects.get` → `None`: **свежий воркер, у которого нет строки назначения, ничего не выдумывает.** Он получает пустой список и не делает ничего — и это буквально утверждение теста `test_a_worker_with_no_assignment_invents_nothing` в М11.

## Шаг 5 — Зачем назначению своя ревизия

У ключа уже есть `ModifyIndex`. Зачем `rev`?

Потому что это разные числа для разных читателей. `ModifyIndex` — механизм хранилища: он растёт при любой записи в любой ключ, и его значение ничего не говорит о том, сколько раз менялось **это** назначение. Он нужен тому, кто пишет, — как `cas`.

`rev` — счётчик изменений назначения, и он нужен тому, кто **читает**. Воркер кладёт его в heartbeat (`assignment_rev`), и консоль показывает: назначение ревизии 4, воркер отчитывается о ревизии 3 — значит, он ещё не дошёл до последнего прохода. Без `rev` это можно было бы получить из `ModifyIndex`, но тогда номер прыгал бы на десятки при каждой чужой записи, и «отстал на одну ревизию» перестало бы что-либо значить.

Та же пара — «версия хранилища для писателя, счётчик изменений для читателя» — повторится в строках единиц: `revision` у камеры бумается контроллером, `observed_revision` возвращается воркером, и цикл сверки сравнивает их через `>=` (это М9, урок 6). Одна и та же идея на двух уровнях.

## Шаг 6 — Как это выглядит в работе

Из теста урока 1, теперь целиком понятный:

```python
    sub = Subsystem("thing")
    ctl = Controller(sub, box.vars, box.objects, wall=box.wall)
    w = Worker(sub, "t-1", box.vars, box.objects, clock=box.clock, wall=box.wall)
    ...
    a = ctl.assign("t-1", ["3", "1", "2"])
    assert a.units == ["1", "2", "3"] and a.rev == 1 and w.assignment().units == ["1", "2", "3"]
    assert ctl.assign("t-1", ["1"]).rev == 2
```

Три вещи за четыре строки. Контроллер назначает `["3", "1", "2"]` — и получает обратно `["1", "2", "3"]`: **назначение сортируется при записи**. Это не косметика: строка в хранилище должна зависеть только от множества единиц, а не от порядка, в котором контроллер их перебрал, иначе два прохода с одинаковым результатом дали бы две разные записи и лишнюю ревизию.

Воркер тут же читает своё назначение и видит то же самое — через `sub.assignment("t-1")`, то есть через тот же составитель ключа. Ни одна строка ключа в тесте не набрана.

Второе назначение даёт `rev == 2`. Счётчик увеличивается при каждой записи, даже если состав изменился на противоположный, — он считает **изменения**, а не единицы.

**Результат:** `Subsystem` и `Assignment` в `contract.py`; раскладка из тринадцати строк, выписанная своими словами; и ответ на вопрос, почему в ней нет ключа со списком воркеров.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Воркер не видит своего назначения | Ключ где-то набран руками (`vms/worker/` вместо `vms/workers/`). Единственное лекарство — не набирать: все обращения через `Subsystem`. |
| Пустое назначение даёт единицу с пустым именем | В разборе потерян фильтр `if u`. `"".split(",")` — это `[""]`, а не `[]`. |
| Идентификатор с запятой разваливает назначение | Так и есть, и нигде не проверяется. Если подсистеме нужны такие идентификаторы, менять придётся `to_items`/`from_items`, и в М11 — вместе с тем, как это читается в `nomad var get`. |
| `rev` прыгает через несколько | Кто-то подставил `ModifyIndex` вместо счётчика. Это разные числа: первое растёт от чужих записей. |
| Контроллер пишет строку камеры и ему это удаётся | Он взял `Subsystem.acl_controller()` — грубую версию `vms/*`. С появлением YAML права должны приходить из `SubsystemSpec.acl_controller()`. |
| Два прохода контроллера с одинаковым исходом дают две ревизии | Назначение записано без сортировки, либо запись происходит без сравнения с текущим значением. |

## Итог

- Ключи не набираются руками нигде: их составляет `Subsystem`, и у него одно поле — имя.
- Платформа знает четыре семейства по имени — назначение, heartbeat, эпоха, слот; всё остальное подсистема называет сама через `config(*parts)`.
- Вся система — тринадцать строк раскладки. В ней нет реестра воркеров, ключа статуса, лидерства и очереди, и каждое отсутствие — решение.
- Список хранится строкой через запятую, потому что значения в хранилище — строки; цена — запрет на запятую в идентификаторе.
- Отсутствующее назначение — это пустой список, а не ошибка: воркер, которому ничего не назначено, ничего не выдумывает.
- У назначения две версии: `ModifyIndex` для писателя, `rev` для читателя. Та же пара повторится как `revision`/`observed_revision`.
- Назначение сортируется при записи, чтобы строка зависела от множества, а не от порядка обхода.

## Упражнения

1. Поменяйте `heartbeat_key` на `<sub>/heartbeat/<воркер>` и прогоните сюиту. Что сломалось, что нет — и что это говорит о том, насколько раскладка «спрятана»?
2. Храните `units` как JSON вместо строки через запятую. Напишите, как теперь выглядит `nomad var get vms/workers/w-1` в М11 и что происходит при повреждённом значении.
3. Добавьте в раскладку ключ `vms/leader`. Опишите протокол, который вам понадобится, чтобы им пользоваться, и посчитайте, сколько секунд в худшем случае лидера не будет.
4. `acl_controller()` даёт `vms/*`. Напишите тест, который ловит контроллер, пишущий строку камеры, — и объясните, почему в уроке 10 он начнёт проходить сам собой.
5. Уберите сортировку в `assign`. Найдите проход контроллера, который теперь даёт новую ревизию при неизменном составе, и скажите, что это ломает выше по течению.
6. Выпишите раскладку для пятой подсистемы — скажем, `ptz` (управление поворотными камерами). Какие строки появятся и какая из тринадцати не понадобится?

## Что дальше

Ключи есть, имена есть, назначение есть. Не хватает того, что делает всё это безопасным при двух живых процессах с одним именем. [**Урок 6**](06-fencing-the-epoch-and-the-lease.md) пишет `next_epoch` и `Lease`: токен отсечения, который выдаётся без координатора, и аренду, которая решает локально, на монотонных часах.
