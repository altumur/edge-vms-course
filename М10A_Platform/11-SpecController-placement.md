# Урок 11 — `SpecController` II: размещение, молчания и снимок

**Модуль:** М10A — Платформа (ServerVMS, часть первая)
**Вы напишете:** вторую половину единственного контроллера курса. Сначала выбор воркера — чтение ёмкости и меток из heartbeat'ов, ограничение, пул, ничью, близость и дом — и `place`, собирающий **причину** размещения по частям; плюс `ensure_home`, который возвращает единицу домой, и `move`: единственную операцию в системе, которая осознанно создаёт двух писателей. Потом три способа потерять место, ручку администратора, перераспределение и перебалансировку — и то, что уезжает наружу: модель чтения, снимок и измеренное время переключения. После этого урока подсистема `counter` запускается целиком.
**Время:** ~180 минут.

## Зачем этот урок

Всё, что контроллер делал до сих пор, — это перекладывание: взять присланное, проверить, записать. Размещение — единственное место, где он **решает**, и решение это принимается по картине мира, которую он собрал сам: кто сейчас жив, сколько у каждого свободной ёмкости, чьи метки подходят, чей сервер отвечает.

Из этого следует то, к чему мы вернёмся на седьмом шаге: разместить может только тот, кто видит всю картину разом. И ещё одно, менее очевидное: решение надо **объяснить**. Строка размещения хранит не только «на ком», но и «почему» — предложение на человеческом языке, которое читают в три часа ночи, когда спрашивают, отчего камера 812 оказалась на этом сервере. Причина собирается по частям в этом уроке, и каждая её часть — это одно условие, которое участвовало в выборе.

Есть и правило, которое определяет всю форму метода и которое стоит назвать до кода: **добавление воркера ничего не двигает.** Новый воркер получает то, что не размещено, и ни одной уже размещённой единицы. Система, которая перебалансируется сама, — это система, в которой запись прерывается без причины, понятной оператору; а перебалансировка по просьбе есть, и она в шаге 18.

Размещение из первой половины урока ставит единицу туда, где есть место, и больше её не трогает. Правило «добавление воркера ничего не двигает» держится ровно до тех пор, пока место, куда поставили, никуда не девается. А оно девается — тремя разными способами, и различить их важнее, чем отреагировать.

**Воркер сказал, что уходит.** Планировщик уменьшил `count`, оператор увёл сервер. Слот отпущен (урок 7), назначение осталось. Это событие, о котором система знает точно, потому что ей сказали.

**Сервер перестал отвечать.** Воркер на нём жив и бьётся, но ресурс, к которому он пишет, замолчал. Ему некуда работать, хотя сам он в порядке. Различие тонкое и в М10B станет решающим.

**Машина исчезла.** И воркер молчит, и ресурс молчит — два молчания из разных процессов одной машины. Одно молчание, как мы решили в уроке 7, не толкуется; два — уже факт о машине.

И есть четвёртый случай, который не является потерей места вовсе: **администратор передумал.** Он решил, что на одном сервере работу несёт один воркер, а не все, сколько их туда попало. Это ручка, а не событие, и она в том же уроке, потому что влияет на тот же пул.

> **Что можно проверить без железа.** Всё, включая три молчания: часы поддельные, ресурсы — это heartbeat-объекты, которые тест пишет сам. В М10B это `test_lesson6_controller.py`: шесть единиц делятся 3/3 по ёмкости 3, седьмая ждёт, третий воркер забирает только седьмую; размещение под метками; два контроллера в гонке размещают сорок камер — каждая ровно один раз. И `test_lesson4_failover.py` в М11: «одно молчание ничего не двигает, два двигают».

## Шаг 1 — Картина мира

```python
    def capacity_of(self, worker: str) -> int:
        hb = self.workers_seen(max_age=1e12).get(worker)
        return int(hb.extra[self.spec.capacity_from]) if hb and self.spec.capacity_from in hb.extra else self.capacity

    def labels_of(self, worker: str) -> set[str]:
        hb = self.workers_seen(max_age=1e12).get(worker)
        return set(l for l in hb.extra.get("labels", "").split(",") if l) if hb else set()

    def server_of(self, worker: str) -> str:
        hb = self.workers_seen(max_age=1e12).get(worker)
        return hb.extra.get("server", "?") if hb else "?"
```

Три чтения одного и того же объекта, и в каждом — `max_age=1e12`, то есть **без ограничения возраста**. Это выглядит ошибкой и ею не является.

Возраст тут действительно неуместен. «Какая у `w-1` ёмкость» — вопрос о свойстве машины, а не о том, жив ли процесс. Если `w-1` молчит десять минут, его ёмкость всё ещё пятьдесят: столько камер эта машина тянет. Живость проверяется **отдельно**, при составлении пула (шаг 4), и проверяется один раз, а не трижды.

Разделение полезно ещё и потому, что причина размещения и страница консоли показывают сервер и метки для воркеров, которые уже молчат, — и показывают правду, а не прочерк.

`capacity_from` — имя ключа из YAML: `capacity` по умолчанию, но подсистема вольна назвать иначе. Если воркер ничего не сказал, берётся `self.capacity` — запасное число из конструктора. Формулировка, которую стоит запомнить: **ёмкость — это слово воркера, а не мнение контроллера.** Контроллер не считает, сколько камер потянет чужая машина; он читает то, что машина сказала о себе, потому что измерить её может только она (в М9, уроке 7, эта величина выводилась как `B + n·I` из настоящего замера).

Метки приходят строкой через запятую (`"vlan:cctv-a,gpu"`) — heartbeat плоский, вложенности в нём нет (урок 4).

```python
    def headroom(self) -> int:
        return sum(int(hb.extra.get(self.spec.headroom_from, 0)) for hb in self.workers_seen().values())
```

А вот здесь возраст **по умолчанию** — сорок пять секунд. Запас суммируется только по живым, потому что это число читает автоскейлер, решая, надо ли добавить процессов. Запас мёртвого воркера — не запас.

## Шаг 2 — Ограничение

```python
def _labels_subset(row: dict, worker_labels: set[str]) -> bool:
    return set(row.get("labels") or []) <= worker_labels


CONSTRAINTS = {"none": lambda row, labels: True, "labels-subset": _labels_subset}


def register_constraint(name: str, fn) -> None:
    """A subsystem's own rule, as code under a name — never as YAML."""
    CONSTRAINTS[name] = fn
```

```python
    def eligible(self, row: dict, workers: list[str]) -> list[str]:
        rule = CONSTRAINTS[self.spec.constraint]
        return [w for w in workers if rule(row, self.labels_of(w))]
```

Правило выбирается **по имени** из каталога. В YAML стоит `constraint: labels-subset`, в каталоге по этому имени лежит функция.

`labels-subset` — единственное содержательное правило курса, и оно ровно такое, как называется: метки единицы должны быть подмножеством меток воркера. Камера с меткой `vlan:cctv-a` идёт на воркера, чей сервер видит этот VLAN. Единица без меток идёт куда угодно (пустое множество — подмножество любого). Воркер без меток берёт только единицы без меток.

Направление отношения стоит проверить на себе: подмножество — **метки единицы**, а не воркера. Воркер с тремя метками годится для камеры с одной; камера с тремя требует воркера, у которого есть все три. Это «что мне нужно» против «что я умею», и перепутать их легко.

## Шаг 3 — Почему правило — код, а не выражение

Соблазн очевиден: описать ограничение прямо в YAML — `constraint: "labels ⊆ worker.labels and row.priority > 50"`. Тогда подсистема получит полную свободу, не трогая платформу.

И получит вместе с ней язык выражений, который надо разобрать, проверить, объяснить в ошибке и версионировать. Правило размещения выполняется на каждом проходе для каждой неразмещённой единицы по каждому воркеру; ошибка в нём — это единицы, которые молча никуда не встают. Отлаживать выражение в YAML нечем: ни отладчика, ни трассировки, ни теста.

Поэтому выбор такой: **правило — это код под именем**, и docstring `register_constraint` говорит это прямо. Подсистема, которой нужно своё правило, пишет функцию, покрывает её тестом и регистрирует под именем; YAML называет имя. Цена — новое правило требует правки кода; выигрыш — правило можно отладить.

Каталог, к слову, за весь курс так и остался из двух записей. Четыре подсистемы обошлись `labels-subset` и `none` — и это само по себе довод: язык выражений понадобился бы ради задач, которых не возникло.

## Шаг 4 — Пул

```python
    def _pool(self, workers):
        pool = sorted(workers if workers is not None else self.workers_seen())
        gone = set(self.without_resource(pool)) | set(self.idle_by_policy(pool))
        return [w for w in pool if w not in gone]
```

Кандидаты: переданный список или те, кто бился за последние сорок пять секунд. Здесь живость и проверяется — один раз, а не в каждом чтении.

Дальше вычитаются две группы, и обе — тема второй половины урока: воркеры, чей сервер молчит (когда подсистема требует ресурса) и воркеры, которых политика оставила простаивать (когда на сервере их несколько, а положено одному). Пока достаточно знать, что пул — это **живые минус непригодные**, и что решение о непригодности принимается до выбора, а не внутри него.

Сортировка нужна для детерминированности: два контроллера, идущие по одному списку в одном порядке, чаще приходят к одному выводу — и реже создают конфликт, который потом разрешает CAS.

## Шаг 5 — Ничья

```python
    def _best(self, pool: list[str]) -> tuple[str | None, int]:
        best, free = None, 0
        for w in pool:                                        # most-free-capacity: the one tie-break in the catalogue
            f = self.capacity_of(w) - self.load(w)
            if f > free:
                best, free = w, f
        return best, free
```

Свободная ёмкость — «сколько сказал» минус «сколько назначено», и берётся максимум. Строгое `>` означает, что при равенстве выигрывает **первый в отсортированном списке**: ничья разрывается детерминированно, а не случайно.

Детерминированность здесь не украшение. Два контроллера, размещающие одну единицу одновременно, при случайном выборе выбрали бы разных воркеров, и один из них проиграл бы CAS — то есть работа была бы сделана дважды. При детерминированном они выбирают одного и того же, и второй просто обнаруживает, что строка уже написана.

`free = 0` в начале даёт полезный побочный эффект: воркер, у которого свободной ёмкости нет (или она отрицательна — назначено больше, чем он объявил), не выбирается никогда, потому что `f > 0` для него ложно. Возврат `None` означает «некому».

И вот что означает `None` **в сообщении оператору**: не «`w-1` переполнен», а «система заполнена — или до этой единицы никто не дотягивается». Разница существенна: первое звучит как проблема конкретной машины, второе — как то, что есть на самом деле.

`tie_break` из YAML сейчас может быть только `most-free-capacity`; поле существует, чтобы каталог правил можно было расширить так же, как каталог ограничений.

## Шаг 6 — Близость и дом: два предпочтения, ни одного фильтра

```python
    def holder_near(self, uid) -> tuple[str, str] | None:
        if self.spec.near == "none":
            return None
        want = self.near_id(uid)
        for w, hb in heartbeats(self.objects, self.spec.near + "/").items():
            if self.wall() - hb.ts > 45.0:
                continue
            for st in hb.status:
                if str(st.get("id")) == str(want) and st.get("phase") == "running":
                    return w, hb.extra.get("server", "?")
        return None

    def near_id(self, uid) -> str:
        if self.spec.near_by == "id":
            return str(uid)
        row = self.unit(uid)
        return str(row.get(self.spec.near_by, "") or "") if row else ""
```

`near: rec` в спецификации VMS означает: «эта единица предпочитает стоять рядом с воркером подсистемы `rec`, который держит единицу с тем же идентификатором». Метод ищет такого воркера в **чужих** heartbeat'ах — по `status`, где каждая запись называет свой `id` и фазу.

Чью именно единицу — отвечают две ручки. `near_id` говорит, **какое моё значение** искать: по умолчанию мой идентификатор, а подсистема, названная иначе, указывает поле — у детектора единица `7-linecross`, и `near: {sub: rec, by: cam}` читает из строки `7`.

Вторая ручка — `near.of`: **где в чужом статусе** это значение искать. По умолчанию — их идентификатор, и это работало, пока запись называлась камерой (`id: cam`). Теперь имя записи выбирает оператор, и «запись с идентификатором 7» стало совпадением: у камеры 7 может быть только `7-cloud`. `near: {sub: rec, of: cam}` сравнивает не с их id, а с их полем `cam`, которое рекордер кладёт в свой статус (`status_extra`), — «тот, кто держит запись **о** камере 7». Чужие строки при этом никто не читает: только heartbeat.

Если ответили несколько — у камеры два архива, значит две записи, — берётся наименьший их идентификатор. Не «любой»: один и тот же проход по тем же heartbeat'ам обязан давать один и тот же сервер, иначе единица ходит между ними.

Строка читается только во второй форме — подсистема, разделяющая чужую нумерацию, не платит за те, которые её не разделяют. И заметьте, что `near_id` может вернуть пустую строку: поле не заполнено, следовать не за кем. Это не ошибка, а обычный ответ — близость всё равно предпочтение, и пустой пул из неё не получается.

### `home` — где единица живёт, и почему это не метка

```python
    def home_for(self, row: dict) -> str:
        if self.spec.home == "near":
            near = self.holder_near(row["id"]) if self.spec.near != "none" else None
            return near[1] if near and near[1] != "?" else ""
        return str(row.get(self.spec.home, "") or "") if self.spec.home else ""
```

`home` принимает одну из двух форм. `home: <поле>` — сервер, названный в этом поле строки: оператор говорит «запись камеры 7 лежит на srv-a». `home: near` — «там, где тот, за кем я иду».

Выразить дом меткой было бы естественным желанием — и ошибкой. Метка это фильтр: с `labels: [srv-a]` единица, чей сервер лёг, становится **неразмещаемой**, то есть перестаёт работать ровно в тот момент, когда должна продолжить работать где-то ещё. Дом — предпочтение: дома, если дом есть; где угодно, если нет.

### Ровно один из пары может следовать

`home: near` — это утверждение «у меня нет своего места». Если его скажут **обе** подсистемы пары, у пары не окажется якоря: каждый проход будет двигать каждую туда, где другая **была**, и они начнут меняться местами вместо того, чтобы встретиться.

Поэтому одна из двух обязана назвать настоящий дом. Какая именно — вопрос не вкуса: следовать может тот, кто **может двигаться**. В М10B это камера: её раздачу читают с любого сервера по RTSP. Запись двигаться не может — она приколочена к дискам, — и потому дом называет она.

Спецификация проверяет это при загрузке: `home: near` без `near` — ошибка, а не пустой дом.

### `spread_by` — единственный фильтр, который смотрит на другие единицы

Предпочтение говорит «лучше бы здесь»; фильтр говорит «только здесь». Есть ровно один случай, где нужен второй:

```python
def eligible(self, row: dict, workers: list[str]) -> list[str]:
    rule = CONSTRAINTS[self.spec.constraint]
    out = [w for w in workers if rule(row, self.labels_of(w))]
    return [w for w in out if self.server_of(w) not in self.servers_taken(row)]
```

`spread_by: <поле>` говорит: единицы с одинаковым значением этого поля размещаются на **разных** серверах. `servers_taken` собирает серверы, на которых уже стоит единица с тем же значением, и вычитает их из списка подходящих.

Почему это фильтр, а не предпочтение, — видно на единственном сценарии, ради которого оно нужно. Две записи одной камеры заводят затем, чтобы пережить отказ **одного** сервера. Вторая копия рядом с первой — не компромисс, а ровно та авария, от которой оператор страховался. Поэтому честный ответ здесь — «разместить негде» и строка в `/unplaceable`, а не тихое совмещение.

Заодно это место, где фильтр обязан побеждать предпочтение: обе копии — записи одной камеры, обе тянутся к её держателю, и близость утащила бы их на один сервер. Порядок в коде и решает: `eligible` отсекает, `_pick` выбирает из оставшегося.

И обратите внимание, чего в этом правиле нет: слова «камера». Платформа знает поле и значение; что две записи одной камеры не должны жить на одном сервере — это `spread_by: cam` в YAML подсистемы.

### Выбор

```python
    def _pick(self, pool: list[str], uid) -> tuple[str | None, int, str]:
        near = self.holder_near(uid)
        home = near[1] if self.spec.home == "near" and near else self.home_of(uid)
        follows = self.spec.home == "near"
        if home:
            best, free = self._best([w for w in pool if self.server_of(w) == home])
            if best is not None:
                return best, free, (f", beside {near[0]} holding it" if follows else f", at home on {home}")
        if near is not None and not follows:
            beside = [w for w in pool if self.server_of(w) == near[1]]
            best, free = self._best(beside)
            if best is not None:
                return best, free, f", beside {near[0]} holding it" + (f" (home {home} has no room)" if home else "")
        best, free = self._best(pool)
        note = ""
        if best is not None and near is not None and self.server_of(best) != near[1]:
            note = f", away from {near[0]} on {near[1]} (no room there)"
        if best is not None and home and not follows and self.server_of(best) != home:
            note += f"; away from home {home}"
        return best, free, note
```

Сначала пробуем выбрать **среди тех, кто на нужном сервере**: дом идёт первым, `near` — вторым. Получилось — возвращаем с припиской, которая называет, чем этот сервер был хорош. Не получилось (там нет места или нет подходящего воркера) — выбираем откуда угодно, и приписка говорит, чего мы при этом лишились.

Вот разница между ограничением и предпочтением, выраженная кодом: **ограничение сужает пул, предпочтение упорядочивает его.** Ограничение может оставить пул пустым — и тогда единица не размещается. Предпочтение не может: оно лишь пробует сначала одно подмножество, потом всё.

Так и должно быть, потому что жёсткое правило здесь было бы неверным. У регистратора твёрдое требование — быть там, где диски; у воркера — там, где сеть до камеры. Эти два места **могут не совпасть**, и тогда запись должна идти по сети, а не прекращаться. Предпочтение делает обычный случай дешёвым, не делая редкий невозможным.

Третий элемент кортежа — кусок будущей причины. Он пустой, когда ни близость, ни дом не настроены: подсистема без них не получает лишних слов в объяснении.

### Предпочтение, которое поддерживается

У `_pick` есть предел: он работает, только когда единицу **размещают**. Единица, уже стоящая не дома, там и останется — и это не теоретическая придирка. Камера, которую унесло на соседний сервер, пока её сервер лежал, будет держаться там вечно: читать её раздачу по RTSP работает, ничего не сломано, и потому ничто не едет обратно.

```python
    def ensure_home(self, budget: int = 1, workers: list[str] | None = None) -> list[tuple]:
        if budget <= 0 or not self.spec.home:
            return []
        moves, pool = [], self._pool(workers)
        for row in self.units():
            if len(moves) >= budget:
                break
            uid, home = row["id"], self.home_for(row)
            pl = self.placement(uid)
            if not home or pl is None or self.server_of(pl.worker) == home:
                continue
            best, free = self._best([w for w in self.eligible(row, pool) if self.server_of(w) == home])
            if best is None:
                continue
            why = f"it follows {self.spec.near} onto" if self.spec.home == "near" else "home is"
            self.move(uid, best, f"{why} {home}; most free capacity ({free}); on {home}")
            moves.append((uid, pl.worker, best))
        return moves
```

Три вещи в этом методе стоят того, чтобы их назвать.

**`budget`.** Каждый переезд — новая эпоха и шов в записи. Поэтому возврат домой ограничен, и контроллер зовёт его с единицей: один переезд за проход. Дом — не повод дёргать десять камер разом.

**`eligible` первым.** Фильтры по-прежнему выигрывают: единица, чей дом закрыт метками или `spread_by`, остаётся там, где стоит. Предпочтение, способное перебить фильтр, поставило бы камеру на сервер, который до неё не дотягивается.

**Молчание, когда дома нет.** Дом не поднялся или там нет места — метод не говорит ничего. Это не ошибка: единица там, где может быть, и в этом весь смысл предпочтения.

Вместе с `_pick` получается пара, которую стоит держать в голове целиком: **`_pick` решает, куда поставить; `ensure_home` — куда вернуть.** Аффинность без второго — разовый совет при рождении; с ним — свойство, которое система поддерживает.


## Шаг 7 — Размещение одной единицы

```python
    def place(self, uid, workers: list[str] | None = None) -> Placement | None:
        have = self.placement(uid)
        if have:
            return have
        row = self.unit(uid)
        if row is None:
            return None
        pool = self.eligible(row, self._pool(workers))
        best, free, near = self._pick(pool, uid)
        if best is None:
            return None                                 # "the system is full" — or nothing that can reach it
        reason = f"most free capacity ({free}) among {len(pool)} worker(s)"
        if self.spec.constraint == "labels-subset" and row.get("labels"):
            reason += f" reaching {','.join(sorted(row['labels']))}"
        reason += f"; on {self.server_of(best)}"
        if self.spec.requires == "resource":
            reason += f", whose resource is {self.resource_state(self.server_of(best))}"
        reason += near
        pl = Placement(self.spec.parse_id(uid), best, reason, self.wall(), 0)
```

**Первая строка — то самое правило.** Уже размещённая единица возвращается как есть, и никакой пересчёт не выполняется. Отсюда «добавление воркера ничего не двигает»: проход контроллера перебирает все единицы, но для размещённых сразу выходит. Новый воркер получит только то, у чего размещения нет.

Это решение стоит осознать как решение. Автоматическая перебалансировка выглядит заботой о системе: нагрузка выровнялась бы сама. Но каждое перемещение камеры — это остановка конвейера, новая эпоха, новый каталог на диске и разрыв в записи длиной в секунды. Система, делающая это по своему усмотрению, теряет запись в моменты, которые оператор не может ни предсказать, ни объяснить. Поэтому движение бывает только по двум поводам: единица не размещена, или кто-то **попросил** (шаг 18).

Дальше — причина, и вот как она собирается. Основа: `most free capacity (7) among 3 worker(s)` — на чём выбрали и из скольких. Под меткой: `reaching vlan:cctv-a` — какие метки пришлось покрыть. Сервер: `on srv-b` — потому что в три часа ночи вопрос звучит как «почему она на этом сервере», а не «почему на этом воркере»; воркер может переехать, сервер — нет. Состояние ресурса, если подсистема его требует: `whose resource is live`. И, если настроена близость, хвост от `_pick`.

Целиком получается предложение вроде:

```
most free capacity (7) among 3 worker(s) reaching vlan:cctv-a; on srv-b, whose resource is live, beside w-1 holding it
```

Каждое слово здесь — условие, которое участвовало в выборе. Ни одного слова, добавленного для красоты.

### Почему консоль не может размещать

Одна строка таблицы токенов из урока 9 стоит отдельного разговора, потому что желание её нарушить возникает у всех.

Пользователь создал камеру. Страница показывает её со словом «не размещена», и так может быть целых пять секунд — до следующего прохода контроллера. Соблазн очевиден: консоль уже держит объект `SpecController` (она использует его класс, чтобы писать строки), ей достаточно вызвать `place()` — и камера окажется размещённой мгновенно.

Не получится: токен консоли не включает `vms/placement/*`, и вызов кончится `Forbidden`. Так и задумано, и вот чем это оплачено.

Размещение — это **решение**, а не запись. Оно принимается по тому, кто сейчас жив, у кого сколько свободной ёмкости, чьи метки подходят, чей ресурс отвечает, не просрочен ли чей-то слот. Консоль этого не знает — точнее, знает ровно столько же, но у неё нет причины быть последовательной с другими консолями. Две консоли, размещающие две камеры одновременно, дважды посчитают одну и ту же свободную ёмкость; обе запишут корректно, по CAS, и обе будут правы — а воркер получит на две камеры больше, чем его число.

Контроллер этого не допускает не потому, что он один (он безопасен при двух), а потому, что **каждое его решение принимается в одном проходе с полным взглядом**. Консоль по своей природе принимает решение в ответ на одно нажатие.

Отсюда формулировка, которую стоит помнить дословно: *консоль, которая умела бы размещать, — это второй контроллер с браузером перед ним.* И плата за отказ — те самые пять секунд и слово «не размещена» на экране, которое честно говорит, что происходит.

## Шаг 8 — Два ключа, и порядок между ними

```python
        def mutate(it):
            if it and it.get("worker"):
                return None                             # the other instance placed it while we thought
            return {"worker": pl.worker, "reason": pl.reason, "at": pl.at, "rev": int(it.get("rev", 0)) + 1 if it else 1}
        written = self.write(self.sub.config("placement", str(uid)), mutate)
        pl = Placement(pl.unit, written["worker"], written["reason"], float(written["at"]), int(written["rev"]))
        self.assign_add(pl.worker, str(uid))
        return pl
```

Решение записывается в два места: строку размещения (кто и почему) и назначение воркера (что ему делать). Порядок — **сначала строка, потом назначение**, и он выбран не произвольно.

Строка размещения — это место, где CAS разрешает гонку. Мутатор возвращает `None`, если там уже есть воркер: значит, другой экземпляр контроллера успел разместить эту единицу, пока мы собирали картину мира. Мы не спорим — берём его решение (`written` содержит то, что лежит) и идём дальше. Именно поэтому объект `pl` **пересобирается** из записанного, а не используется свой: в назначение должен попасть тот воркер, который выиграл, а не тот, которого выбрали мы.

Если бы порядок был обратным — сначала назначить, потом записать строку, — проигравший успел бы добавить единицу в назначение своего кандидата, и её пришлось бы оттуда убирать. Два воркера получили бы одну единицу, и пусть ненадолго — этого достаточно, чтобы оба её запустили.

Падение между записями безвредно: строка размещения есть, назначения нет. Следующий проход увидит размещённую единицу, выйдет на первой строке `place`… и не добавит её в назначение. Это единственная известная дыра в проходе, и закрывает её `redistribute` из шага 17, который сверяет назначения с размещениями. В М11 то же самое делает `Directory`, отвечая на вопрос «где камера 7» сканом назначений: он **видит** расхождение и показывает его.

## Шаг 9 — Проход

```python
    def ensure_placed(self, workers: list[str] | None = None) -> list[Placement]:
        self.unplace_deleted()
        self.unplace_retired()
        out = []
        for r in self.units():
            pl = self.place(r["id"], workers)
            if pl:
                out.append(pl)
        return out
```

Восемь строк, и это весь основной проход контроллера: сначала прибрать удалённые (урок 10) и законченные, потом пройти по всем единицам. Возвращаются все размещения, а не только новые, — вызывающему обычно нужен именно полный список.

### Законченная работа — второе «не размещать»

Удалённая единица — не единственная, которую размещать не надо. Подсистема, чья единица **заканчивается**, добавляет второй случай, и объявляется он в спеке:

```yaml
  retire_when: {field: state, in: [done, failed]}
```

Дальше — две половины, и обе обязательны. `place` отказывается размещать строку, которая это говорит; `unplace_retired` забирает назначение у той, которая сказала это, уже будучи размещённой. Без второй половины предикат останавливает только следующее размещение, а вся ёмкость кластера рано или поздно оказывается занята работой, которая кончилась.

Почему **строка**, а не heartbeat, — вопрос, на который легко ответить неверно. Заманчиво читать фазу воркера: он единственный знает, что доделал. Но снятие назначения заставит воркера единицу бросить, следующий heartbeat её не упомянет, доказательство `done` исчезнет — и единица будет размещена снова, и начнёт сначала. И так навсегда. Законченность обязана лежать там, где она не зависит от того, назначена ли ещё единица; строку при этом пишет не воркер (ему запрещено — урок 9) и не контроллер (тогда у строки два писателя), а консоль.

Это же объясняет, почему `retire_when` — не `enabled`. Выключенную камеру читает воркер, а не размещение: она сохраняет назначение и строку в списке консоли. «Стоять видимой и ничего не делать» и «кончиться» — разные вещи, и спека называет, какое поле и какие значения означают второе.

Стоимость: чтение всех строк плюс по чтению размещения на каждую. При пятидесяти камерах — сто с небольшим обращений к хранилищу раз в пять секунд. На коробке это чтение файлов, в М11 — HTTP; и это та цифра, при которой в М11 появится кэш на чтения консоли, но не контроллера.

## Шаг 10 — Перемещение

```python
    def move(self, uid, to: str, reason: str) -> Placement:
        """The one two-writer operation: the destination takes the next epoch when
        it starts; the source's lease fences on renewal and it stops. Explicit,
        never automatic."""
        for w, a in self.assignments().items():                     # wherever it is listed, and not only where the row says
            if str(uid) in a.units and w != to:
                self.assign_remove(w, str(uid))
        new = self.write(self.sub.config("placement", str(uid)),
                         lambda it: {"worker": to, "reason": reason, "at": self.wall(), "rev": int(it.get("rev", 0)) + 1 if it else 1})
        self.assign_add(to, str(uid))
        return Placement(self.spec.parse_id(uid), to, reason, float(new["at"]), int(new["rev"]))
```

Единственный метод, который **осознанно создаёт двух писателей**, и docstring это называет прямо.

Смотрите, что происходит. Единицу убирают из старого назначения и добавляют в новое. Но старый воркер узнает об этом только на своём следующем проходе — до тех пор он продолжает её вести. А новый начнёт, как только прочитает своё назначение. Между этими моментами двое ведут одну единицу.

Это тот самый случай, ради которого существует эпоха **на единицу**, а не на воркера (урок 6, шаг 11). Слот тут никого не отсечёт: оба воркера живы и держат свои имена честно. Отсечёт эпоха: новый берёт следующий номер при старте, старый обнаруживает это при продлении аренды и останавливает эту единицу — только её, потому что в его назначении её больше нет (урок 8).

Наложение ограничено сверху: не больше `TTL − margin`, то есть двадцати пяти секунд. За это время в системе видеонаблюдения получается двадцать пять секунд, записанных дважды, в двух каталогах эпох. Не потеряно ничего, и обе записи опознаваемы.

Первая строка — тонкость, которую легко пропустить: единица убирается **отовсюду, где она числится**, а не только у того воркера, которого называет строка размещения. Расхождение между строкой и назначениями возможно (шаг 8, падение между записями), и `move` — хорошее место, чтобы его прибрать заодно.

`reason` здесь не собирается, а **передаётся**: перемещение всегда происходит по какому-то поводу, и повод знает вызывающий. В шаге 17 это будут `slot w-3 released; …`, `resource on srv-a silent; …`, `server srv-a gone: …` — и каждый из них попадёт в строку и на экран.

Разница между «неразмещаемой» и «просто ждущей» существенна для оператора. Камера, ждущая, потому что система заполнена, дождётся следующего воркера. Камера с меткой `vlan:cctv-c`, которую не видит ни один сервер, не дождётся никогда — и об этом надо сказать, а не оставлять её в списке ожидающих.

## Шаг 12 — Ручка администратора

```python
    POLICY_CHOICES = {"servers": ("distinct", "shared")}

    @property
    def POLICY_DEFAULTS(self) -> dict:
        return {"servers": self.spec.servers}

    def policy(self) -> dict:
        items, _ = self.vars.get(self.sub.config("policy"))
        out = dict(self.POLICY_DEFAULTS)
        for k, v in (items or {}).items():
            if k in self.POLICY_CHOICES and v in self.POLICY_CHOICES[k]:
                out[k] = v
        return out
```

Одна ручка на весь курс, и у неё два положения. **`shared`** — на одном сервере может работать сколько угодно воркеров, и все несут единицы. **`distinct`** — на сервере работает один несущий воркер; остальные, попавшие туда, простаивают.

Умолчание приходит **из спецификации**, а не из константы: `placement.servers` в YAML. Так у камер `shared` (коробка — это несколько воркеров на одном сервере, и это нормально), а у записей `distinct` (второй регистратор на тех же дисках — не второе место для записи). Одна ручка, два разумных умолчания, и оба записаны там же, где остальное описание подсистемы.

Чтение **снисходительно**: неизвестный ключ и неизвестное значение молча игнорируются, и возвращается умолчание. Строка в хранилище, испорченная чужой правкой или оставшаяся от старой версии, не может сломать проход контроллера.

```python
    def set_policy(self, changes: dict) -> dict:
        for k, v in changes.items():
            if k not in self.POLICY_CHOICES or v not in self.POLICY_CHOICES[k]:
                raise Refused(f"policy {k} must be one of {', '.join(self.POLICY_CHOICES.get(k, ()))}")
        self.write(self.sub.config("policy"), lambda it: {**(it or {}), **{k: str(v) for k, v in changes.items()}})
        return self.policy()
```

Запись **строгая**: неизвестное значение — `Refused` с перечислением допустимых. Асимметрия сознательная и повторяет линию урока 9: человеку, который ошибся **сейчас**, говорят сразу; данные, которые уже лежат, не должны ломать работу.

Возвращается `policy()`, а не то, что записали: администратор видит полный набор ручек после правки, включая те, которых не трогал.

## Шаг 13 — Кто простаивает по политике

```python
    def idle_by_policy(self, workers) -> list[str]:
        if self.policy()["servers"] != "distinct":
            return []
        by_place: dict[str, list[str]] = {}
        for w in sorted(workers, key=slot_number):
            by_place.setdefault(self.place_of(w), []).append(w)
        idle = []
        for server, ws in by_place.items():
            if server == "?" or len(ws) < 2:
                continue
            keep = max(ws, key=lambda w: (self.load(w), -slot_number(w)))
            idle += [w for w in ws if w != keep]
        return idle
```

При `shared` — пустой список, и дальше ничего не считается.

При `distinct` воркеры группируются по серверам, и на каждом сервере с двумя и более остаётся один: **тот, у кого больше загрузка, а при равной — с меньшим номером слота.**

Оба критерия нужны. Первый — «остаётся тот, кто уже работает»: если `w-1` несёт двадцать камер, а `w-4` только что приехал на тот же сервер, простаивать должен приезжий, иначе двадцать камер поедут без всякой пользы. Второй — детерминированность: при равной загрузке (обычно нулевой) выбор не должен зависеть от порядка обхода, иначе два контроллера решат по-разному.

`server == "?"` — воркеры, чьего сервера мы не знаем (не бились ни разу), пропускаются: складывать их в одну корзину было бы неверно, это разные неизвестности.

### `place_of`, а не `server_of`: в чём считается «одно место»

Группировка идёт не по серверу, а по **месту**, и слово стоит объяснить, потому что до сих пор эти два были одним.

Сервер с одним диском — одно место, и всё сказанное выше про него верно. Сервер с тремя дисками — **три**: на каждом диске пишет свой рекордер, и два рекордера на одном диске по-прежнему не второе место записи, а два на разных дисках одной коробки — ровно оно. Считай мы по серверам, две трети купленного железа простаивали бы по политике.

Поэтому у спецификации появилось слово:

```yaml
placement:
  place_by:  volume        # в чём считается место: поле heartbeat'а, по умолчанию `server`
  servers:   distinct      # один рекордер на МЕСТО
  home:      home          # строка называет том, а не сервер
```

```python
    def place_of(self, worker: str) -> str:
        if self.spec.place_by == "server":
            return self.server_of(worker)
        hb = self.workers_seen(max_age=1e12).get(worker)
        return str(hb.extra.get(self.spec.place_by) or hb.extra.get("server", "?"))
```

**За этим полем идут ровно двое: политика и дом.** Остальное остаётся на сервере, и каждый случай стоит проговорить, потому что соблазн перевести всё одинаково велик:

| Что | Считается в | Почему |
|---|---|---|
| `servers: distinct` | **месте** | диск — это место записи, коробка — нет |
| `home` | **месте** | оператор говорит «эта камера пишется на этот диск» |
| `requires: resource` | сервере | достижимость — свойство машины; у тома нет адреса |
| осушение (`drain`) | сервере | выводят из работы коробку, а не диск |
| `spread_by` | сервере | две копии на двух дисках одной машины не переживут её смерть |

Последняя строка — самая важная. `spread_by` существует, чтобы вторая копия была **не там, где первая**; перевести её на тома значило бы разложить обе копии по двум дискам одного сервера и назвать это страховкой.

**Падение на сервер, когда поле не сказано**, — это миграция: воркер, написанный до появления тома, читается как один том, названный по серверу. Для коробки с одним диском это правда; а там, где неправда, ошибка безопасная — три нерасставленных рекордера прочитаются как три на одном месте, и политика оставит один, вместо того чтобы дать двоим считать, что диск их.

Заметьте, что метод возвращает **кого исключить**, а не кого оставить. Так его удобнее складывать с другим исключением в пуле.

## Шаг 14 — Три состояния ресурса

```python
    def resource_state(self, server: str, lost_after: float = 45.0) -> str:
        from .resource import resources_seen
        hb = resources_seen(self.objects).get(server)
        if hb is None:
            return "unknown"
        return "live" if self.wall() - float(hb["ts"]) <= lost_after else "silent"
```

Три значения, и среднее из них — **`unknown`** — важнее двух крайних.

`live` — ресурс на этом сервере бился недавно. `silent` — бился, но давно. `unknown` — **не бился никогда**, мы про него ничего не знаем.

Разница между `silent` и `unknown` — это разница между «замолчал» и «не запускался», и она определяет, действовать ли. Замолчавший ресурс был и пропал: место, которое было, исчезло, и это повод. Неизвестный ресурс, возможно, просто ещё не стартовал — а на коробке, где процесс ресурса появился в М10B позже воркера, так бывает при каждом первом запуске. Считать `unknown` за `silent` значило бы отказываться размещать на свежей коробке, пока не поднимется каждый процесс.

Поэтому правило, которое проходит через весь оставшийся код: **исключает только `silent`.** Формулировка «неизвестность — не повод действовать» — из той же семьи, что «одно молчание не толкуется».

Ленивый импорт `resources_seen` внутри метода — из-за кругового импорта: `resource.py` пользуется спецификацией. Один такой импорт в платформе на весь курс, и стоит он одной строки.

```python
    def without_resource(self, workers) -> list[str]:
        if self.spec.requires != "resource":
            return []
        return [w for w in workers if self.resource_state(self.server_of(w)) == "silent"]
```

Проверка включается только для подсистем, объявивших `requires: resource` в YAML. Для `counter` она не нужна: тик не пишет на диск, и молчащий ресурс ему безразличен. Для камер и записей — нужна.

## Шаг 15 — Два молчания

```python
    def gone_servers(self, lost_after: float = 45.0) -> dict[str, str]:
        """Lapsed slots whose server's resource is silent too: {slot: server}."""
        if self.spec.requires != "resource" or self.policy()["servers"] != "distinct":
            return {}
        now = self.wall(); out = {}
        for name, slot in self.slots().items():
            if slot.lapsed(now) and now > slot.until + lost_after and self.assignment(name).units:
                server = self.server_of(name)
                if server != "?" and self.resource_state(server, lost_after) == "silent":
                    out[name] = server
        return out
```

Единственное место в системе, где контроллер действует **по молчанию**, — и посмотрите, сколько условий на это навешано.

Первое: подсистема требует ресурса. Если ей всё равно, где работать, отсутствие сервера не мешает — планировщик перезапустит процесс где-нибудь ещё.

Второе: политика `distinct`. При `shared` умерший сервер — забота планировщика: он поставит замену на соседний, та возьмёт слот и унаследует назначение (урок 7). Вмешиваться незачем. А при `distinct` замена, приехавшая на соседний сервер, **будет простаивать по политике** — и работа не тронется с места, пока кто-нибудь её не перенесёт.

Третье: слот просрочен — **и просрочен ещё на один `lost_after` сверх того**. Это отсрочка, данная планировщику: сорок пять секунд на то, чтобы слот лапсировался, и ещё сорок пять на то, чтобы он поставил замену. Если за полторы минуты никто не пришёл, никто и не придёт.

Четвёртое: у слота есть назначение. Пустой слот двигать незачем.

Пятое: сервер известен и его ресурс **молчит** — не `unknown`, именно `silent`.

Пять условий, и это правильная цена. Ошибка здесь стоит переезда работы туда, откуда она через минуту поедет обратно, — то есть двух разрывов записи вместо нуля.

Возвращается `{слот: сервер}`, потому что причина будет называть и то, и другое: человеку нужно знать, какая машина исчезла, а не только чьи единицы поехали.

## Шаг 16 — Пул, собранный целиком

```python
    def _pool(self, workers):
        pool = sorted(workers if workers is not None else self.workers_seen())
        gone = set(self.without_resource(pool)) | set(self.idle_by_policy(pool))
        return [w for w in pool if w not in gone]
```

Теперь метод из шага 4 читается полностью: живые, минус те, чей ресурс замолчал, минус те, кого политика оставила простаивать. Обе группы вычитаются **до** выбора, и потому ни в `_best`, ни в `_pick` нет ни одной проверки про ресурсы и политику. Каждое решение принимается в одном месте.

## Шаг 17 — Перераспределение

```python
    def redistribute(self, workers: list[str] | None = None) -> list[tuple]:
        self.unplace_deleted()
        moves = []
        seen = sorted(workers if workers is not None else self.workers_seen())
        gone_for = {g: f"slot {g} released" for g in self.released_slots()}
        for w in self.without_resource(seen):
            if self.assignment(w).units:
                gone_for.setdefault(w, f"resource on {self.server_of(w)} silent")
        for w, server in self.gone_servers().items():
            gone_for.setdefault(w, f"server {server} gone: slot {w} lapsed and its resource silent")
```

Сначала собирается словарь «откуда уносим → почему», и в нём три источника ровно из шага «Зачем». Порядок важен: `setdefault` не перезаписывает, поэтому воркер, попавший в список отпущенных, сохранит причину «слот отпущен», даже если он заодно без ресурса. Наиболее определённая причина выигрывает.

Каждая причина — **готовое предложение на человеческом языке**, и в этом видно, чему курс придаёт значение: `server srv-a gone: slot w-1 lapsed and its resource silent` — это ответ на вопрос «почему камера уехала», данный до того, как его задали.

```python
        for gone, why in gone_for.items():
            live = [w for w in self._pool(workers) if w != gone]
            for unit in sorted(self.assignment(gone).units, key=_unit_key):
                uid = self.spec.parse_id(unit)
                row = self.unit(uid)
                pool = self.eligible(row, live) if row else live
                best, free, near = self._pick(pool, uid)
                if best is None:
                    break
                self.move(uid, best, f"{why}; most free capacity ({free}); on {self.server_of(best)}{near}")
                moves.append((uid, gone, best))
        return moves
```

Дальше — тот же выбор, что при размещении: пул, ограничение, близость. Причина склеивается из двух частей: **почему уносим** и **почему принесли именно сюда**.

`break` при `best is None` — не `continue`. Если некуда деть эту единицу, остальным из того же назначения тоже некуда: пул один. Единицы остаются там, где были, и это честнее, чем снять их в никуда: строка размещения продолжает указывать на мёртвого воркера, консоль показывает это, а следующий проход попробует снова, когда появится место.

Строка размещения при этом **не обнуляется**. Единица числится там, где её последний раз разместили, — и если воркер вернётся (просрочка, а не уход), он её подберёт, ничего не потеряв.

## Шаг 18 — Перебалансировка по просьбе

```python
    def rebalance(self, budget: int, dead_band: float | None = None, workers: list[str] | None = None) -> list[tuple]:
        dead_band = self.spec.dead_band if dead_band is None else dead_band
        workers = self._pool(workers)
        moves = []
        for _ in range(budget):
            if len(workers) < 2:
                break
            loads = {w: self.load(w) / self.capacity_of(w) for w in workers}
            hi, lo = max(workers, key=loads.get), min(workers, key=loads.get)
            if loads[hi] - loads[lo] < dead_band:
                break
            cands = sorted(self.assignment(hi).units, key=_unit_key)
            if not cands or self.load(lo) + 1 > self.capacity_of(lo):
                break
            uid = self.spec.parse_id(cands[0])
            self.move(uid, lo, f"rebalance from {hi} (spread {(loads[hi] - loads[lo]) * 100:.0f}%)")
            moves.append((uid, hi, lo))
        return moves
```

Три ограничителя, и каждый защищает от своей беды.

**Бюджет.** Число перемещений, заданное вызывающим. Не «выровнять», а «сделать не больше стольких шагов». Оператор, нажавший кнопку, получает предсказуемое количество разрывов записи, а не «сколько понадобится».

**Мёртвая зона.** Пока разница загрузок меньше десяти процентов, ничего не двигается. Без неё перебалансировка гонялась бы за идеалом, перекладывая единицы туда-сюда ради процента.

**Проверка вместимости.** Если у наименее загруженного нет места даже на одну, выход. Без неё можно было бы переложить туда, откуда придётся класть обратно.

И самое важное — **этого метода нет в проходе контроллера**. `ensure_placed` и `redistribute` вызываются каждые пять секунд; `rebalance` вызывается только когда попросили. Разница в том же, о чём говорил урок 11: система, которая двигает работу по своему усмотрению, теряет запись в моменты, которых оператор не ждал.

Причина называет разброс в процентах — то число, которое оператор увидел на странице перед нажатием.

## Шаг 19 — Модель чтения

```python
    def read_model(self, lost_after: float = 45.0) -> list[dict]:
        now = self.wall()
        rows = []
        for w, hb in self.workers_seen(max_age=1e12).items():
            age = now - hb.ts
            state = "live" if age <= lost_after else "stale"
            for s in hb.status:
                rows.append({**s, "worker": w, "server": hb.extra.get("server", "?"), "age": round(age, 1), "worker_state": state})
        return sorted(rows, key=lambda r: _unit_key(str(r["id"])))
```

То, что видит человек на странице: строка на **наблюдение**, собранная из heartbeat'ов всех воркеров. К тому, что сказал воркер, добавляются четыре поля: кто сказал, на каком сервере, сколько секунд назад и живой ли он сейчас.

Возраст берётся **без ограничения** (`max_age=1e12`), а состояние вычисляется отдельно. Это ровно то же решение, что в шаге 1 с ёмкостью: устаревшие данные **показываются со своим возрастом**, а не прячутся. Оператор, у которого воркер молчит две минуты, должен видеть последнее, что тот сказал, и метку `stale` рядом, — а не пустую страницу.

Обратите внимание: модель чтения строится из наблюдений, а не из конфигурации. Строка, которую никто не наблюдает (единица не размещена, или её воркер не бился ни разу), в ней **не появится** — и консоль поэтому показывает две вещи рядом: `rows` (что наблюдается) и `configured` (что настроено). Разница между ними — это и есть «настроено, но не работает».

## Шаг 20 — Снимок

```python
    def snapshot(self) -> dict:
        """Units and placement as one object: what the layer above reads. A copy
        with an age — never the rows themselves, which do not leave raft."""
        keep = ["id"] + [f for f in self.spec.snapshot if f != "id"] + ["revision"]
        units = []
        for r in self.units():
            w = self.where(r["id"])
            units.append({**{k: r[k] for k in keep if k in r}, "worker": w, "server": self.server_of(w or "")})
        return {"cluster": self.cluster, "ts": self.wall(), self.spec.rows: units}

    def publish_snapshot(self) -> None:
        import json
        self.objects.put(self.sub.config("snapshot"), json.dumps(self.snapshot()).encode())
```

Единственное, что покидает кластер. Поля отбираются по списку `snapshot` из YAML — плюс идентификатор и ревизия всегда — и к каждой единице добавляется, где она сейчас.

Docstring называет суть: **копия с возрастом, а не сами строки.** `ts` в снимке — это момент, когда его собрали, и слой выше (домен М12) обязан на него смотреть: то, что он читает, устарело ровно на столько. Строки не покидают raft никогда, потому что у них один писатель и он здесь; то, что уезжает, — производное, и его старость видна.

Публикуется в **объектное** хранилище (урок 4): пишется целиком, читается целиком, версия не нужна. Раз в проход контроллера, то есть каждые пять секунд.

> **Одним объектом — пока.** Здесь снимок пишется в один ключ на весь кластер, и это единственное место в платформе, где данные растут вместе с кластером, а не вместе со своим писателем. У объектного хранилища есть потолок, и на проектных 600 камерах этот объект в него не влезает. Нарезка по воркеру — **урок 19**; до него форма остаётся такой, чтобы было видно, откуда взялась проблема.

Отбор полей по списку — способ подсистемы сказать, чего наружу отдавать не надо. Камера, к примеру, не отдаёт свой источник целиком, если в нём мог оказаться адрес с учётными данными.

## Шаг 21 — Измеренное переключение

```python
    def failover_seconds(self) -> dict[str, float]:
        """Per worker: the gap between the heartbeat before its current instance
        started and that instance's first — measured from what the workers wrote."""
        out = {}
        for w, hb in self.workers_seen(max_age=1e12).items():
            started = float(hb.extra.get("started", hb.ts))
            prev = float(hb.extra.get("previous_hb", 0) or 0)
            if prev:
                out[w] = round(started - prev, 1)
        return out
```

Сколько секунд прошло между последним сигналом **предыдущего** экземпляра слота и первым сигналом нынешнего.

Откуда берутся эти числа: при старте воркер читает heartbeat, лежащий под его именем (урок 8), и, если он написан другим экземпляром, запоминает его время как `previous_hb`, а своё — как `started`. Обе величины он публикует в своём heartbeat'е. Контроллер просто вычитает.

Смысл в том, **кто измеряет**. Не контроллер по своим часам, не монитор снаружи — сам воркер, по тому, что осталось на диске от его предшественника. Это время от «прошлый замолчал» до «нынешний заговорил», то есть настоящий провал в работе, и в М11 оно становится числом в паспорте продукта: `vms_failover_seconds{kind="worst"}`.

`if prev` отбрасывает воркеров, у которых предшественника не было: первый запуск переключением не является.

## Шаг 22 — `counter` запускается

Контроллер закончен, и подсистема из урока 9 теперь работает целиком. Воркер для неё — сорок строк на базе из урока 8:

```python
class CounterWorker(Worker):
    def __init__(self, *a, **kw):
        super().__init__(*a, **kw); self.claim_slot(); self.running = {}
    def reconcile_once(self, now):
        rows = {r["id"]: r for u in self.assignment().units
                for r in [Row(self.vars.get(SPEC.sub.config("ticks", u))[0])] if r}
        for uid in list(self.running):
            if uid not in rows: self.running.pop(uid); self.release(str(uid))
        for uid, r in rows.items():
            if uid not in self.running and r["enabled"]:
                self.take_epoch(str(uid))
                if self.may_write(str(uid)): self.running[uid] = r
        return sorted(self.running)
    def heartbeat_once(self):
        self.heartbeat([{"id": u, "phase": "running", "epoch": self.epochs[str(u)]} for u in self.running],
                       server=self.server, capacity=self.capacity, headroom=self.capacity - len(self.rows))
```

И вся система:

```python
ctl = SpecController(SPEC, vars_.as_writer("countercontroller", SPEC.acl_controller()), objects)
con = SpecController(SPEC, vars_.as_writer("counterconsole",    SPEC.acl_console()),    objects)
w   = CounterWorker(SPEC.sub, None, vars_.as_writer("counterworker", SPEC.sub.acl_worker()), objects)
w.heartbeat_once()
con.create({"name": "первый", "every": 5})       # оператор создал единицу — через свой токен
ctl.ensure_placed()                              # контроллер разместил её — через свой
w.reconcile_once(0)                              # воркер прочитал назначение и взял эпоху
```

Три токена, три роли, ни одной строки платформы, написанной ради счётчика. Уберите воркера, подождите — единица останется размещённой на просроченном слоте. Скажите `w.release_slot()` — и `redistribute` унесёт её к соседу с причиной `slot w-1 released`. Поставьте `servers: distinct` и приведите второго воркера на тот же сервер — он будет простаивать.

Это и есть демонстрация, ради которой модуль отделён: **всё поведение системы уже существует, и камеры к нему не имеют отношения.**

**Результат:** размещение целиком и контроллер целиком; собранная своими словами причина для конкретной единицы с меткой; объяснение, почему строка размещения пишется раньше назначения; работающий `counter` из YAML и сорока строк; и написанное своими словами объяснение, почему `unknown` не считается за `silent`, а одно молчание — за два.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Новый воркер «перетягивает» на себя уже размещённые единицы | Потеряна первая строка `place`. Перебалансировка бывает только по просьбе. |
| Две единицы у двух воркеров после гонки контроллеров | Объект размещения не пересобран из записанного: в назначение ушёл свой кандидат, а не победитель CAS. |
| Единица размещена, но воркер её не видит | Падение между двумя записями. Проход это не чинит; чинит `redistribute` (шаг 17), а показывает `Directory` в М11. |
| Ёмкость воркера всегда запасная | В heartbeat'е нет ключа, названного в `capacity_from`, — или подсистема назвала его иначе, чем воркер пишет. |
| Молчащий воркер показывается без сервера и меток | Где-то в `capacity_of`/`labels_of`/`server_of` появился возраст. Они читают свойства машины, а не живость. |
| Камера с меткой не размещается никуда | Направление подмножества перепутано: метки **единицы** должны входить в метки воркера, а не наоборот. |
| Причина размещения нечитаема | В неё добавили то, что не участвовало в выборе. Каждое слово — условие. |
| Единица дома не появляется, хотя дом вернулся | Забыт `ensure_home` в проходе контроллера: `_pick` работает только при размещении. |
| Две подсистемы каждый проход меняются серверами | Обе сказали `home: near`. У пары нет якоря; настоящий дом должна назвать та, что приколочена к железу. |
| Единица не едет домой, хотя дом жив | Дом закрыт фильтром — метками или `spread_by`. Так и задумано: `ensure_home` выбирает из `eligible`. |
| Две записи одной единицы дольше полуминуты | Аренда длиннее, чем должна: наложение ограничено `TTL − margin`. |
| На свежей коробке ничего не размещается | `unknown` считается за `silent`. Ресурс ещё не стартовал — это не повод отказывать. |
| Работа уехала и через минуту вернулась | Сработало `gone_servers` без отсрочки в один `lost_after`. Планировщику надо дать шанс. |
| При `shared` умерший сервер двигает работу | `gone_servers` не проверяет политику. При `shared` замена приедет на соседний сервер и всё подберёт сама. |
| При `distinct` работа встала после смерти сервера | Обратное: `gone_servers` не срабатывает. Замена простаивает по политике, и двигать должен контроллер. |
| Простаивает тот, кто нёс двадцать единиц | В `idle_by_policy` потерян критерий загрузки. Остаётся тот, кто уже работает. |
| Два контроллера оставляют разных воркеров | Потерян второй критерий (`-slot_number`). При равной загрузке выбор обязан быть детерминированным. |
| Перебалансировка идёт сама | `rebalance` попал в проход контроллера. Он вызывается только по просьбе. |
| Перекладывание туда-сюда | Мёртвая зона нулевая или слишком мала. |
| Страница пустеет, когда воркер молчит | В `read_model` появился возраст-фильтр. Показывать надо последнее сказанное, с меткой `stale`. |
| Домен М12 показывает свежие данные как устаревшие | Он не смотрит на `ts` снимка — или контроллер не публикует его каждым проходом. |
| Консоль получает `Forbidden` на `vms/placement/*` | Так и должно быть. Размещает контроллер, следующим проходом. Если пять секунд ожидания неприемлемы, уменьшают период прохода, а не расширяют токен. |

## Итог

- Размещение — единственное настоящее решение контроллера, и потому оно объясняется: причина хранится рядом с выбором.
- Ёмкость — слово воркера; контроллер её не вычисляет. Метки, сервер и ёмкость читаются без учёта возраста: это свойства машины, а живость проверяется отдельно, один раз.
- Ограничение — код под именем, а не выражение в YAML: правило выполняется в горячем цикле и должно быть отлаживаемым.
- Метки единицы должны быть подмножеством меток воркера, а не наоборот.
- Ничья разрывается детерминированно — чтобы два контроллера чаще приходили к одному выводу и реже конфликтовали.
- Близость и дом упорядочивают пул, ограничение его сужает. Предпочтение не может оставить единицу без места — потому дом и не выражается меткой.
- Из пары подсистем следовать может ровно одна: иначе у пары нет якоря и обе меняются местами каждый проход. Следует та, что способна двигаться.
- `_pick` решает, куда поставить; `ensure_home` — куда вернуть. Без второго аффинность остаётся разовым советом при рождении единицы.
- Уже размещённая единица не пересматривается: добавление воркера ничего не двигает. Движение — только по просьбе или потому, что двигать некуда.
- Сначала строка размещения (там CAS решает спор), потом назначение — и объект пересобирается из записанного.
- `move` сознательно создаёт двух писателей на время до `TTL − margin`; их разводит эпоха на единицу, а не слот.
- Место теряется тремя способами: воркер сказал, ресурс замолчал, машина исчезла. Различить важнее, чем отреагировать.
- Ручка читается снисходительно и пишется строго: испорченные данные не ломают проход, ошибка человека называется сразу.
- Умолчание политики приходит из спецификации: у камер `shared`, у записей `distinct`.
- Три состояния ресурса, и действовать можно только на `silent`. `unknown` — это «не знаем», и это не повод.
- По молчанию контроллер действует в единственном месте, и там пять условий, включая отсрочку планировщику.
- При `shared` умерший сервер — забота планировщика; при `distinct` — контроллера, потому что замена простаивала бы.
- Причина перераспределения склеивается из «почему уносим» и «почему принесли сюда».
- Некуда деть одну — значит, некуда деть и остальные: `break`, и строка размещения не обнуляется.
- Перебалансировка только по просьбе, с бюджетом и мёртвой зоной; в проходе её нет.
- Наружу уезжает копия с возрастом, а не строки. Время переключения измеряют сами воркеры, а не наблюдатель.
- Консоль, умеющая размещать, — второй контроллер: она решает по одному нажатию, а не по одному полному взгляду.
