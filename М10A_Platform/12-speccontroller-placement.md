Плюс `ensure_home`, который возвращает единицу домой, и `move`: единственную операцию в системе, которая осознанно создаёт двух писателей.
**Время:** ~90 минут.

## Зачем этот урок

Всё, что контроллер делал до сих пор, — это перекладывание: взять присланное, проверить, записать. Размещение — единственное место, где он **решает**, и решение это принимается по картине мира, которую он собрал сам: кто сейчас жив, сколько у каждого свободной ёмкости, чьи метки подходят, чей сервер отвечает.

Из этого следует то, о чём говорил урок 3: разместить может только тот, кто видит всю картину разом. И ещё одно, менее очевидное: решение надо **объяснить**. Строка размещения хранит не только «на ком», но и «почему» — предложение на человеческом языке, которое читают в три часа ночи, когда спрашивают, отчего камера 812 оказалась на этом сервере. Причина собирается по частям в этом уроке, и каждая её часть — это одно условие, которое участвовало в выборе.

Есть и правило, которое определяет всю форму метода и которое стоит назвать до кода: **добавление воркера ничего не двигает.** Новый воркер получает то, что не размещено, и ни одной уже размещённой единицы. Система, которая перебалансируется сама, — это система, в которой запись прерывается без причины, понятной оператору; а перебалансировка по просьбе есть, и она в уроке 13.

> **Что можно проверить без железа.** Всё. В М10B это `test_lesson6_controller.py`: шесть единиц делятся 3/3 по ёмкости 3, седьмая ждёт, третий воркер забирает только седьмую; размещение под метками; два контроллера в гонке размещают сорок камер — каждая ровно один раз.

## Шаг 1 — Картина мира

```python
    def capacity_of(self, worker: str) -> int:
        hb = self.workers_seen(max_age=1e12).get(worker)
        return int(hb.extra[self.spec.capacity_from]) if hb and self.spec.capacity_from in hb.extra else self.capacity

    def labels_of(self, worker: str) -> set[str]:
        hb = self.workers_seen(max_age=1e12).get(worker)
        return set(l for l in hb.extra.get("labels", "").split(",") if l) if hb else set()

    def server_of(self, worker: str) -> str:
        hb = self.workers_seen(max_age=1e12).get(worker)
        return hb.extra.get("server", "?") if hb else "?"
```

Три чтения одного и того же объекта, и в каждом — `max_age=1e12`, то есть **без ограничения возраста**. Это выглядит ошибкой и ею не является.

Возраст тут действительно неуместен. «Какая у `w-1` ёмкость» — вопрос о свойстве машины, а не о том, жив ли процесс. Если `w-1` молчит десять минут, его ёмкость всё ещё пятьдесят: столько камер эта машина тянет. Живость проверяется **отдельно**, при составлении пула (шаг 4), и проверяется один раз, а не трижды.

Разделение полезно ещё и потому, что причина размещения и страница консоли показывают сервер и метки для воркеров, которые уже молчат, — и показывают правду, а не прочерк.

`capacity_from` — имя ключа из YAML: `capacity` по умолчанию, но подсистема вольна назвать иначе. Если воркер ничего не сказал, берётся `self.capacity` — запасное число из конструктора. Формулировка, которую стоит запомнить: **ёмкость — это слово воркера, а не мнение контроллера.** Контроллер не считает, сколько камер потянет чужая машина; он читает то, что машина сказала о себе, потому что измерить её может только она (в М9, уроке 7, эта величина выводилась как `B + n·I` из настоящего замера).

Метки приходят строкой через запятую (`"vlan:cctv-a,gpu"`) — heartbeat плоский, вложенности в нём нет (урок 4).

```python
    def headroom(self) -> int:
        return sum(int(hb.extra.get(self.spec.headroom_from, 0)) for hb in self.workers_seen().values())
```

А вот здесь возраст **по умолчанию** — сорок пять секунд. Запас суммируется только по живым, потому что это число читает автоскейлер, решая, надо ли добавить процессов. Запас мёртвого воркера — не запас.

## Шаг 2 — Ограничение

```python
def _labels_subset(row: dict, worker_labels: set[str]) -> bool:
    return set(row.get("labels") or []) <= worker_labels


CONSTRAINTS = {"none": lambda row, labels: True, "labels-subset": _labels_subset}


def register_constraint(name: str, fn) -> None:
    """A subsystem's own rule, as code under a name — never as YAML."""
    CONSTRAINTS[name] = fn
```

```python
    def eligible(self, row: dict, workers: list[str]) -> list[str]:
        rule = CONSTRAINTS[self.spec.constraint]
        return [w for w in workers if rule(row, self.labels_of(w))]
```

Правило выбирается **по имени** из каталога. В YAML стоит `constraint: labels-subset`, в каталоге по этому имени лежит функция.

`labels-subset` — единственное содержательное правило курса, и оно ровно такое, как называется: метки единицы должны быть подмножеством меток воркера. Камера с меткой `vlan:cctv-a` идёт на воркера, чей сервер видит этот VLAN. Единица без меток идёт куда угодно (пустое множество — подмножество любого). Воркер без меток берёт только единицы без меток.

Направление отношения стоит проверить на себе: подмножество — **метки единицы**, а не воркера. Воркер с тремя метками годится для камеры с одной; камера с тремя требует воркера, у которого есть все три. Это «что мне нужно» против «что я умею», и перепутать их легко.

## Шаг 3 — Почему правило — код, а не выражение

Соблазн очевиден: описать ограничение прямо в YAML — `constraint: "labels ⊆ worker.labels and row.priority > 50"`. Тогда подсистема получит полную свободу, не трогая платформу.

И получит вместе с ней язык выражений, который надо разобрать, проверить, объяснить в ошибке и версионировать. Правило размещения выполняется на каждом проходе для каждой неразмещённой единицы по каждому воркеру; ошибка в нём — это единицы, которые молча никуда не встают. Отлаживать выражение в YAML нечем: ни отладчика, ни трассировки, ни теста.

Поэтому выбор такой: **правило — это код под именем**, и docstring `register_constraint` говорит это прямо. Подсистема, которой нужно своё правило, пишет функцию, покрывает её тестом и регистрирует под именем; YAML называет имя. Цена — новое правило требует правки кода; выигрыш — правило можно отладить.

Каталог, к слову, за весь курс так и остался из двух записей. Четыре подсистемы обошлись `labels-subset` и `none` — и это само по себе довод: язык выражений понадобился бы ради задач, которых не возникло.

## Шаг 4 — Пул

```python
    def _pool(self, workers):
        pool = sorted(workers if workers is not None else self.workers_seen())
        gone = set(self.without_resource(pool)) | set(self.idle_by_policy(pool))
        return [w for w in pool if w not in gone]
```

Кандидаты: переданный список или те, кто бился за последние сорок пять секунд. Здесь живость и проверяется — один раз, а не в каждом чтении.

Дальше вычитаются две группы, и обе — тема урока 13: воркеры, чей сервер молчит (когда подсистема требует ресурса) и воркеры, которых политика оставила простаивать (когда на сервере их несколько, а положено одному). Пока достаточно знать, что пул — это **живые минус непригодные**, и что решение о непригодности принимается до выбора, а не внутри него.

Сортировка нужна для детерминированности: два контроллера, идущие по одному списку в одном порядке, чаще приходят к одному выводу — и реже создают конфликт, который потом разрешает CAS.

## Шаг 5 — Ничья

```python
    def _best(self, pool: list[str]) -> tuple[str | None, int]:
        best, free = None, 0
        for w in pool:                                        # most-free-capacity: the one tie-break in the catalogue
            f = self.capacity_of(w) - self.load(w)
            if f > free:
                best, free = w, f
        return best, free
```

Свободная ёмкость — «сколько сказал» минус «сколько назначено», и берётся максимум. Строгое `>` означает, что при равенстве выигрывает **первый в отсортированном списке**: ничья разрывается детерминированно, а не случайно.

Детерминированность здесь не украшение. Два контроллера, размещающие одну единицу одновременно, при случайном выборе выбрали бы разных воркеров, и один из них проиграл бы CAS — то есть работа была бы сделана дважды. При детерминированном они выбирают одного и того же, и второй просто обнаруживает, что строка уже написана.

`free = 0` в начале даёт полезный побочный эффект: воркер, у которого свободной ёмкости нет (или она отрицательна — назначено больше, чем он объявил), не выбирается никогда, потому что `f > 0` для него ложно. Возврат `None` означает «некому».

И вот что означает `None` **в сообщении оператору**: не «`w-1` переполнен», а «система заполнена — или до этой единицы никто не дотягивается». Разница существенна: первое звучит как проблема конкретной машины, второе — как то, что есть на самом деле.

`tie_break` из YAML сейчас может быть только `most-free-capacity`; поле существует, чтобы каталог правил можно было расширить так же, как каталог ограничений.

## Шаг 6 — Близость и дом: два предпочтения, ни одного фильтра

```python
    def holder_near(self, uid) -> tuple[str, str] | None:
        if self.spec.near == "none":
            return None
        for w, hb in heartbeats(self.objects, self.spec.near + "/").items():
            if self.wall() - hb.ts > 45.0:
                continue
            for st in hb.status:
                if str(st.get("id")) == str(uid) and st.get("phase") == "running":
                    return w, hb.extra.get("server", "?")
        return None
```

`near: rec` в спецификации VMS означает: «эта единица предпочитает стоять рядом с воркером подсистемы `rec`, который держит единицу с тем же идентификатором». Метод ищет такого воркера в **чужих** heartbeat'ах — по `status`, где каждая запись называет свой `id` и фазу.

### `home` — где единица живёт, и почему это не метка

```python
    def home_for(self, row: dict) -> str:
        if self.spec.home == "near":
            near = self.holder_near(row["id"]) if self.spec.near != "none" else None
            return near[1] if near and near[1] != "?" else ""
        return str(row.get(self.spec.home, "") or "") if self.spec.home else ""
```

`home` принимает одну из двух форм. `home: <поле>` — сервер, названный в этом поле строки: оператор говорит «запись камеры 7 лежит на srv-a». `home: near` — «там, где тот, за кем я иду».

Выразить дом меткой было бы естественным желанием — и ошибкой. Метка это фильтр: с `labels: [srv-a]` единица, чей сервер лёг, становится **неразмещаемой**, то есть перестаёт работать ровно в тот момент, когда должна продолжить работать где-то ещё. Дом — предпочтение: дома, если дом есть; где угодно, если нет.

### Ровно один из пары может следовать

`home: near` — это утверждение «у меня нет своего места». Если его скажут **обе** подсистемы пары, у пары не окажется якоря: каждый проход будет двигать каждую туда, где другая **была**, и они начнут меняться местами вместо того, чтобы встретиться.

Поэтому одна из двух обязана назвать настоящий дом. Какая именно — вопрос не вкуса: следовать может тот, кто **может двигаться**. В М10B это камера: её раздачу читают с любого сервера по RTSP. Запись двигаться не может — она приколочена к дискам, — и потому дом называет она.

Спецификация проверяет это при загрузке: `home: near` без `near` — ошибка, а не пустой дом.

### `spread_by` — единственный фильтр, который смотрит на другие единицы

Предпочтение говорит «лучше бы здесь»; фильтр говорит «только здесь». Есть ровно один случай, где нужен второй:

```python
def eligible(self, row: dict, workers: list[str]) -> list[str]:
    rule = CONSTRAINTS[self.spec.constraint]
    out = [w for w in workers if rule(row, self.labels_of(w))]
    return [w for w in out if self.server_of(w) not in self.servers_taken(row)]
```

`spread_by: <поле>` говорит: единицы с одинаковым значением этого поля размещаются на **разных** серверах. `servers_taken` собирает серверы, на которых уже стоит единица с тем же значением, и вычитает их из списка подходящих.

Почему это фильтр, а не предпочтение, — видно на единственном сценарии, ради которого оно нужно. Две записи одной камеры заводят затем, чтобы пережить отказ **одного** сервера. Вторая копия рядом с первой — не компромисс, а ровно та авария, от которой оператор страховался. Поэтому честный ответ здесь — «разместить негде» и строка в `/unplaceable`, а не тихое совмещение.

Заодно это место, где фильтр обязан побеждать предпочтение: обе копии названы одной камерой, и потому у обеих одинаковый дом — он утащил бы их на один сервер. Порядок в коде и решает: `eligible` отсекает, `_pick` выбирает из оставшегося.

И обратите внимание, чего в этом правиле нет: слова «камера». Платформа знает поле и значение; что две записи одной камеры не должны жить на одном сервере — это `spread_by: cam` в YAML подсистемы.

### Выбор

```python
    def _pick(self, pool: list[str], uid) -> tuple[str | None, int, str]:
        near = self.holder_near(uid)
        home = near[1] if self.spec.home == "near" and near else self.home_of(uid)
        follows = self.spec.home == "near"
        if home:
            best, free = self._best([w for w in pool if self.server_of(w) == home])
            if best is not None:
                return best, free, (f", beside {near[0]} holding it" if follows else f", at home on {home}")
        if near is not None and not follows:
            beside = [w for w in pool if self.server_of(w) == near[1]]
            best, free = self._best(beside)
            if best is not None:
                return best, free, f", beside {near[0]} holding it" + (f" (home {home} has no room)" if home else "")
        best, free = self._best(pool)
        note = ""
        if best is not None and near is not None and self.server_of(best) != near[1]:
            note = f", away from {near[0]} on {near[1]} (no room there)"
        if best is not None and home and not follows and self.server_of(best) != home:
            note += f"; away from home {home}"
        return best, free, note
```

Сначала пробуем выбрать **среди тех, кто на нужном сервере**: дом идёт первым, `near` — вторым. Получилось — возвращаем с припиской, которая называет, чем этот сервер был хорош. Не получилось (там нет места или нет подходящего воркера) — выбираем откуда угодно, и приписка говорит, чего мы при этом лишились.

Вот разница между ограничением и предпочтением, выраженная кодом: **ограничение сужает пул, предпочтение упорядочивает его.** Ограничение может оставить пул пустым — и тогда единица не размещается. Предпочтение не может: оно лишь пробует сначала одно подмножество, потом всё.

Так и должно быть, потому что жёсткое правило здесь было бы неверным. У регистратора твёрдое требование — быть там, где диски; у воркера — там, где сеть до камеры. Эти два места **могут не совпасть**, и тогда запись должна идти по сети, а не прекращаться. Предпочтение делает обычный случай дешёвым, не делая редкий невозможным.

Третий элемент кортежа — кусок будущей причины. Он пустой, когда ни близость, ни дом не настроены: подсистема без них не получает лишних слов в объяснении.

### Предпочтение, которое поддерживается

У `_pick` есть предел: он работает, только когда единицу **размещают**. Единица, уже стоящая не дома, там и останется — и это не теоретическая придирка. Камера, которую унесло на соседний сервер, пока её сервер лежал, будет держаться там вечно: читать её раздачу по RTSP работает, ничего не сломано, и потому ничто не едет обратно.

```python
    def ensure_home(self, budget: int = 1, workers: list[str] | None = None) -> list[tuple]:
        if budget <= 0 or not self.spec.home:
            return []
        moves, pool = [], self._pool(workers)
        for row in self.units():
            if len(moves) >= budget:
                break
            uid, home = row["id"], self.home_for(row)
            pl = self.placement(uid)
            if not home or pl is None or self.server_of(pl.worker) == home:
                continue
            best, free = self._best([w for w in self.eligible(row, pool) if self.server_of(w) == home])
            if best is None:
                continue
            why = f"it follows {self.spec.near} onto" if self.spec.home == "near" else "home is"
            self.move(uid, best, f"{why} {home}; most free capacity ({free}); on {home}")
            moves.append((uid, pl.worker, best))
        return moves
```

Три вещи в этом методе стоят того, чтобы их назвать.

**`budget`.** Каждый переезд — новая эпоха и шов в записи. Поэтому возврат домой ограничен, и контроллер зовёт его с единицей: один переезд за проход. Дом — не повод дёргать десять камер разом.

**`eligible` первым.** Фильтры по-прежнему выигрывают: единица, чей дом закрыт метками или `spread_by`, остаётся там, где стоит. Предпочтение, способное перебить фильтр, поставило бы камеру на сервер, который до неё не дотягивается.

**Молчание, когда дома нет.** Дом не поднялся или там нет места — метод не говорит ничего. Это не ошибка: единица там, где может быть, и в этом весь смысл предпочтения.

Вместе с `_pick` получается пара, которую стоит держать в голове целиком: **`_pick` решает, куда поставить; `ensure_home` — куда вернуть.** Аффинность без второго — разовый совет при рождении; с ним — свойство, которое система поддерживает.


## Шаг 7 — Размещение одной единицы

```python
    def place(self, uid, workers: list[str] | None = None) -> Placement | None:
        have = self.placement(uid)
        if have:
            return have
        row = self.unit(uid)
        if row is None:
            return None
        pool = self.eligible(row, self._pool(workers))
        best, free, near = self._pick(pool, uid)
        if best is None:
            return None                                 # "the system is full" — or nothing that can reach it
        reason = f"most free capacity ({free}) among {len(pool)} worker(s)"
        if self.spec.constraint == "labels-subset" and row.get("labels"):
            reason += f" reaching {','.join(sorted(row['labels']))}"
        reason += f"; on {self.server_of(best)}"
        if self.spec.requires == "resource":
            reason += f", whose resource is {self.resource_state(self.server_of(best))}"
        reason += near
        pl = Placement(self.spec.parse_id(uid), best, reason, self.wall(), 0)
```

**Первая строка — то самое правило.** Уже размещённая единица возвращается как есть, и никакой пересчёт не выполняется. Отсюда «добавление воркера ничего не двигает»: проход контроллера перебирает все единицы, но для размещённых сразу выходит. Новый воркер получит только то, у чего размещения нет.

Это решение стоит осознать как решение. Автоматическая перебалансировка выглядит заботой о системе: нагрузка выровнялась бы сама. Но каждое перемещение камеры — это остановка конвейера, новая эпоха, новый каталог на диске и разрыв в записи длиной в секунды. Система, делающая это по своему усмотрению, теряет запись в моменты, которые оператор не может ни предсказать, ни объяснить. Поэтому движение бывает только по двум поводам: единица не размещена, или кто-то **попросил** (урок 13).

Дальше — причина, и вот как она собирается. Основа: `most free capacity (7) among 3 worker(s)` — на чём выбрали и из скольких. Под меткой: `reaching vlan:cctv-a` — какие метки пришлось покрыть. Сервер: `on srv-b` — потому что в три часа ночи вопрос звучит как «почему она на этом сервере», а не «почему на этом воркере»; воркер может переехать, сервер — нет. Состояние ресурса, если подсистема его требует: `whose resource is live`. И, если настроена близость, хвост от `_pick`.

Целиком получается предложение вроде:

```
most free capacity (7) among 3 worker(s) reaching vlan:cctv-a; on srv-b, whose resource is live, beside w-1 holding it
```

Каждое слово здесь — условие, которое участвовало в выборе. Ни одного слова, добавленного для красоты.

## Шаг 8 — Два ключа, и порядок между ними

```python
        def mutate(it):
            if it and it.get("worker"):
                return None                             # the other instance placed it while we thought
            return {"worker": pl.worker, "reason": pl.reason, "at": pl.at, "rev": int(it.get("rev", 0)) + 1 if it else 1}
        written = self.write(self.sub.config("placement", str(uid)), mutate)
        pl = Placement(pl.unit, written["worker"], written["reason"], float(written["at"]), int(written["rev"]))
        self.assign_add(pl.worker, str(uid))
        return pl
```

Решение записывается в два места: строку размещения (кто и почему) и назначение воркера (что ему делать). Порядок — **сначала строка, потом назначение**, и он выбран не произвольно.

Строка размещения — это место, где CAS разрешает гонку. Мутатор возвращает `None`, если там уже есть воркер: значит, другой экземпляр контроллера успел разместить эту единицу, пока мы собирали картину мира. Мы не спорим — берём его решение (`written` содержит то, что лежит) и идём дальше. Именно поэтому объект `pl` **пересобирается** из записанного, а не используется свой: в назначение должен попасть тот воркер, который выиграл, а не тот, которого выбрали мы.

Если бы порядок был обратным — сначала назначить, потом записать строку, — проигравший успел бы добавить единицу в назначение своего кандидата, и её пришлось бы оттуда убирать. Два воркера получили бы одну единицу, и пусть ненадолго — этого достаточно, чтобы оба её запустили.

Падение между записями безвредно: строка размещения есть, назначения нет. Следующий проход увидит размещённую единицу, выйдет на первой строке `place`… и не добавит её в назначение. Это единственная известная дыра в проходе, и закрывает её `redistribute` из урока 13, который сверяет назначения с размещениями. В М11 то же самое делает `Directory`, отвечая на вопрос «где камера 7» сканом назначений: он **видит** расхождение и показывает его.

## Шаг 9 — Проход

```python
    def ensure_placed(self, workers: list[str] | None = None) -> list[Placement]:
        self.unplace_deleted()
        out = []
        for r in self.units():
            pl = self.place(r["id"], workers)
            if pl:
                out.append(pl)
        return out
```

Семь строк, и это весь основной проход контроллера: сначала прибрать удалённые (урок 11), потом пройти по всем единицам. Возвращаются все размещения, а не только новые, — вызывающему обычно нужен именно полный список.

Стоимость: чтение всех строк плюс по чтению размещения на каждую. При пятидесяти камерах — сто с небольшим обращений к хранилищу раз в пять секунд. На коробке это чтение файлов, в М11 — HTTP; и это та цифра, при которой в М11 появится кэш на чтения консоли, но не контроллера.

## Шаг 10 — Перемещение

```python
    def move(self, uid, to: str, reason: str) -> Placement:
        """The one two-writer operation: the destination takes the next epoch when
        it starts; the source's lease fences on renewal and it stops. Explicit,
        never automatic."""
        for w, a in self.assignments().items():                     # wherever it is listed, and not only where the row says
            if str(uid) in a.units and w != to:
                self.assign_remove(w, str(uid))
        new = self.write(self.sub.config("placement", str(uid)),
                         lambda it: {"worker": to, "reason": reason, "at": self.wall(), "rev": int(it.get("rev", 0)) + 1 if it else 1})
        self.assign_add(to, str(uid))
        return Placement(self.spec.parse_id(uid), to, reason, float(new["at"]), int(new["rev"]))
```

Единственный метод, который **осознанно создаёт двух писателей**, и docstring это называет прямо.

Смотрите, что происходит. Единицу убирают из старого назначения и добавляют в новое. Но старый воркер узнает об этом только на своём следующем проходе — до тех пор он продолжает её вести. А новый начнёт, как только прочитает своё назначение. Между этими моментами двое ведут одну единицу.

Это тот самый случай, ради которого существует эпоха **на единицу**, а не на воркера (урок 6, шаг 11). Слот тут никого не отсечёт: оба воркера живы и держат свои имена честно. Отсечёт эпоха: новый берёт следующий номер при старте, старый обнаруживает это при продлении аренды и останавливает эту единицу — только её, потому что в его назначении её больше нет (урок 8).

Наложение ограничено сверху: не больше `TTL − margin`, то есть двадцати пяти секунд. За это время в системе видеонаблюдения получается двадцать пять секунд, записанных дважды, в двух каталогах эпох. Не потеряно ничего, и обе записи опознаваемы.

Первая строка — тонкость, которую легко пропустить: единица убирается **отовсюду, где она числится**, а не только у того воркера, которого называет строка размещения. Расхождение между строкой и назначениями возможно (шаг 8, падение между записями), и `move` — хорошее место, чтобы его прибрать заодно.

`reason` здесь не собирается, а **передаётся**: перемещение всегда происходит по какому-то поводу, и повод знает вызывающий. В уроке 13 это будут `slot w-3 released; …`, `resource on srv-a silent; …`, `server srv-a gone: …` — и каждый из них попадёт в строку и на экран.

## Шаг 11 — Ответы оператору

```python
    def unplaceable(self) -> list[dict]:
        """Units nothing live can serve — the console's honest answer, with the labels named."""
        live = self._pool(None)
        return [{"id": r["id"], "labels": r.get("labels", []), "workers_live": len(live)}
                for r in self.units() if self.placement(r["id"]) is None and not self.eligible(r, live)]
```

Единицы, которые не размещены и которых **не может взять никто из живых**. Отдельный вопрос, отдельный ответ — и в нём названы метки, из-за которых это вышло, и число живых воркеров.

Разница между «неразмещаемой» и «просто ждущей» существенна для оператора. Камера, ждущая, потому что система заполнена, дождётся следующего воркера. Камера с меткой `vlan:cctv-c`, которую не видит ни один сервер, не дождётся никогда — и об этом надо сказать, а не оставлять её в списке ожидающих.

```python
    def where(self, uid) -> str | None:
        pl = self.placement(uid)
        return pl.worker if pl else None
```

Одна строка — и в М11 она превратится в отдельный модуль, потому что на кластере тот же вопрос задают двумя способами: «что записано в строке размещения» и «в чьём назначении она числится». Обычно ответы совпадают; когда нет — это и есть окно перемещения, и консоль показывает оба.

**Результат:** размещение целиком; собранная своими словами причина для конкретной единицы с меткой; и объяснение, почему строка размещения пишется раньше назначения.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Новый воркер «перетягивает» на себя уже размещённые единицы | Потеряна первая строка `place`. Перебалансировка бывает только по просьбе. |
| Две единицы у двух воркеров после гонки контроллеров | Объект размещения не пересобран из записанного: в назначение ушёл свой кандидат, а не победитель CAS. |
| Единица размещена, но воркер её не видит | Падение между двумя записями. Проход это не чинит; чинит `redistribute` (урок 13), а показывает `Directory` в М11. |
| Ёмкость воркера всегда запасная | В heartbeat'е нет ключа, названного в `capacity_from`, — или подсистема назвала его иначе, чем воркер пишет. |
| Молчащий воркер показывается без сервера и меток | Где-то в `capacity_of`/`labels_of`/`server_of` появился возраст. Они читают свойства машины, а не живость. |
| Камера с меткой не размещается никуда | Направление подмножества перепутано: метки **единицы** должны входить в метки воркера, а не наоборот. |
| Причина размещения нечитаема | В неё добавили то, что не участвовало в выборе. Каждое слово — условие. |
| Единица дома не появляется, хотя дом вернулся | Забыт `ensure_home` в проходе контроллера: `_pick` работает только при размещении. |
| Две подсистемы каждый проход меняются серверами | Обе сказали `home: near`. У пары нет якоря; настоящий дом должна назвать та, что приколочена к железу. |
| Единица не едет домой, хотя дом жив | Дом закрыт фильтром — метками или `spread_by`. Так и задумано: `ensure_home` выбирает из `eligible`. |
| Две записи одной единицы дольше полуминуты | Аренда длиннее, чем должна: наложение ограничено `TTL − margin`. |

## Итог

- Размещение — единственное настоящее решение контроллера, и потому оно объясняется: причина хранится рядом с выбором.
- Ёмкость — слово воркера; контроллер её не вычисляет. Метки, сервер и ёмкость читаются без учёта возраста: это свойства машины, а живость проверяется отдельно, один раз.
- Ограничение — код под именем, а не выражение в YAML: правило выполняется в горячем цикле и должно быть отлаживаемым.
- Метки единицы должны быть подмножеством меток воркера, а не наоборот.
- Ничья разрывается детерминированно — чтобы два контроллера чаще приходили к одному выводу и реже конфликтовали.
- Близость и дом упорядочивают пул, ограничение его сужает. Предпочтение не может оставить единицу без места — потому дом и не выражается меткой.
- Из пары подсистем следовать может ровно одна: иначе у пары нет якоря и обе меняются местами каждый проход. Следует та, что способна двигаться.
- `_pick` решает, куда поставить; `ensure_home` — куда вернуть. Без второго аффинность остаётся разовым советом при рождении единицы.
- Уже размещённая единица не пересматривается: добавление воркера ничего не двигает. Движение — только по просьбе или потому, что двигать некуда.
- Сначала строка размещения (там CAS решает спор), потом назначение — и объект пересобирается из записанного.
- `move` сознательно создаёт двух писателей на время до `TTL − margin`; их разводит эпоха на единицу, а не слот.
