# Урок 15 — База, которая является кэшем

**Модуль:** М10A — Платформа (ServerVMS, часть первая)
**Вы напишете:** `psimplatform/eventdatabase.py` — `EventDatabase`, SQLite над собственным деревом ресурса, и `MergedIndex`, то, что есть у консоли **вместо** базы. И докажете, что первая является кэшем, удалив её целиком.
**Время:** ~90 минут.

## Зачем этот урок

Событий на диске много, лежат они по файлу на единицу, эпоху и промежуток, а спрашивают их иначе: «что происходило с седьмой вчера с трёх до четырёх», «покажи все `motion` за час», «что было на этом сервере, пока он отваливался». Ни один из этих вопросов не отвечается обходом каталога за приемлемое время.

Значит, нужен индекс. И тут же — вопрос, который в этом курсе задают каждому новому куску состояния: **чей он и что будет, если он пропадёт?**

Ответ определяет всё остальное. Индекс — это **кэш**: в нём нет ни байта, которого нет в файлах, и его можно удалить целиком, не потеряв ничего, кроме скорости. Из этого следует, что он не подсистема (нечего размещать), что у него нет контроллера (нечего решать), что ему не нужна ни репликация, ни резервная копия, и что он живёт **внутри процесса ресурса**, один на ресурс.

А дальше — вопрос, на который курс отвечает не так, как обычно отвечают. Консоль должна показывать события **со всех** серверов. Соблазн: собрать их в одну базу, кластерную. Нет: **у консоли нет базы вообще.** Она спрашивает каждый живой ресурс и сливает ответы по времени. Почему — во второй половине урока.

> **Что можно проверить без железа.** Оба свойства. В М10B `test_lesson10_events.py` собирает вторую базу над тем же деревом и сравнивает ответы: «удалена и пересобрана к тому же ответу». И удаляет бакет по сроку хранения, проверяя, что строки ушли вместе с файлом.

## Что нужно знать заранее

- **Урок 14** — бакеты: путь, `buckets_under`, `subsystems_under`.
- **Урок 6** — эпоха: отсечение решается сравнением, и сравнивает не база.
- **Урок 4** — heartbeat ресурса: по нему `MergedIndex` узнаёт, кого спрашивать.

## Чему вы научитесь

1. Определять, является ли кусок состояния кэшем, и что из этого следует.
2. Хранить прочитанное так, чтобы дочитывать растущий файл, а не перечитывать.
3. Отвечать на вопрос, пока индекс ещё не готов, — и не врать при этом.
4. Объяснять, почему база не решает, что отсечено, хотя поле `fenced` возвращает она.
5. Собирать ответ из нескольких источников, различая «молчит» и «не отвечает».
6. Понимать, почему у консоли нет своей базы, и чем за это платят.

## Шаг 1 — Таблицы

```python
        self.db.executescript("""
            CREATE TABLE IF NOT EXISTS seen   (server TEXT, path TEXT, n INTEGER DEFAULT 0, PRIMARY KEY (server, path));
            CREATE TABLE IF NOT EXISTS events (subsystem TEXT, unit TEXT, cam INTEGER, epoch INTEGER, t REAL, kind TEXT,
                                               server TEXT, path TEXT, fields TEXT);
            CREATE INDEX IF NOT EXISTS events_cam_t ON events (cam, t);
            CREATE INDEX IF NOT EXISTS events_sub_unit_t ON events (subsystem, unit, t);
            CREATE INDEX IF NOT EXISTS events_kind_t ON events (kind, t);""")
        self.state = "empty"
```

Две таблицы. **`events`** — по строке на наблюдение, с указанием, из какого файла оно пришло. **`seen`** — сколько строк каждого файла уже прочитано; именно она превращает «перечитывать» в «дочитывать».

Три индекса — по трём вопросам, которые задают: про единицу («что с седьмой»), про подсистему с единицей и про вид («все `motion`»). Каждый — составной, со временем вторым столбцом, потому что вопрос всегда ограничен окном.

Столбец `cam` в платформенной таблице — единственная уступка предметной области во всём модуле, и она мнимая: `cam` здесь не «камера», а **поле, которое событие может нести**, проиндексированное, если оно есть. Комментарий в файле говорит это дословно: *it knows nothing about what an event means: `cam` is a field an event may carry, indexed if present*. Имя осталось от того, что именно этим полем связывают событие детектора с камерой, о которой оно говорит.

`fields` — остальные поля одной JSON-строкой. Не разложены по столбцам, потому что их набор задаёт подсистема, а таблица общая.

По умолчанию база — `":memory:"`. Она кэш; ей не обязательно переживать перезапуск, и на коробке она его не переживает. Путь к файлу можно дать (в М11 это `EVENTDB`), и тогда старт будет быстрее — но правильность от этого не зависит ни на йоту.

`state` — то, что база о себе говорит: `empty`, `catching up`, `live`. Про него шаг 5.

## Шаг 2 — Дочитывание

```python
    def _ingest(self, server: str, b: Bucket, file: str) -> int:
        with self._lock:
            row = self.db.execute("SELECT n FROM seen WHERE server=? AND path=?", (server, b.path)).fetchone()
            have = row[0] if row else 0
            if b.events <= have:                                              # nothing new
                return 0
            rows = []
            for e in read_bucket(file)[have:]:                                # the lines past what we hold
                cam = e.get("cam", int(b.unit) if b.unit.isdigit() else None)
                rows.append((b.subsystem, b.unit, cam, b.epoch, float(e["t"]), e["kind"], server, b.path,
                             json.dumps({k: v for k, v in e.items() if k not in ("t", "kind", "cam")})))
            with self.db:
                self.db.executemany("INSERT INTO events VALUES (?,?,?,?,?,?,?,?,?)", rows)
                self.db.execute("INSERT OR REPLACE INTO seen VALUES (?,?,?)", (server, b.path, have + len(rows)))
            self.indexed_segments += 0 if row else 1
            return len(rows)
```

Сердце файла, и работает оно на одном свойстве бакета: **файл только дописывается** (урок 14). Значит, число прочитанных строк — достаточное состояние: строки с первой по `have` уже в базе и никогда не изменятся.

`if b.events <= have: return 0` — закрытый бакет пропускается **без чтения файла**. Именно это делает проход по дереву дешёвым: из тысячи бакетов читается только тот один, в который сейчас пишут.

`read_bucket(file)[have:]` — дочитывание. Файл всё же читается целиком (построчный разбор JSON), и срез отбрасывает известное; для десятиминутного бакета это несколько десятков строк.

`cam` — то самое поле: берётся из события, а если его нет, но единица числовая, ею же и становится. Так событие камеры само себя связывает, а событие детектора о камере 7 несёт `cam: 7` явно.

`with self.db` — транзакция на бакет: строки и отметка прочитанного фиксируются вместе. Иначе падение между ними дало бы либо дубли (строки есть, отметка нет), либо потерю (отметка есть, строк нет).

`self._lock` — база одна, а трогают её два потока: тот, что тайлит по таймеру, и тот, что отвечает на HTTP-запросы.

## Шаг 3 — Проход по дереву

```python
    def tail(self, rebuild: bool = False) -> dict:
        self.state = "catching up" if rebuild else self.state
        added = 0
        for sub, units in subsystems_under(self.root).items():
            for unit in units:
                for b in buckets_under(self.root, sub, unit, self.bucket_seconds):
                    added += self._ingest(self.server, b, os.path.join(self.root, b.path))
        mirrored = mirrored_servers(self.root)
        for server in mirrored:
            for b in mirrored_buckets(self.root, server, self.bucket_seconds):
                added += self._ingest(server, b, os.path.join(self.root, MIRROR_DIR, server, b.path))
        self.state = "live"
        return {"added": added, "segments": self.indexed_segments, "mirrored": mirrored}
```

Своё дерево — через обнаружение каталогов (урок 14), без всякого списка подсистем. Потом копии соседей из `.mirror/` (урок 16) — и вот ключевая деталь: они вставляются **под именем настоящего владельца**, а не того, у кого лежат. Копия события с `srv-a`, хранящаяся на `srv-b`, в базе `srv-b` числится за `srv-a`. Это то, что позволит слиянию на шаге 7 отличить копию от оригинала и не показать событие дважды.

```python
    def rebuild(self) -> dict:
        """From nothing: what a restarted resource job does first."""
        with self._lock:
            self.db.executescript("DELETE FROM seen; DELETE FROM events;")
            self.indexed_segments = 0
        return self.tail(rebuild=True)
```

Две команды `DELETE` и полный проход. Вот и весь механизм «база — это кэш», выраженный тремя строками: **всё содержимое стирается, и всё возвращается из файлов.**

Это не аварийная процедура, а **штатный старт**: перезапущенный процесс ресурса делает именно это. Отсюда и право держать базу в памяти, и отсутствие резервного копирования, и то, что схему можно менять между версиями, ничего не мигрируя.

```python
    def start(self) -> "EventDatabase":
        self.rebuild()

        def loop():
            while not self._stop.wait(self.interval):
                try:
                    self.tail()
                except Exception:
                    logging.getLogger("psimplatform.eventdatabase").exception("event database tail failed")
        threading.Thread(target=loop, daemon=True).start()
        return self
```

Восстановить, потом дотаивать каждые три секунды в фоновом потоке. Три секунды — задержка, с которой только что записанное событие появляется в ответе; для страницы, где события рисуются точками на таймлайне, это незаметно.

Исключение в цикле **логируется и не убивает поток**. Сбойный бакет (испорченная строка, исчезнувший файл) не должен останавливать индексацию остального: поток жив, следующий проход через три секунды.

`daemon=True` — поток не держит процесс при выходе.

## Шаг 4 — Запрос

```python
    def query(self, t0: float, t1: float, cam=None, kind=None, subsystem=None, unit=None,
              current_epochs=None, limit: int = 1000) -> dict:
        """`current_epochs` is {(subsystem, unit): epoch} — fencing is per unit, and only the
        unit's own subsystem knows its current epoch; the database just compares."""
        sql, args = "SELECT … FROM events WHERE t >= ? AND t < ?", [t0, t1]
        if cam is not None: sql += " AND cam = ?"; args.append(cam)
        …
        sql += " ORDER BY t LIMIT ?"; args.append(limit)
        …
        for sub, u, c, ep, t, k, server, path, fields in rows:
            cur = (current_epochs or {}).get((sub, u))
            out.append({"subsystem": sub, "unit": u, "cam": c, "epoch": ep, "t": t, "kind": k, "server": server,
                        "bucket": path, "fenced": cur is not None and ep < cur, **json.loads(fields)})
        return {"events": out, "state": self.state}
```

Окно времени обязательно, остальные условия — по желанию. Порядок по времени, предел на число строк.

Самое интересное — **`current_epochs`**, и docstring объясняет, зачем так. Событие отсечено, если его эпоха меньше текущей эпохи единицы. Но текущую эпоху знает не база: она лежит в `<sub>/epoch/<unit>` в хранилище конфигурации, к которому ресурс не обращается и обращаться не должен — он платформенная работа, он не знает ни одной подсистемы.

Поэтому спрашивающий **приносит** словарь «(подсистема, единица) → текущая эпоха», а база сравнивает. Разделение труда: знание принадлежит тому, у кого оно есть, сравнение — тому, у кого данные. То же самое, что в уроке 8, где `renew_leases` сообщал факты, а решение принимал наследник.

`fields` разворачиваются в корень результата — тот же приём, что у heartbeat'а в уроке 4, и по той же причине: событие читают люди.

Возвращается **пара**: события и `state`. Второе — про следующий шаг.

## Шаг 5 — Не отвечать коротко

`state` принимает три значения: `empty` (только создана), `catching up` (идёт восстановление), `live` (актуальна).

Зачем это нужно, видно на сценарии. Ресурс перезапустился, база пуста, идёт восстановление — тридцать секунд на большом дереве. Приходит запрос «что было с седьмой за час». Ответить можно двумя способами.

Первый: вернуть то, что успело проиндексироваться. Формально — не ложь; практически — **ложь**, потому что спрашивающий получил три события вместо двадцати и не имеет причин усомниться. Пустой ответ неотличим от «ничего не происходило».

Второй: вернуть то же самое, но сказать `state: "catching up"`. Консоль покажет это словами, и человек поймёт, что смотрит на неполную картину.

Курс выбирает второй, и правило формулируется так: **система, которая не может ответить полно, говорит об этом, а не отвечает коротко.** Оно повторится в `MergedIndex` (шаг 7) и в таймлайне М11, где недоступный сервер называется по имени, а его записи объявляются *недоступными*, но не *потерянными*.

## Шаг 6 — Забывание

```python
    def forget(self, server: str, paths: list[str]) -> int:
        """Retention on the resource removed a bucket: its events go with it."""
        with self._lock, self.db:
            for p in paths:
                self.db.execute("DELETE FROM events WHERE server=? AND path=?", (server, p))
                self.db.execute("DELETE FROM seen WHERE server=? AND path=?", (server, p))
        return len(paths)
```

Проход хранения на ресурсе (урок 16) удалил бакеты по сроку — и говорит об этом базе. Удаляются строки **и** отметка прочитанного.

Второе важнее первого. Без удаления из `seen` осталась бы запись «в этом файле прочитано 42 строки», и если бы тот же бакет вернулся — а он может вернуться, копией от соседа при восстановлении диска, — `_ingest` увидел бы `b.events <= have` и **пропустил бы его целиком**. Событий не было бы ни в файлах базы, ни в ответах, хотя файл на диске есть.

Почему нельзя было положиться на проход, который сам заметит исчезновение: потому что проход идёт по **существующим** файлам. Файла нет — цикл до него не доходит, и строки жили бы в базе вечно. Удаление должно быть сказано.

## Шаг 7 — У консоли нет базы

Теперь вторая половина, и начинается она с решения, которое стоит назвать прямо.

Консоль показывает события со всех серверов. Очевидное решение — кластерная база: собрать всё в одно место, спрашивать одно место. Курс сделал наоборот: **одна база на ресурс, ни одной на консоль, ни одной на кластер.**

Причины три. **Владение**: события пишутся на диск того сервера, где работает воркер, и индексировать их правильнее там же — рядом с данными, которыми индекс живёт. **Восстановимость**: база ресурса восстанавливается из его собственного дерева, а кластерную пришлось бы восстанавливать, опрашивая все серверы, то есть она перестала бы быть кэшем в том простом смысле, в каком является эта. **Отказ**: кластерная база — это ещё одно, что должно быть живо, чтобы консоль показывала события. Сейчас сервер, который упал, уносит с собой только свои события — и консоль называет его по имени.

```python
class MergedIndex:
    """A console's view of the event databases: every live resource's `/events`, merged by time."""

    def __init__(self, objects, fetch=None, wall=time.time, lost_after: float = 45.0, timeout: float = 3.0):
        self.objects, self.wall, self.lost_after, self.timeout = objects, wall, lost_after, timeout
        self.fetch = fetch or self._http
        self.state = "live"
```

Никакого хранилища — только объектное, чтобы узнать, **кого спрашивать**: heartbeat'ы ресурсов (урок 4). `fetch` подменяемо, и тесты подсовывают вызов вместо HTTP.

```python
    def query(self, t0, t1, cam=None, …) -> dict:
        now = self.wall(); seen = resources_seen(self.objects)
        live = {s for s, hb in seen.items() if now - float(hb["ts"]) <= self.lost_after}
        …
        for server in sorted(live):
            try:
                rep = self.fetch(seen[server]["url"], params)
            except Exception:                                   # live by heartbeat, not answering
                unreachable.append(server); continue
```

Спрашиваются живые по heartbeat'у. Ресурс, который бился, но не ответил, попадает в `unreachable` — **«живой по сигналу, но не отвечающий»** — и запрос идёт дальше. Один медленный сервер не должен рушить ответ; таймаут три секунды.

```python
            for e in rep["events"]:
                if e["server"] != server:                         # a copy this resource holds for a peer
                    if e["server"] in live:
                        continue                                  # the owner answers for itself
                    key = (e["server"], e["bucket"], e["t"], e["kind"], e["unit"])
                    if key in have:
                        continue                                  # two peers hold the same copy
                    have.add(key); from_mirror.add(e["server"])
                events.append(e)
```

Самая плотная часть, и она — про копии. Ресурс может держать копии бакетов соседа (урок 16), и в его ответе они приходят **под именем владельца** (шаг 3). Три правила.

Событие своё (`e["server"] == server`) — берём.

Событие чужое, а владелец **жив** — пропускаем: он ответит за себя сам, и его ответ полнее (у него есть и незакрытые бакеты, которые не зеркалятся).

Событие чужое, владелец молчит — берём, но с защитой от дублей: копию могут держать двое соседей. Ключ — владелец, бакет, время, вид, единица.

`from_mirror` запоминает, чьи события пришли копиями, — это попадёт в `state`.

```python
        for server in sorted(seen):
            if server not in live and server not in from_mirror:
                unreachable.append(server)                        # silent, and nobody holds its copies
```

Молчащий сервер, чьих копий ни у кого нет, объявляется недоступным. А молчащий, чьи копии нашлись, — **не объявляется**: его события в ответе есть.

```python
        self.state = "live" + (f"; {', '.join(unreachable)} unreachable" if unreachable else "") \
                            + (f"; {', '.join(sorted(from_mirror))} from mirror" if from_mirror else "")
```

И честный ответ одной строкой: `live`, или `live; srv-c unreachable`, или `live; srv-a from mirror`. То же правило, что на шаге 5: сказать, а не ответить коротко.

Отсечение считается здесь же, после слияния, по тому же принесённому словарю эпох, — потому что сортировать и резать по `limit` надо до того, как помечать.

## Шаг 8 — Доказательство

Свойство, которым проверяется вся конструкция:

```python
>>> first  = EventDatabase(root, "box"); first.rebuild()
>>> second = EventDatabase(root, "box"); second.rebuild()          # вторая над тем же деревом
>>> first.query(t0, t1)["events"] == second.query(t0, t1)["events"]
True
```

Две базы над одним деревом дают один ответ. Значит, в базе нет ничего, чего нет в файлах, — то есть она кэш не по названию, а по проверяемому свойству.

И второе, из М10B:

```python
>>> platform.retain()          # срок хранения удалил два бакета и сказал базе
2
>>> db.query(t0, t1, cam=7)["events"]
[]
```

Строки ушли вместе с файлами — и вот тут кэш **не** восстановился бы сам, если бы `forget` не позвали: проход по существующим файлам не замечает исчезнувших.

**Результат:** `eventdatabase.py` на 169 строк; проверенное равенство ответов двух баз; и объяснение своими словами, почему консоль спрашивает четыре ресурса вместо одной базы.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Проход по дереву медленный | Не работает пропуск `b.events <= have`: читается каждый бакет, а не один открытый. |
| После восстановления диска события не появляются | `forget` не удалил из `seen`. Вернувшийся бакет считается уже прочитанным. |
| Дубли после перезапуска | Транзакция разорвана: строки вставились, отметка не записалась. `with self.db` должен охватывать оба. |
| Пустой ответ сразу после старта | База ещё `catching up`. Консоль обязана это показать; ответ без пометки — ложь. |
| Всё отсечено или ничего не отсечено | `current_epochs` не передан или собран не тем ключом. Ключ — пара (подсистема, единица). |
| Событие видно дважды | Копия взята при живом владельце — или потерян ключ дедупликации при двух соседях. |
| Один медленный сервер вешает страницу | Потерян таймаут или `continue` на исключении. |
| «Ничего не происходило» вместо «сервер молчит» | `state` не доходит до страницы. Недоступный сервер называется по имени. |
| В базе накопились строки удалённых бакетов | Хранение не зовёт `forget`. Проход по файлам исчезнувшего не увидит. |

## Итог

- Индекс над событиями — кэш: в нём нет ни байта, которого нет в файлах, и это проверяется равенством ответов двух баз.
- Отсюда: не подсистема, нет контроллера, нет репликации, можно держать в памяти, схему можно менять без миграций.
- `seen` превращает перечитывание в дочитывание; закрытый бакет пропускается без чтения файла.
- Копии соседей индексируются под именем настоящего владельца — иначе слияние не отличило бы копию от оригинала.
- База не решает, что отсечено: текущую эпоху приносит спрашивающий, база сравнивает.
- Система, которая не может ответить полно, говорит об этом. `catching up`, `unreachable`, `from mirror` — три способа не соврать.
- Забывание надо сказать: проход по существующим файлам исчезнувший не заметит.
- У консоли нет базы. Она спрашивает живые ресурсы и сливает ответы — по владению, по восстановимости и потому, что кластерная база была бы ещё одним, что должно быть живо.

## Упражнения

1. Уберите таблицу `seen` и перечитывайте бакеты целиком. Замерьте проход на дереве из тысячи бакетов; во сколько раз и почему?
2. Индексируйте копии под именем держателя, а не владельца. Опишите, что покажет консоль, когда владелец вернётся.
3. Уберите `state` и покажите пустой ответ во время восстановления. Напишите жалобу оператора, которая из этого получится.
4. Пусть база сама читает текущую эпоху из хранилища. Какие права ей для этого понадобятся и какое свойство ресурса при этом сломается?
5. Постройте кластерную базу вместо слияния. Перечислите, что станет проще, и назовите, что теперь обязано быть живо, чтобы консоль показывала события.
6. Два соседа держат копии одного бакета. Проследите, что происходит с дедупликацией, если у копий разные `path` (например, разный регистр).
7. Прикиньте объём таблицы `events` при пятидесяти единицах, событии в минуту и месяце хранения. Когда `:memory:` перестанет быть разумным?

## Что дальше

События пишутся воркерами, индексируются базой и сливаются консолью — а живёт всё это на ресурсе, у которого до сих пор не было ни процесса, ни правил. [**Урок 16**](16-the-resource-as-a-platform-job.md) даёт ему и то, и другое: heartbeat, сроки хранения по строке каждой подсистемы, зеркало к соседу и возвращение домой после замены диска.
