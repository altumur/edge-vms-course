# Запись событий сразу в БД

Итог разбора: что курс делает с событиями, почему он пишет jsonl и потом SQLite, какие аргументы этого пути держатся, какие нет, и как ту же задачу решают NVR и облако.

Одна фраза, пока не раскрыто остальное:

> Для сработки типичный продукт пишет сразу в таблицу. Курс пишет файл и строит кэш. Это не отраслевой стандарт и не ускорение I/O. Честный плюс таблицы — атомарность одной строки (`COMMIT`: событие есть целиком или его нет). Остаётся ещё изоляция: воркер умеет только файл и не знает, какая у вас база. Видео в ту же схему не кладут — два потока в один файл нельзя слить.

Курс этой схемой не меняется. Здесь — разбор альтернативы и границы, на которых она ломается или нет.

## 1. Две схемы

**Курс (М10–М11).** Воркер дописывает jsonl на диск своего сервера, эпоха в пути:

```
/data/archive/vms/8123/e7/20260914T150000Z.events.jsonl
```

Процесс resource на том же диске раз в ~3 с читает хвост в SQLite (`EventDatabase`). Часто `EVENTDB=:memory:`: таблица в RAM, на старте дерево читают заново. Консоль базы не держит: спрашивает каждый живой resource и сливает.

**Сразу в БД.** Воркер (или очередь в его процессе) делает `INSERT` в SQLite/MySQL/Postgres/DynamoDB. Ролик — по-прежнему файл. Поиск идёт по той же таблице, куда писали. Промежуточного jsonl нет.

Это разные жанры. Первое — «журнал на диске, оглавление можно сжечь». Второе — «событие есть строка учёта». Курс ближе к логам. Типичный NVR ближе ко второму.

## 2. Что курс утверждает — и что из этого правда

| Утверждение | Держится? | Почему |
|---|---|---|
| Писать можно, когда индекс мёртв | да, если jsonl — правда | Resource не встал, SQLite залочена — в курсе события всё равно лежат в файле |
| Старый и новый воркер не попадут в одну кучу | для **видео** — да; для **событий** — почти нет | Два `INSERT` с нормальным ключом дают две строки, не битый файл |
| Соседу копируют файл, не реплику базы | да, если jsonl — правда | Зеркало закрытого бакета — `cp`. Живая SQLite — уже кто мастер |
| Стерли файл — события исчезли сами | да в схеме курса | Retention зовёт `forget`. В БД-правде надо `DELETE` отдельно |
| Кэш можно выкинуть | да в схеме курса | Второй `EventDatabase` над тем же деревом даёт те же строки |
| Так пишут все VMS | **нет** | Frigate, ZoneMinder, Shinobi, китайские NVR — сразу в таблицу |
| Файл быстрее `INSERT` | **нет** | Наоборот: лишний хвост, задержка поиска на секунды |
| Двойной диск на каждое событие | **нет**, если кэш в RAM | Второй прочный писатель появляется только если SQLite тоже на диск |
| Эпоха в пути заменяет колонку | удобство, не другая физика | Забор тот же: колонка `epoch` + `WHERE`, или папка `e7` |
| `INSERT` атомарнее append в файл | **да, для одной сработки** | `COMMIT` — строка целиком или никак. Курс: `write` + `flush`, без `fsync`; хвост может оборваться |
| ФС вообще не умеет атомарность | **нет** | `write tmp` + `os.replace` атомарно публикует файл. Так курс переписывает манифест и двигает ролик из spool |

Курс жертвует удобством записи, чтобы запись и поиск не были одной сущностью. Как отраслевой стандарт записи сработки это не предъявить.

## 3. Уникальный ключ, счётчик, эпоха

`INSERT` не затирает чужую строку, если в ключе есть что-то своё: uuid, автоинкремент, `(камера, эпоха, время)`, id инстанса. Два воркера в одну таблицу дадут **две разные строки**. Это не битый файл.

Баг «в одну кучу» появляется только если ключ **без** поколения, например `(camera_id, timestamp)`. Оба пишут 15:03:01 — конфликт или тихий overwrite. С нормальным ключом этого нет.

Счётчик даёт разные строки. Эпоха для этого **не нужна**.

Эпоха нужна, чтобы потом понять **чьё это поколение**.

```
id=101  cam=8123  15:03:01  motion     ← старый воркер
id=102  cam=8123  15:03:01  motion     ← новый
id=103  cam=8123  15:03:02  motion     ← старый
```

Три валидных ключа. Что из этого живое? По `id` не скажешь: они вперемешку. Показать всё — нормально (как оставить `e6` на диске). Нажать на событие и открыть ролик — какой файл, `e6` или `e7`? Без метки поколения не знаете.

Счётчик ещё и **локальный**. Своя SQLite на каждом из 20 серверов — у всех `id=1`. Глобально ключ всё равно `(сервер, id)`. Одна общая БД на кластер — ключ глобальный, но общий store на пути записи и репликация.

| Задача | Хватает int / uuid | Нужна эпоха (или аналог) |
|---|---|---|
| Не затереть чужой `INSERT` | да | нет |
| Показать оба поколения | да | нет |
| Понять, какая строка живая | нет | да (`WHERE epoch = текущая`) |
| Открыть ролик с события | нет | да: какой путь, `e6` или `e7` |
| Глобальный id на 20 коробках | нет, если база локальная | не вместо сервера: ключ `(сервер, id)` |

Чем файлы лучше БД с полем `epoch`? Для событий — почти ничем в смысле «строки не смешаются». Забор тот же, только в колонке, не в пути. Забыли `WHERE epoch = текущая` — в ленте оба. В файлах «просто открыть папку камеры» уже без старого поколения, если смотрите `e7`. Это дисциплина, не другая физика.

## 4. Какие «два процесса»

У Frigate на одной коробке в таблицу событий обычно пишет **один** процесс. Двух писателей в спокойной жизни нет.

«Два процесса» — что будет, если схему «событие = строка в SQLite» поставить в архитектуру курса.

Сервер A пишет `w-17`. Питание моргнуло или `kill -STOP`. Nomad поднял **второго** `w-17` на сервере B. Старый ещё жив и тоже считает себя `w-17`.

- Файлы: старый пишет в `…/e6/…`, новый в `…/e7/…`. Разные папки.
- Одна SQLite «как правда» без эпохи в строке: оба делают `INSERT` в одну таблицу. Кто живой — в пути не написано.
- Одна SQLite **с** колонкой `epoch` (или id инстанса): две строки, как два каталога. Дальше лента режет по текущей эпохе — как консоль курса режет jsonl.

Это не баг Frigate. У него нет переезда воркера и зомби на втором сервере. Цена всплывает, когда одну базу событий делят старый и новый писатель **и** в ключе нет поколения.

На одной коробке без failover «сразу в SQLite» нормально. Два писателя — про кластер курса.

Файлы зомби не ловят. Они **не пускают его в ту же папку**. Путь собирают из эпохи, которую выдал CAS: выигрывает один, второй остаётся с шестёркой. Поиск смотрит текущую эпоху. Строки из `e6` не показывают или помечают *fenced*. Минута partition не выкинута — она просто не живая.

Старые файлы **не удаляют** только потому что эпоха старая. Это настоящая запись той минуты. На таймлайне бледные, рядом живые `e7`. Стирает их обычный retention, не «сборщик зомби». После failover `e6` лежит на старом сервере, `e7` — на новом.

## 5. Что делают продукты

### Типичный NVR

Для «событие → база приложения» в индустрии почти всегда пишут **сразу в БД**. Промежуточный jsonl ради своего же SQLite — редкость, не норма.

**Frigate.** Сработка сразу в SQLite: `Event.insert(…).on_conflict(…).execute()` в `frigate/events/maintainer.py`. Ролики — файлы в `/media/frigate/`. Документация: стёрли `frigate.db` — записи на диске сироты. Промежуточного jsonl нет. Между детектором и БД — **очередь в памяти**, не файл.

**ZoneMinder.** Метаданные событий — сразу MySQL/MariaDB. Картинка — файлы (иногда jpeg ещё и в таблицу `Frames`, то есть наоборот: кадры в БД). Не «файл событий → потом индекс».

**Shinobi.** То же: видео-файлы, события в MySQL.

**Китайские NVR.** Обычно то же: ролик на диск, сработка в локальную таблицу.

ETL «свой файл → своя БД» делают, когда писатель и склад **разные системы** (Kafka, склад аналитики), а не когда оба ваши на одном диске.

### Родственники, на которые курс похож — другой жанр

Так делают не «все VMS», а системы, где **сначала пишут журнал, индекс потом можно выкинуть**.

| Жанр | Правда | Индекс |
|---|---|---|
| Почта (`Maildir`) | файлы писем | Dovecot / notmuch |
| Фото | оригинал-файл | каталог Lightroom / «Фото» |
| Логи | `access.log` | Loki, ELK |
| git | `.git/objects` | то, что показывает `git log`; хостинг кэширует отдельно |
| Kafka | append-only топик | проекции у консьюмеров |
| Ролик в любом VMS | файл / фрагмент | в БД только «вот этот путь» |

Письмо и ролик через файл имеют смысл: их должны читать другие программы, rsync, другой сервер. Сработка камеры — дискретная запись учёта. Её обычно не отдают mutt’у.

Внутренний WAL Postgres/SQLite — не ваш jsonl: вы его не проектируете.

### Облако: Kinesis и типичный cloud VMS

В облаке промежуточный jsonl на диске писателя тоже не делают. Делают **поток или объект**, а индекс часто чужой.

**Amazon Kinesis Video Streams** (М8 курса). Продюсер шлёт фрагменты в поток из памяти/пайплайна, не «сначала файл, потом БД». AWS сам кладёт медиа и свой указатель: номер фрагмента, время продюсера. Свой SQLite вы не пишете. Playback — `GetClip` / HLS. Стёрли свой индекс — у Kinesis фрагменты всё равно есть. Это «правда в чужом store», не схема М10.

**Kinesis Data Streams / Firehose.** Тут лог → потом склад: консьюмер пишет в DynamoDB, OpenSearch, S3+Athena. Лог — отдельный продукт (replay, много подписчиков), не хвост своего же файла на той же машине. Firehose в S3 — сразу файлы для аналитики, не «чтобы потом свой SQLite собрать».

**Типичный облачный VMS** (и то, к чему приходят с KVS): ролик → S3 или KVS; сработка → сразу DynamoDB/RDS/OpenSearch, часто из Lambda на том же потоке. Две записи с бэкенда, горячий путь без «файл событий → ETL в свою БД». Обход S3 ради отчётов — потом, не для ленты камеры.

**Rekognition** и подобные: детекции уходят в Data Stream или в JSON на S3, вы уже сами решаете, класть ли в таблицу. Снова поток/объект как шина, не локальный jsonl воркера.

Облако изолирует писателя **чужим API потока/бакета**, не своим файлом. Идея та же («писатель не знает, какая у вас таблица»), реализация другая: очередь/объект как продукт, не двойной локальный склад.

| | Куда пишет «воркер» | Где поиск |
|---|---|---|
| KVS | фрагменты в сервис | индекс AWS |
| Облачный VMS | объект + сразу строка в БД | БД |
| Kafka / Kinesis Data | лог | проекции у консьюмеров |
| Курс М10 | jsonl на свой диск | свой SQLite хвостом |
| Frigate | сразу SQLite | та же SQLite |

Локальный jsonl+SQLite — не то, как устроены Kinesis и облачные VMS.

## 6. I/O

Двойная запись на диск есть, если **оба** живут на диске: дописали jsonl и ещё `INSERT` в файл SQLite. Тогда два fsync, зряшняя нагрузка.

В курсе кэш по умолчанию **в памяти**. На диск воркер пишет только jsonl. SQLite раз в три секунды *читает* хвост (часто из page cache) и держит таблицу в RAM. Второй прочный писатель не появляется. Рестарт resource — снова прочитать файлы, не догонять чужой WAL.

События сами по себе мелкие: килобайты на камеру в минуту. Рядом ролик 4 Мбит/с. Спорить об I/O событий, пока пишете видео на тот же диск — обычно не про то.

Больно станет, если:

- каждую строку jsonl сбрасывать `fsync`;
- и SQLite тоже на диск, с fsync на каждый `tail`;
- или событий как логов (тысячи в секунду на камеру), не как сработки.

Изоляция воркера стоит **одного** append в файл, не двойной БД. Двойной диск — только если кэш тоже сделали прочным. Курс этого как раз не делает.

Файл → SQLite — не оптимизация записи. Воркер пишет в файл медленнее и неудобнее, чем `INSERT`. Если бы цель была «писать быстрее» — сразу в SQLite, как Frigate.

## 7. Атомарность

Подозрение верное **для одной сработки**. Как «файловая система не умеет атомарность» — нет.

**`COMMIT` в БД.** Строка либо целиком есть, либо её нет. Читатель не видит половины JSON. Это не магия и не другой диск: SQLite сам пишет WAL, журналит, делает `fsync` в нужном порядке. База — протокол поверх той же ФС.

**Дописать строку в jsonl**, как в курсе (`EventLog.append`: `write` + `flush`, без `os.fsync`):

```
f.write(json.dumps({...}) + "\n"); f.flush()
```

`flush` только в page cache ОС. Питание моргнуло — последние строки могли не попасть на пластину. Запись оборвалась посередине строки — хвост битый. `read_bucket` делает `json.loads` на каждую непустую строку; порванная последняя роняет ingest всего бакета. Курс это знает: открытый бакет — принятая потеря при отказе диска.

Один писатель на файл у них уже есть (эпоха в пути). Значит строки двух процессов не переплетутся. Атомарность, которой не хватает, — не «два `write` вперемешку», а «краш посередине одной строки» и «строка была только в кэше».

Файловая система **умеет** атомарно публиковать целый файл: записать `.tmp`, при желании `fsync`, `os.replace`. Курс так переписывает манифест. Ролик: `rename` spool → archive (атомарно на одной ФС), потом строка в манифест. Между шагами щель: файл есть, строки нет — `repair` догоняет. Это протокол из двух шагов, не один `COMMIT`.

Что атомарность таблицы **даёт** для события:

- нет порванной строки;
- читатель не видит полусобытие;
- после краша: либо событие есть, либо нет — не надо чинить хвост jsonl.

Что она **не даёт**:

| Кажется, что даёт | На деле |
|---|---|
| Событие и mp4 вместе | Два склада. Сирота (событие без ролика / ролик без события) и у Frigate |
| Прочность без `fsync` | `synchronous=OFF` в SQLite — та же потеря, что файл без `fsync`. `COMMIT` без сброса — не прочность |
| Атомарность на два сервера | Локальная транзакция. `srv-09` умер — его строки недоступны, как его jsonl |
| Защиту от зомби | Это эпоха в строке или в пути, не `COMMIT` |

Итого: для одной дискретной сработки «сразу в БД» реально атомарнее сырого append курса. Это честный плюс таблицы, рядом с поиском без хвоста. Файлы курса атомарны там, где они пользуются `rename` (сегмент, rewrite манифеста), и не атомарны на горячем пути события.

## 8. Что остаётся, если писать сразу в БД

Аргументы «строки столкнутся», «индустрия так не делает», «так быстрее диск» — сняты.

Добавляется **атомарность одной сработки** — см. главу 7. Это не изоляция и не про зомби; это «строка не порвётся при краше».

Остаётся **изоляция**: воркер умеет только «дописать событие в свой сток» и не знает, SQLite это, Postgres, OpenSearch или завтра что-то ещё. В курсе сток — файл на resource. В облаке сток — API потока или бакета. В Frigate сток — та же SQLite, которой отвечает `/events`.

Второй остаток — **видео**. Два процесса в один и тот же `8123.mp4` портят байты. Путь с эпохой обязателен. Событие — дискретная строка, ролик — несливаемый поток. Их нельзя класть в одну схему «просто INSERT».

Третий — **зеркалирование и retention**, если jsonl больше нет. Соседу нечего `cp`. Срок хранения — `DELETE` в таблице плюс отдельно файлы роликов. Бэкап базы ≠ бэкап роликов: это цена, о которой курс говорил честно, и её NVR уже платят.

Четвёртый — **зависимость записи от индекса**. Resource не встал, база залочена, файл SQLite поехал после power loss — события писать нельзя, камера при этом жива. Frigate это принимает: нет базы — нет ленты. Курс не принимает: наблюдение уже на диске, индекс догонит.

## 9. Как выглядела бы «сразу в БД» в архитектуре курса

Не одна общая Postgres на кластер. Это вернул бы Node: запись зависит от чужого сервера, снова репликация.

Локальная таблица **на каждом сервере**, куда пишет воркер этого сервера:

```
events(
  id,            -- локальный счётчик или uuid
  server,        -- кто диск
  subsystem,
  unit,
  cam,
  epoch,         -- обязательно, иначе не открыть ролик и не отрезать зомби
  t,
  kind,
  fields
)
```

Консоль как сейчас: спрашивает каждый resource `GET /events`, сливает, режет по текущим эпохам всех подсистем. Resource по-прежнему процесс на диске; вместо хвоста jsonl он отдаёт свою таблицу.

Что надо не забыть:

1. Колонка поколения (`epoch` или id инстанса) в **каждой** строке и в **каждом** `SELECT` ленты.
2. Fence по-прежнему в консоли: resource не знает, какая эпоха сейчас в raft.
3. Ролик по-прежнему `…/<cam>/e7/….mp4`. Событие несёт эпоху, чтобы найти файл.
4. Зомби не чистить в момент failover. Показать *fenced*, стереть по `retention_days`.
5. Не делать из таблицы кластерный store. Упал `srv-09` — его события недоступны, как его ролики. Это тот же отказ, что у jsonl на его диске.
6. Очередь в памяти между детектором и `INSERT` — нормально (Frigate). Это не jsonl.

Что пропадает: доказательство «база — кэш» (второй обход дерева). Что появляется: поиск без хвоста в три секунды и без двух форматов.

## 10. Почему курс всё-таки остаётся как есть

Главы 2–7 сняли слабые доводы: скорость, «так делают все», «строки столкнутся», «ФС не умеет атомарность». Глава 8 перечислила, что осталось, — но не сделала вывода. Вот он, пятью пунктами, и первый из них в записке отсутствовал.

### 1. У Frigate один писатель событий, у курса — три

События пишут `vms/worker.py` (держатель камеры), `vms/detworker.py` (детектор) и `w2cplatform/console.py` (отметки оператора). **Три независимых процесса, три подсистемы, один ресурс.**

Сравнение с Frigate неприменимо раньше, чем начинается разговор про failover из главы 4: у Frigate **один** продюсер событий, и свою SQLite он ни с кем не делит.

Правило платформы — «один писатель на префикс», а не «один писатель на систему», и сейчас оно выполняется буквально: `vms/8123/`, `det/8123-linecross/`, `console/<instance>/`. Три дерева, ни одного общего изменяемого объекта. Детектор пишет свою строку, не зная, жив ли держатель и поднята ли консоль.

С общей таблицей они делят **блокировку**. SQLite в WAL пускает несколько процессов, но записи сериализуются, и `SQLITE_BUSY` становится состоянием, которое каждому надо обрабатывать.

Следствие важнее самой блокировки: **стоимость новой подсистемы перестаёт быть нулевой.** М10B построен на убывании — первая подсистема четыре урока, вторая, третья и четвёртая по одному. Пятая сегодня стоит YAML, воркера и каталога на ресурсе. С общей таблицей она стоит ещё и доли одной блокировки и куска одной схемы. Деградирует ровно та ось, по которой модуль оптимизирован.

### 2. Ресурс получает вопрос о консенсусе, которого у него нет

Ресурс зеркалит **закрытые** бакеты соседу обычным копированием и забирает их обратно после замены диска. Работает это потому, что закрытый бакет — неизменяемый файл.

Живую SQLite копированием не зеркалят. Нужна репликация, а с ней — «кто мастер». Ресурс — единственный компонент курса, определённый как не имеющий контроллера и ничего не решающий: он там, где он есть. Проектная записка М11 отвергла моделирование архива подсистемой со ссылкой на чужие грабли (Nomad #12118, CSI-тома); таблица как правда вернула бы тот же класс задач через другую дверь.

### 3. Одна история отказа вместо двух

Сейчас на все данные одна фраза: **теряется ровно открытое.** Открытый сегмент при `kill -9`, открытая строка бакета при пропаже питания. Одно объяснение, одна величина, один способ её ограничить.

С таблицей у видео остаётся файловая история, а у событий появляется транзакционная — со своими `synchronous`, WAL, восстановлением после power loss и версией формата. Две модели отказа там, где была одна.

### 4. `repair` перестаёт покрывать половину архива

Сейчас **весь** архив восстановим с диска: манифесты — `repair` из путей, события — `EventDatabase.rebuild` из бакетов. Диск, вынутый и принесённый на другую машину, самодостаточен.

С событиями в таблице диск несёт видео и файл базы, который может быть повреждён, заблокирован или несовместим по версии. «Забрать диск целиком» перестаёт работать — а это то, ради чего индекс с самого начала лежит рядом с данными.

### 5. Для курса — решающее

Позвоночник курса — одна мысль, повторённая семь раз: **то, что выводится, не хранят.** `actual` в памяти, вычисляемый статус воркера, путь как самодостаточная запись, `repair`, модель чтения, `EventDatabase` как кэш, `MergedIndex`.

События — единственное место, где это **демонстрируется буквально**: удалить базу, пересобрать, получить тот же ответ. На это есть тест.

Убрав демонстрацию, вы оставляете шесть остальных появлений россыпью отдельных приёмов. Для продукта это слабый довод. Для курса он сильнее прочих: текущая схема **учит тому, чему альтернатива научить не может**, и делает это в модуле, который обосновывает платформу.

### Что из главы 7 признано и что с этим сделано

Атомарность одной сработки — настоящий плюс таблицы. Но разрыв уже, чем выглядело:

**Переплетения строк нет.** Дозапись короткой строки в файл, открытый на дозапись, не смешивается с чужой — и писатель тут в любом случае один, эпоха в пути это гарантирует. Остаётся краш посередине строки и строка, оставшаяся в кэше страниц. Это **политика `fsync`**, то есть ручка, а не архитектура.

**А вот это было настоящим багом, и он исправлен** *(16 сентября 2026)*. `read_bucket` делал `json.loads` на каждой непустой строке, и одна оборванная последняя строка роняла **весь бакет** — десять минут наблюдений вместо одной повреждённой записи. Это не соответствовало истории видео, где теряется ровно открытый сегмент, а не день.

Теперь неразбираемая строка пропускается и считается (`w2cplatform.events.torn`), а счётчик виден снаружи. Принятая потеря стала **последней строкой** вместо десяти минут, и разрыв с транзакцией сократился до величины, о которой уже не спорят. Тест: `test_a_torn_last_line_loses_the_line_not_the_bucket`.

### Вывод

Оставить как есть — не потому, что «так лучше вообще» (индустрия пишет в таблицу, и записка права), а потому, что в **этой** системе таблица связывает трёх независимых писателей общей блокировкой, вносит консенсус в компонент, спроектированный без него, раздваивает модель отказа и лишает диск самодостаточности.

Плата за это — один append и знание, что последняя строка не гарантирована. После починки `read_bucket` цена стала честной.

## 11. Коротко

```
сработка  ── курс ──────── jsonl на свой диск ──хвост──► SQLite (часто RAM)
          ── NVR ───────── очередь в памяти ───────────► SQLite / MySQL
          ── облако ────── поток / объект ─────────────► чужой индекс
                                                       или сразу Dynamo/RDS
ролик     ── везде ─────── файл / фрагмент с поколением в пути
```

Сработка и ролик — разная физика. Ролик без эпохи в пути нельзя. Сработку в таблицу с колонкой эпохи — можно, и так делают продукты. Таблица даёт атомарность одной строки; сырой append курса — нет. Курс платит лишний шаг, чтобы воркер не знал базу и чтобы индекс можно было сжечь. Это контракт, не стандарт индустрии — и для системы с тремя писателями событий и ресурсом без консенсуса он окупается (глава 10).
