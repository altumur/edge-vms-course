# Урок 26 — Свой резервный архив

**Модуль:** М10B — ServerVMS (часть вторая)
**Вы напишете:** вид тома `backup` в `vms/volumes.py` и два правила размещения за именованными дверями платформы (`register_admit`, `register_near_rank`); дверь архива у регистратора (`serve_archive`) и сводку покрытия резервной записи в heartbeat; второй источник дозаписи — `backup_sources`, чтение манифеста и копию диапазона (`copy_range`) вместо перезаписи; и резервную запись `when: offline`, которая пишет только за упавшую основную.
**Время:** ~90 минут.

## Зачем этот урок

Урок 16 закрывал дыры записи из архива **устройства**: из того, что камера хранит на своей карте, через дверь воспроизведения держателя. Когда код курса стал продуктом, эта дверь оказалась закрыта — у привязки к DriverPack в продукте нет вызовов хранилища и воспроизведения, они только зарезервированы. Зато открытой оказалась другая: **наши собственные архивы**.

Критичную камеру пишут дважды. Основная запись — на диски сервера, как всегда. Резервная — на том вида `backup`: диск второго сервера или карту камеры, которая сама работает на платформе. Основная закрывает из резервной любую дыру: обрыв связи с сервером, секунды переезда собственного регистратора, перезагрузку. Механизм — урок 16 целиком, над вторым видом источника.

Урок 10 уже сделал две записи одной камеры правкой YAML: `id: name`, и «камера 7 на диски» и «камера 7 в сетевой архив» — две строки. Там две записи были двумя **независимыми** копиями, и пропуск одной оставался пропуском. Здесь одна из них становится **источником** для другой — и из этого вытекает всё остальное в уроке: где резервная запись может жить, рядом с какой из двух стоит воркер камеры, и когда резервной вообще писать.

> **Что проверяется без железа.** Всё, в `tests/test_backup_archive.py`: камера, основная запись на `srv-a`, резервная на томе `backup` сервера `srv-b`, у каждой свой настоящий `RecWorker` со своим архивом; резервный регистратор отдаёт архив по HTTP. Копия ровно недостающих ста секунд; дыра внутри самой резервной; резервная, которая ни у кого не берёт; правило тома при упавшем сервере; воркер камеры рядом с резервной записью; и запись по отказу — работающая основная, молчащая, выключенная и закончившееся событие.

## Что нужно знать заранее

- **Урок 10** — тома (`rec/volumes/*`), их захват, `place_by: volume`, `home` как предпочтение; две записи одной камеры.
- **Урок 15** — держатель публикует сводку покрытия, а не индекс.
- **Урок 16** — дозапись: наше покрытие, дыры вычитанием, бюджет, «только дыры», и шаг 9 — память о пустом, конец видимого, дыры только внутри записанного.

- **Урок 25** — запись по событию: строка с `until`.

## Чему вы научитесь

1. Объяснить, почему резервный архив — это **запись**, а не новый механизм.
2. Найти резервный источник так же, как находится всё остальное, — в heartbeat.
3. Планировать по сводке и копировать по манифесту.
4. Скопировать диапазон, а не записать его заново.

7. Писать резервную только за сбой основной, никогда за решение.

## Шаг 1 — Резервный том

```python
KINDS = ("local", "network", "backup")
ON_A_BOX = ("local", "backup")
```

Том вида `backup` — диск на **одной** коробке, как локальный: карта в камере или диск второго сервера. Поэтому он обязан назвать свой сервер:

```python
    if kind == "backup" and not str(fields.get("server", "")):
        raise Refused("a backup volume is a disk on one box — a camera's card, a second server — and a copy "
                      "is only a copy if you know which box it is on: name it")
```

Всё остальное — захват тома регистратором, квота, ватерлиния, `archives_of` у ресурса — работает с ним как с локальным: `ON_A_BOX` заменил в трёх местах проверку `kind == "local"`.

Резервная запись — обычная строка `rec/recordings/*`, у которой `home` — резервный том:

```
rec/recordings/7        {cam: 7, home: disks}
rec/recordings/7-copy   {cam: 7, home: copy}          ← copy — том вида backup на srv-b
```

Ни новой подсистемы, ни нового вида строки. **Резервность — свойство тома, а не записи**: `is_backup(row)` смотрит, на каком томе живёт запись.

## Шаг 2 — Резервная говорит, что у неё есть

Урок 15 научил держателя публиковать сводку покрытия карты: начало, конец, число фрагментов. Резервный регистратор делает то же для своей записи — в её статусе в heartbeat:

```python
        if volumes.is_backup(cam, self.vars):
            ours = self.our_coverage(cam["id"])
            if ours:
                out["coverage"] = {"from": ours[0][0], "to": ours[-1][1], "fragments": len(ours)}
```

И рядом — дверь, через которую его архив можно прочитать. Это те же два маршрута, что у ресурса (`vms/resource.py`): `/manifest/<unit>` и `/segment/<path>`, только над архивом, который пишет **этот** процесс. `serve_archive()` поднимает их и кладёт адрес в heartbeat как `archive_url`.

Сводка, а не индекс, — по той же причине, что в уроке 15: heartbeat читают все и часто, а резервная запись по движению держит тысячи фрагментов.

## Шаг 3 — Где искать резервную

Так же, как здесь находится всё, — в heartbeat'ах:

```python
    def backup_sources(self, row: dict, now: float | None = None) -> list[dict]:
        names = volumes.backups(self.vars)
        if not names or volumes.is_backup(row, names=names):
            return []
        ... записи той же камеры, чей дом — резервный том,
        ... у живого регистратора, который публикует archive_url и coverage
```

Два отказа в первых строках — правила, а не оптимизации. **Сама себе запись не источник.** И **резервная не берёт ни у кого**: ни у основной, ни с карты. Резервная, дозаписывающая свои дыры из основной, заполнила бы их тем же, что есть у основной, — и два архива перестали бы быть двумя независимыми свидетельствами того, что видела камера. Одна дыра, скопированная в обе стороны, — это одна дыра дважды.

Источники одной записи идут по порядку: сначала устройство (урок 16), потом каждая резервная запись той же камеры.

```python
    def sources_of(self, row: dict) -> list[dict]:
        out = []
        dev = self.device_source(row["cam"])
        if dev is not None:
            out.append({"key": "device", "kind": "device", "url": dev[0], "coverage": dev[1]})
        return out + self.backup_sources(row)
```

## Шаг 4 — План по сводке, копия по манифесту

`gaps` из урока 16 не меняется: дыры — это покрытие источника минус наше, в тех же границах. Меняется только то, что происходит с каждой дырой.

У устройства есть только сводка, и выкачка говорит правду о дырах карты лишь после того, как её сделали (шаг 9 урока 16). У резервной записи есть **манифест** — точный список того, что она держит. Поэтому перед копированием его читают через её дверь, и копируется ровно то, что в нём есть:

```python
        segs = self.read_manifest(src["url"], src["recording"])
        for seg in sorted(segs, key=lambda x: x.start):
            lo, hi = max(t0, seg.start), min(t1, seg.end)
            if hi > lo:
                paths += self.actuator.copy_range(unit, f"{src['url']}/segment/{seg.path}#{seg.start}",
                                                  self.epochs.get(unit, 0), lo, hi, self.archive.spool)
```

План по сводке, решение по манифесту — то же «проверить дважды», что в шаге 6 урока 16, только вторая проверка точнее первой. Чего нет и в манифесте резервной, запоминается как пустое для **этого** источника (`backup:7-copy`), и следующий проход у неё не спрашивает. У устройства при этом можно спросить: у него своя память.

## Шаг 5 — Копия, а не вторая запись

Устройство отдаёт диапазон воспроизведением, и урок 16 прогоняет его через конвейер: `record_range`. Для своего архива это неправильно сразу по двум причинам.

Во-первых, это медленно: воспроизведение идёт в реальном времени, а сегменты резервной уже лежат файлами. Во-вторых, и это важнее, это **вторая запись того же**, а не копия: всё, что конвейер делает с потоком, он сделает ещё раз. Продукт нашёл это на ящике: его приёмник ставил кадру метку времени прихода, и позавчерашний час лёг бы как «сейчас».

Поэтому у исполнителя второй метод, `copy_range`: взять сэмплы сегмента как они хранятся, с их метками, и положить в наш спул. Настоящий — тот же демукс в тот же приёмник, что у `record_range`, с переходом (seek) к нужному месту сегмента; поддельный пишет файлы, как для любого диапазона. Режется диапазон по дыре: копируются не десятиминутные сегменты резервной целиком, а ровно недостающие сто секунд, иначе дыра шириной в переезд регистратора не закрылась бы никогда — сегмент резервной, покрывающий её, перекрывает нашу запись с обеих сторон.

Дальше всё из урока 16: `promote`, текущая эпоха регистратора, наш срок хранения, проверка перекрытия перед записью. Одно новое значение поля:

```
{"kind":"media","cam":"7","epoch":4,"start":…,"end":…,"path":…,"source":"backup"}
```

В курсе происхождение по-прежнему живёт в строке манифеста, а не в пути, — по той же причине, что `edge`. Продукт здесь разошёлся с курсом: у тома ObjectStorage нет ни манифеста, ни починки по пути, и имя потока — единственное место для метаданных, поэтому там дозапись пишется в свой поток `<rec>/e<n>/backfill`. Обе стороны правы для своего хранилища.

## Шаг 6 — Резервный том — не место для чужих, и резервная — не место для чужого тома

`home` в курсе — **предпочтение**, и урок 11 М10A объяснил почему: дом, который упал, не должен делать запись неразмещаемой — именно тогда работа и должна продолжиться где-то ещё.

Для резервного тома это неверно в обе стороны. Основная запись, переложенная на него, пока её сервер перезагружался, оставляет **одну** копию там, где их должно быть две — а на карте ещё и занимает аплинк камеры. Резервная, переложенная на диск основной, — не копия вовсе.

Предпочтение здесь нужно заменить фильтром, а платформа про тома ничего не знает. Для таких правил у неё есть дверь того же рода, что `register_constraint`, — правило подсистемы кодом под именем:

```python
register_admit("rec", admit_recording)

def admit_recording(ctl, row: dict, worker: str) -> bool:
    names = backups(ctl.vars)
    if not names:
        return True
    place = ctl.place_of(worker)
    home = str(row.get("home") or "")
    if home in names:
        return place == home
    return place not in names
```

`admit` работает в `eligible`, рядом с метками и `spread_by`, поэтому он сильнее и `home`, и `near`, как любой фильтр. Запись, которой некуда, попадает в `/unplaceable` и говорит об этом — честный ответ на «сервер с резервным томом упал».

## Шаг 7 — Воркер камеры — рядом с резервной

Воркер камеры следует за записью (`near: {sub: rec, of: cam}`, `home: near`, урок 11 М10A). Записей теперь две, и `holder_near` выбирал из них меньшую по имени — обычно основную.

Это очевидный выбор и неправильный. Падение сервера основной уносит с собой и воркер камеры, и резервная запись теряет поток ровно в ту минуту, ради которой она существует. Воркер рядом с резервной переживает падение сервера основной; резервная продолжает писать; основная, переехав, дозаписывает из резервной собственный переезд.

Вторая дверь платформы — порядок среди нескольких совпадений:

```python
register_near_rank("vms", rank_near_recording)       # резервная запись первой
```

Платформа по-прежнему не знает, что такое резерв: она сортирует найденных по числу, которое вернула подсистема, а при равенстве — по имени, чтобы два прохода пришли к одному серверу.

## Шаг 8 — Писать за сбой, никогда за решение

Резервная, которая пишет всегда, стоит второго архива и, на карте, второго потока через аплинк камеры. Часто это правильно. Но есть установки, где резервная нужна **только** когда основная не пишется: `when: offline`.

Соблазнительное правило — «писать, когда камеру никто не пишет» — неверно. Выключенная основная — это «никто не пишет». Запись по событию между событиями — тоже. С таким правилом резервная писала бы всегда, а запись по событиям стала бы постоянной — на диске резервной.

Правило то же, что у дозаписи в шаге 9 урока 16: **прикрывается сбой, а не решение.** Резервная пишет за основную, которая **должна** писаться — включена, и её `until` не прошёл, — и не пишется:

```python
            until = float(other.get("until") or 0)
            should = bool(other.get("enabled")) and (until == 0 or until > now)
            if not should or str(other["id"]) in running:
                ...                                        # не повод
            since = self._not_written_since.setdefault(str(other["id"]), now)
            need = need or now - since >= self.START_GRACE
```

И только что замолчавшей основной даются секунды: так начинается **каждая** запись по событию — строка появилась, конвейер поднимается, — и будить резервную на каждое событие не нужно.

Пока резервной писать не за кого, её строки нет в `desired()`, и её статус говорит об этом словами: `standby` — *the primary recording is being written*.

**Чего в курсе нет.** Продукт держит конвейер резервной всегда запущенным, «на удержании», и кольцо последних тридцати секунд в памяти его приёмника: когда пропажу основной замечают, кольцо пишется первым, и запись начинается раньше пропажи (на ящике — за 28,5 секунды до снятия удержания). Это работа конвейера и приёмника, а не планировщика, и в курсе её нет: здесь резервная `when: offline` начинает писать через `START_GRACE` после того, как основная замолчала, и первые секунды пропажи закрывает только дозапись из устройства, если она есть.

## Что может пойти не так

- **Резервная берёт у основной.** Дыра копируется в обе стороны, и два архива становятся одним.
- **Копировать по сводке.** Сводка не знает дыр резервной; каждая пустая копия занимает дверь её регистратора, и без памяти о пустом — каждый проход.
- **Копировать сегменты целиком.** Дыра шириной в переезд регистратора не закроется никогда: сегмент резервной перекрывает нашу запись с обеих сторон.
- **Записать заново вместо копии.** Реальное время вместо скорости диска, и метки времени того, кто записал заново.
- **`home` предпочтением для резервного тома.** Основная переедет на резервный том при перезагрузке своего сервера, и копий станет одна.
- **Воркер камеры рядом с основной.** Падение её сервера забирает и поток резервной.
- **`when: offline` как «никто не пишет».** Выключенная основная и паузы между событиями превратят резервную в постоянную.
- **Без секунд на старт.** Резервная просыпается на каждое событие и пишет его дважды.

## Итог

- Резервный архив — это **запись** на томе вида `backup`: ни новой подсистемы, ни нового вида строки.
- Резервная публикует сводку покрытия и дверь архива; основная находит её в heartbeat'ах.
- Источники дозаписи идут по порядку: устройство, затем резервные записи той же камеры.
- План — по сводке, копия — по манифесту; чего нет и там, запоминается для этого источника.
- Диапазон копируется, а не пишется заново, и режется по дыре.
- Резервная не берёт ни у кого.
- Для резервного тома `home` — фильтр: дверь `register_admit`.
- Воркер камеры стоит рядом с резервной записью: дверь `register_near_rank`.
- `when: offline` пишет за основную, которая должна писаться и не пишется; за решение — никогда.
